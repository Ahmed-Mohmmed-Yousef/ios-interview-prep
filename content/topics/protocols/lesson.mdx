## The simple idea

<Analogy>
Think of a driver license requirement. A licensing agency requires drivers to pass a vision test and follow road signs. The agency does not care what brand of car you drive. Both compact cars and large trucks can meet the requirements. In Swift, a protocol works like a license: it sets rules and capabilities that any conforming struct, enum, or class must satisfy.
</Analogy>

In Swift, a **protocol** defines a blueprint of methods, properties, and other requirements for a particular task.

A protocol does not provide storage or implementation on its own. Instead, structs, enums, and classes **conform** to the protocol by implementing its requirements.

Core protocol rules:
- **Property requirements**: Always declared with `var`. Must specify whether each property is gettable (`{ get }`) or gettable and settable (`{ get set }`).
- **Method requirements**: Declares function signatures without bodies. Methods that modify value types must use the `mutating` keyword.
- **Initializer requirements**: Declares initializers that conforming types must provide. Non-final classes must mark them with `required`.
- **Class-only protocols**: Protocols inheriting from `AnyObject` can only be adopted by classes. This is necessary for weak delegate references.

## In code

<CodeExample title="Defining protocols and conforming structs and classes">

```swift
protocol Greetable {
    var name: String { get }
    func greet() -> String
}

struct Student: Greetable {
    let name: String
    func greet() -> String {
        return "Hello, my name is \(name)."
    }
}

class Teacher: Greetable {
    var name: String
    init(name: String) {
        self.name = name
    }
    
    func greet() -> String {
        return "Welcome class, I am Professor \(name)."
    }
}

let members: [any Greetable] = [
    Student(name: "Taylor"),
    Teacher(name: "Anderson")
]

for member in members {
    print(member.greet())
}
```

```output
Hello, my name is Taylor.
Welcome class, I am Professor Anderson.
```

</CodeExample>

This example shows the flexibility of protocols:
- **Shared contract**: `Student` (a value type) and `Teacher` (a reference type) share a common interface.
- **Read-only satisfaction**: `Student` fulfills `{ get }` with a constant `let name`.
- **Existential collection**: `[any Greetable]` holds any conforming type, allowing clean polymorphic iteration.

<CodeExample title="Mutating methods and class-only delegate protocols">

```swift
protocol Togglable {
    mutating func toggle()
}

struct LightSwitch: Togglable {
    var isOn = false
    
    mutating func toggle() {
        isOn.toggle()
    }
}

var bedroomSwitch = LightSwitch()
bedroomSwitch.toggle()
print("Switch is on: \(bedroomSwitch.isOn)")

// Class-only protocol for delegates
protocol TaskDelegate: AnyObject {
    func taskDidFinish()
}

class Worker {
    weak var delegate: TaskDelegate?
    func completeWork() {
        print("Work completed.")
        delegate?.taskDidFinish()
    }
}

class Supervisor: TaskDelegate {
    func taskDidFinish() {
        print("Supervisor received notification.")
    }
}

let supervisor = Supervisor()
let worker = Worker()
worker.delegate = supervisor
worker.completeWork()
```

```output
Switch is on: true
Work completed.
Supervisor received notification.
```

</CodeExample>

This code highlights two critical protocol patterns:
- **`mutating` keyword**: Enables value types to modify their stored properties inside protocol methods. Classes omit `mutating`.
- **`AnyObject` constraint**: Restricts `TaskDelegate` to classes. This enables `weak var delegate` to prevent retain cycles.

## Interview traps

<Trap title="Forgetting the mutating keyword on protocol methods for value types">
If a protocol method alters properties on a conforming struct, you must declare it with `mutating func` in the protocol. If you omit `mutating`, structs cannot mutate `self` inside that method.
</Trap>

<Trap title="Declaring weak delegate references without AnyObject">
ARC can only manage weak references on class instances. If a protocol does not inherit from `AnyObject`, writing `weak var delegate: MyDelegate?` causes a compiler error.
</Trap>

<Trap title="Assuming protocols can store property values directly">
Protocols declare property requirements, not physical storage. They cannot allocate memory or store default property values on their own.
</Trap>

## How to answer in the interview

<InterviewAnswer level="fresh">
A protocol in Swift is a contract defining required properties and methods. Classes, structs, and enums can conform to protocols by implementing those requirements. Protocols let different types share behavior without relying on class inheritance.
</InterviewAnswer>

<InterviewAnswer level="junior">
Protocols define blueprints for properties, methods, and initializers. Property requirements specify get or get set access. For value types, methods modifying self must be marked mutating. Class-only protocols inherit from AnyObject, which allows them to be used with weak references in delegate patterns.
</InterviewAnswer>

<InterviewAnswer level="senior">
Swift is a protocol-oriented language. Protocols decouple interfaces from concrete implementations, enabling horizontal composition across value types. Existential types using any Protocol introduce dynamic dispatch and boxing overhead. In contrast, opaque types with some Protocol and generic constraints allow static devirtualization and compiler optimizations.
</InterviewAnswer>

## Recap

<Recap>
- Protocols define blueprints of properties, methods, and initializers without storage.
- Classes, structs, and enumerations can all conform to protocols.
- Properties specify `{ get }` or `{ get set }` requirements using `var`.
- Methods modifying value types must use the `mutating` keyword in the protocol.
- Non-final classes must mark protocol initializers with `required`.
- Class-only protocols inherit from `AnyObject` to allow `weak` delegate references.
</Recap>
