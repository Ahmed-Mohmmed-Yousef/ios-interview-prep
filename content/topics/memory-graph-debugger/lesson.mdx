## The simple idea

Automatic Reference Counting frees an object when its reference count drops to zero. If two objects hold strong references to each other, their count never reaches zero. This creates a retain cycle, also known as a memory leak.

<Analogy>
  Imagine two people holding hands. Neither person lets go until the other lets go first. Both people stay stuck forever. The Memory Graph debugger takes a photograph of the room so you can spot who holds hands.
</Analogy>

The Xcode Memory Graph debugger pauses your app and scans heap memory. It builds a visual map of every active object and the strong pointers between them.

When Xcode finds an isolated cycle of objects that reference each other, it marks them with a purple exclamation badge. You click any node to see who owns it.

To see the exact line of code that created a leaked object, turn on Malloc Stack Logging in your scheme diagnostics.

## In code

Here is an example of a retain cycle created by a closure. The closure strongly captures `self`, and `self` holds the closure. The object never deallocates.

```swift
final class DetailScreen {
    var onDismiss: (() -> Void)?
    let name: String

    init(name: String) {
        self.name = name
    }

    func setup() {
        onDismiss = {
            print("Dismissing \(self.name)")
        }
    }

    deinit {
        print("DetailScreen deinit")
    }
}

var screen: DetailScreen? = DetailScreen(name: "Profile")
screen?.setup()
screen = nil
print("End of retain cycle test")
```
```output
End of retain cycle test
```

Notice that `deinit` never runs. In the Xcode Memory Graph, you see both `DetailScreen` and its closure lingering on the heap with a purple badge.

To break the cycle, add a weak capture list `[weak self]` inside the closure.

```swift
final class SafeScreen {
    var onDismiss: (() -> Void)?
    let name: String

    init(name: String) {
        self.name = name
    }

    func setup() {
        onDismiss = { [weak self] in
            guard let self = self else { return }
            print("Dismissing \(self.name)")
        }
    }

    deinit {
        print("SafeScreen deinit")
    }
}

var safe: SafeScreen? = SafeScreen(name: "Settings")
safe?.setup()
safe = nil
print("End of safe test")
```
```output
SafeScreen deinit
End of safe test
```

Now `SafeScreen` deallocates immediately when `safe` is set to nil. The Memory Graph debugger shows zero instances lingering.

## Interview traps

<Trap label="Purple badges do not find every leak">
  Xcode only puts a purple badge on isolated retain cycles that have no incoming external references. If an object is kept alive by a global collection or a singleton, it is still reachable. Xcode will not flag it with a purple badge. You must filter by class name and check instance counts manually.
</Trap>

<Trap label="Debugging without Malloc Stack Logging">
  Opening the Memory Graph without Malloc Stack Logging reveals that an object exists, but you cannot see where your code created it. Always enable Malloc Stack Logging under Scheme Diagnostics before hunting leaks.
</Trap>

## How to answer in the interview

<InterviewAnswer level="mid">
  I use the Xcode Memory Graph debugger by clicking the three-node icon during a debug session. It pauses the app and shows all objects on the heap. Xcode marks isolated retain cycles with purple warning badges. I enable Malloc Stack Logging in scheme diagnostics so I can inspect the exact call stack that allocated the leaking instance. Once I identify the circular strong reference, I break it with weak or unowned references.
</InterviewAnswer>

<InterviewAnswer level="senior">
  I use the Memory Graph debugger to distinguish true retain cycles from abandoned memory. Retain cycles form isolated islands with zero external roots and show purple warnings. In contrast, abandoned memory occurs when objects remain reachable through singletons, notification observers, or caches, which ARC cannot clean up. To diagnose leaks automatically, I export `.memgraph` files and run command-line tools like `leaks`, `vmmap`, and `malloc_history` in continuous integration pipelines.
</InterviewAnswer>

## Recap

<Recap>
  The Xcode Memory Graph debugger pauses your app to show all heap allocations and references. Purple badges highlight isolated retain cycles. Turn on Malloc Stack Logging in Scheme Diagnostics to see allocation call stacks. Remember that abandoned memory still attached to roots will not show a purple badge, so verify instance counts after closing screens.
</Recap>
