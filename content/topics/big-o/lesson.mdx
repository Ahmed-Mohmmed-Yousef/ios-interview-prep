## The simple idea

<Analogy>
Imagine looking for a person in a long line at a movie theater.

If you know their ticket number, you can walk straight to their seat in one step. This is constant time: O(1).

If you must check every face one by one, your search time grows with the line. Checking 10 people takes 10 steps. Checking 1,000 people takes 1,000 steps. This is linear time: O(n).

Big-O notation gives us a shared language to describe how time and memory grow as the input gets larger.
</Analogy>

In computer science, **Big-O notation** measures how an algorithm grows as the input size $n$ gets very large.

We use Big-O to check two things:
- **Time complexity**: How the number of steps grows as input size grows.
- **Space complexity**: How much extra memory (auxiliary space) the code creates as input size grows.

In interviews, Big-O usually describes the worst case, though average-case costs (like hash lookups) also use Big-O. We drop constant multipliers and smaller terms. For example, $O(2n + 5)$ simplifies to $O(n)$ because the $2$ and $+ 5$ do not matter as $n$ grows huge.

Here are the six most common time complexities, from fastest to slowest:
1. **$O(1)$ — Constant time**: The work stays the same no matter how large $n$ becomes. Reading an array element with `array[0]` takes $O(1)$ time.
2. **$O(\log n)$ — Logarithmic time**: The work cuts the remaining problem in half at every step. Binary search on a sorted list takes $O(\log n)$ time.
3. **$O(n)$ — Linear time**: The work scales in direct proportion to $n$. A single loop over an array takes $O(n)$ time.
4. **$O(n \log n)$ — Linearithmic time**: Common in efficient sorting algorithms like Swift's `array.sorted()`.
5. **$O(n^2)$ — Quadratic time**: The work multiplies with nested loops over the data. Checking every pair in an array takes $O(n^2)$ time.
6. **$O(2^n)$ — Exponential time**: The work doubles with each added item. Naive recursive Fibonacci calculations take $O(2^n)$ time.

## In code

<CodeExample title="Comparing O(1), O(n), and O(n^2) time complexity in Swift">

```swift
let numbers = [10, 20, 30, 40, 50]

// 1. O(1) Constant Time
let firstNumber = numbers[0]
print("First item: \(firstNumber)")

// 2. O(n) Linear Time
func linearSearch(in array: [Int], target: Int) -> Bool {
    for item in array {
        if item == target {
            return true
        }
    }
    return false
}
print("Found 30: \(linearSearch(in: numbers, target: 30))")

// 3. O(n^2) Quadratic Time
func countDuplicatePairs(in array: [Int]) -> Int {
    var count = 0
    for i in 0..<array.count {
        for j in (i + 1)..<array.count {
            if array[i] == array[j] {
                count += 1
            }
        }
    }
    return count
}
let duplicates = [1, 2, 2, 3, 3]
print("Duplicate pairs: \(countDuplicatePairs(in: duplicates))")
```

```output
First item: 10
Found 30: true
Duplicate pairs: 2
```

</CodeExample>

This example contrasts the three most common time curves in daily Swift programming:
- **`numbers[0]`**: Swift arrays support random access. Reading any element by index takes $O(1)$ constant time.
- **`linearSearch`**: In the worst case, the loop checks all $n$ items. The time complexity is $O(n)$.
- **`countDuplicatePairs`**: The outer loop runs $n$ times and the inner loop runs up to $n$ times. The time complexity is $O(n^2)$.

<CodeExample title="Measuring space complexity and recursive call stack memory">

```swift
// 1. O(1) Auxiliary Space: Uses a fixed set of scalar variables
func calculateSum(of array: [Int]) -> Int {
    var total = 0
    for number in array {
        total += number
    }
    return total
}

let items = [1, 2, 3, 4]
print("Sum: \(calculateSum(of: items))")

// 2. O(n) Auxiliary Space: Allocates a new array with n elements
func squareAll(numbers: [Int]) -> [Int] {
    var result: [Int] = []
    result.reserveCapacity(numbers.count)
    for number in numbers {
        result.append(number * number)
    }
    return result
}
print("Squared: \(squareAll(numbers: items))")

// 3. O(n) Call Stack Space: Recursion creates a stack frame per level
func countdown(from n: Int) {
    if n <= 0 {
        print("Blast off!")
        return
    }
    countdown(from: n - 1)
}
countdown(from: 3)
```

```output
Sum: 10
Squared: [1, 4, 9, 16]
Blast off!
```

</CodeExample>

Space complexity measures the extra memory code allocates while running:
- **`calculateSum`**: Uses only one integer variable `total`. Its extra space complexity is $O(1)$.
- **`squareAll`**: Allocates a new array for $n$ integers, so its extra space is $O(n)$. Calling `result.reserveCapacity(numbers.count)` reserves space for all $n$ items once to avoid repeated resizing.
- **`countdown`**: Each recursive call pushes a frame onto the system call stack. A depth of $n$ recursive calls uses $O(n)$ stack space.

## Interview traps

<Trap title="Assuming string.count is O(1)">
In many languages, string length is stored as a number and read in $O(1)$ time. In Swift, each `Character` is an **extended grapheme cluster** made from one or more Unicode parts.

Swift walks those Unicode boundaries across the string to count characters. As a result, `string.count` takes **$O(n)$** linear time.

Do not write `string.count == 0` to check for an empty string. Always use **`string.isEmpty`**, which only checks `startIndex == endIndex` in guaranteed $O(1)$ constant time.
</Trap>

<Trap title="Calling contains inside an array loop">
Checking whether an array contains an item with `array.contains(x)` takes $O(n)$ linear time.

If you call `array.contains` inside a loop that also runs $n$ times, total runtime becomes **$O(n^2)$**.

To fix this, use a **`Set`** (an unordered collection of unique values with fast lookup). Writing `var seen = Set<Int>()` lets you check `seen.contains(x)` and call `seen.insert(x)` in $O(1)$ average time, dropping total time to **$O(n)$**.
</Trap>

<Trap title="Inserting elements at index 0 of an array">
`array.append(element)` adds an item to the end of an array in $O(1)$ average (amortized) time.

However, calling `array.insert(element, at: 0)` forces Swift to shift all $n$ items one slot to the right in memory. This makes inserting at the front an **$O(n)$** operation.
</Trap>

<Trap title="Forgetting call stack space in recursion">
Even when a recursive function creates no local arrays, each call takes space on the call stack.

If a function recurses $n$ levels deep, its space cost is **$O(n)$**, not $O(1)$. Very deep inputs can crash with a stack overflow.

When you only need a straight pass (like counting down), rewrite the recursion as a `for` or `while` loop. An iterative loop drops extra space to **$O(1)$**.
</Trap>

## How to answer in the interview

<InterviewAnswer level="fresh">
"Big-O notation describes how an algorithm grows in time and memory as the input size $n$ grows. For example, reading an array item by index is $O(1)$ constant time. It takes one step no matter how big the array is. Searching with a loop is $O(n)$ linear time because we may check every item."
</InterviewAnswer>

<InterviewAnswer level="junior">
"Big-O measures how time and space grow as input grows. In Swift, collection costs matter a lot. For example, `string.count` is $O(n)$ because Swift counts extended grapheme clusters, while `string.isEmpty` checks `startIndex == endIndex` in $O(1)$. Also, `array.append` is amortized $O(1)$, while `array.insert(at: 0)` is $O(n)$ because items shift. When searching often, I use a `Set` so lookups drop from $O(n)$ to $O(1)$."
</InterviewAnswer>

<InterviewAnswer level="senior">
"Big-O guides choices around app speed and memory limits on mobile devices. Beyond Big-O growth, CPU cache speed matters too. Swift arrays store items side by side in memory, which makes sequential reads fast. In hot paths, we also watch memory allocations. We use `reserveCapacity` on collections to avoid repeated resizing, and prefer loops over deep recursion to keep call stack space at $O(1)$."
</InterviewAnswer>

## Recap

<Recap>
- **Big-O notation** measures how time or memory usage grows as input size $n$ grows.
- **$O(1)$** is constant time, **$O(\log n)$** is logarithmic, **$O(n)$** is linear, and **$O(n^2)$** is quadratic.
- **Space complexity** counts extra heap memory and call stack frames pushed during recursion.
- In Swift, **`string.isEmpty`** checks `startIndex == endIndex` in $O(1)$, while **`string.count`** takes $O(n)$.
- **`array[index]`** is $O(1)$, **`array.append`** is amortized $O(1)$, and **`array.insert(at: 0)`** is $O(n)$.
- Use a **`Set`** for $O(1)$ average lookups instead of `array.contains` inside a loop.
</Recap>
