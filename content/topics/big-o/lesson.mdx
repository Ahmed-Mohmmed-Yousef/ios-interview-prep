## The simple idea

<Analogy>
Imagine looking for a person in a long line at a movie theater.

If you know their ticket number, you can walk straight to their seat in one step. This is constant time: O(1).

If you must check every face one by one, your search time grows with the line. Checking 10 people takes 10 steps. Checking 1,000 people takes 1,000 steps. This is linear time: O(n).

Big-O notation gives us a shared language to describe how time and memory grow as the input gets larger.
</Analogy>

In computer science, **Big-O notation** measures how an algorithm scales as the input size $n$ increases toward infinity.

We use Big-O to analyze two things:
- **Time complexity**: How the number of operations grows as input size grows.
- **Space complexity**: How much extra memory (auxiliary space) the algorithm allocates as input size grows.

Big-O focuses on the worst-case scenario. We ignore constant multipliers and smaller terms. For example, $O(2n + 5)$ simplifies to $O(n)$.

Here are the six most common time complexities, from fastest to slowest:
1. **$O(1)$ — Constant time**: The work stays the same no matter how large $n$ becomes. Reading an array element with `array[0]` takes $O(1)$ time.
2. **$O(\log n)$ — Logarithmic time**: The work cuts the remaining problem in half at every step. Binary search on a sorted list takes $O(\log n)$ time.
3. **$O(n)$ — Linear time**: The work scales in direct proportion to $n$. A single loop over an array takes $O(n)$ time.
4. **$O(n \log n)$ — Linearithmic time**: Common in efficient sorting algorithms like Swift's `array.sorted()`.
5. **$O(n^2)$ — Quadratic time**: The work multiplies with nested loops over the data. Checking every pair in an array takes $O(n^2)$ time.
6. **$O(2^n)$ — Exponential time**: The work doubles with each added item. Naive recursive Fibonacci calculations take $O(2^n)$ time.

## In code

<CodeExample title="Comparing O(1), O(n), and O(n^2) time complexity in Swift">

```swift
let numbers = [10, 20, 30, 40, 50]

// 1. O(1) Constant Time
let firstNumber = numbers[0]
print("First item: \(firstNumber)")

// 2. O(n) Linear Time
func linearSearch(in array: [Int], target: Int) -> Bool {
    for item in array {
        if item == target {
            return true
        }
    }
    return false
}
print("Found 30: \(linearSearch(in: numbers, target: 30))")

// 3. O(n^2) Quadratic Time
func countDuplicatePairs(in array: [Int]) -> Int {
    var count = 0
    for i in 0..<array.count {
        for j in (i + 1)..<array.count {
            if array[i] == array[j] {
                count += 1
            }
        }
    }
    return count
}
let duplicates = [1, 2, 2, 3, 3]
print("Duplicate pairs: \(countDuplicatePairs(in: duplicates))")
```

```output
First item: 10
Found 30: true
Duplicate pairs: 2
```

</CodeExample>

This example contrasts the three most common time curves in daily Swift programming:
- **`numbers[0]`**: Swift arrays support random access. Reading any element by index takes $O(1)$ constant time.
- **`linearSearch`**: In the worst case, the loop checks all $n$ items. The time complexity is $O(n)$.
- **`countDuplicatePairs`**: The outer loop runs $n$ times and the inner loop runs up to $n$ times. The time complexity is $O(n^2)$.

<CodeExample title="Measuring space complexity and recursive call stack memory">

```swift
// 1. O(1) Auxiliary Space: Uses a fixed set of scalar variables
func calculateSum(of array: [Int]) -> Int {
    var total = 0
    for number in array {
        total += number
    }
    return total
}

let items = [1, 2, 3, 4]
print("Sum: \(calculateSum(of: items))")

// 2. O(n) Auxiliary Space: Allocates a new array with n elements
func squareAll(numbers: [Int]) -> [Int] {
    var result: [Int] = []
    result.reserveCapacity(numbers.count)
    for number in numbers {
        result.append(number * number)
    }
    return result
}
print("Squared: \(squareAll(numbers: items))")

// 3. O(n) Call Stack Space: Recursion creates a stack frame per level
func countdown(from n: Int) {
    if n <= 0 {
        print("Blast off!")
        return
    }
    countdown(from: n - 1)
}
countdown(from: 3)
```

```output
Sum: 10
Squared: [1, 4, 9, 16]
Blast off!
```

</CodeExample>

Space complexity measures the extra memory an algorithm allocates during execution:
- **`calculateSum`**: Allocates only one integer variable `total`. Its auxiliary space complexity is $O(1)$.
- **`squareAll`**: Allocates a new array storing $n$ integers. Its auxiliary space complexity is $O(n)$.
- **`countdown`**: Each recursive call adds a stack frame to the system call stack. A depth of $n$ recursive calls uses $O(n)$ stack space.

## Interview traps

<Trap title="Assuming string.count is O(1)">
In many languages, string length is stored as an integer and checked in $O(1)$ time. In Swift, characters are **extended grapheme clusters** that can combine multiple Unicode code points.

Swift must inspect Unicode scalar boundaries across the string to count characters. As a result, `string.count` takes **$O(n)$** linear time.

Do not write `string.count == 0` to test for an empty string. Always use **`string.isEmpty`**, which runs in guaranteed $O(1)$ constant time.
</Trap>

<Trap title="Calling contains inside an array loop">
Checking whether an array contains an item with `array.contains(x)` takes $O(n)$ linear time.

If you call `array.contains` inside a loop that also runs $n$ times, your total runtime becomes **$O(n^2)$**.

To fix this, convert the array into a **`Set`** before the loop. Building the set takes $O(n)$ time once, and set lookups take $O(1)$ average time. This reduces the total time to **$O(n)$**.
</Trap>

<Trap title="Inserting elements at index 0 of an array">
`array.append(element)` adds an item to the end of an array in amortized $O(1)$ time.

However, calling `array.insert(element, at: 0)` forces Swift to shift all existing $n$ items one position to the right in memory. This turns your insert into an **$O(n)$** operation.
</Trap>

<Trap title="Forgetting call stack space in recursion">
Even when a recursive function creates no local arrays, each function call takes memory on the call stack.

If an algorithm recurses $n$ levels deep, its space complexity is **$O(n)$**, not $O(1)$. If $n$ is very large, this can cause a stack overflow crash.
</Trap>

## How to answer in the interview

<InterviewAnswer level="fresh">
"Big-O notation describes how an algorithm scales in time and memory as the input size $n$ grows. For example, reading an array element by index is $O(1)$ constant time. It takes the same step regardless of array size. Searching for an element with a loop is $O(n)$ linear time because we may need to inspect every item."
</InterviewAnswer>

<InterviewAnswer level="junior">
"Big-O measures the upper bound of time and space growth. In Swift, understanding collection costs is critical. For example, `string.count` is $O(n)$ because Swift counts extended grapheme clusters, whereas `string.isEmpty` is $O(1)$. Similarly, `array.append` is amortized $O(1)$, while `array.insert(at: 0)` is $O(n)$ because all elements shift. When searching repeatedly, I convert arrays to sets to change lookup time from $O(n)$ to $O(1)$."
</InterviewAnswer>

<InterviewAnswer level="senior">
"Big-O guides architectural decisions around latency and memory footprint on mobile devices. Beyond asymptotic complexity, cache locality matters. Swift arrays store elements contiguously in memory, giving them superior cache line performance over pointer-based structures. In performance-critical paths, we also consider memory allocations. We use `reserveCapacity` on collections to prevent repeated reallocations, and favor iterative algorithms over deep recursion to protect the call stack."
</InterviewAnswer>

## Recap

<Recap>
- **Big-O notation** measures how an algorithm's time or memory usage scales as input size $n$ grows.
- **$O(1)$** is constant time, **$O(\log n)$** is logarithmic, **$O(n)$** is linear, and **$O(n^2)$** is quadratic.
- **Space complexity** includes auxiliary memory allocated on the heap and stack frames pushed to the call stack during recursion.
- In Swift, **`string.isEmpty`** is $O(1)$, while **`string.count`** is $O(n)$ due to Unicode grapheme clusters.
- **`array[index]`** is $O(1)$, **`array.append`** is amortized $O(1)$, and **`array.insert(at: 0)`** is $O(n)$.
- Use a **`Set`** for $O(1)$ average lookups instead of calling `array.contains` inside a loop.
</Recap>
