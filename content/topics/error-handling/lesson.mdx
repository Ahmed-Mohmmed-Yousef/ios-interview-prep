## The simple idea

<Analogy>
Think of ordering food at a restaurant counter. If an item is sold out, the cashier tells you immediately and gives you a clear reason. You can choose a backup item, cancel your order, or check another restaurant. Swift error handling works the same way by returning clean, expected error information instead of crashing the program.
</Analogy>

In Swift, **error handling** is the process of responding to and recovering from error conditions in your program.

Errors are represented by values of any type that conforms to the **`Error`** protocol. Enums are especially popular because their cases can model distinct failure states with associated values.

Swift provides four main ways to handle errors:
1. **Propagate errors**: Mark a function with the **`throws`** keyword to pass errors up to the caller.
2. **Handle errors with `do-catch`**: Use a `do` block with one or more `catch` clauses to respond to specific errors.
3. **Convert errors to Optionals with `try?`**: If an error is thrown, the expression evaluates to `nil`.
4. **Assert success with `try!`**: Disables error handling. If an error is thrown, the app crashes immediately.

Swift also provides two related features:
- **`defer`**: Defers execution of cleanup code until the current scope exits, running even if an error is thrown.
- **`Result`**: A built-in enum that represents either `.success` or `.failure`.

## In code

<CodeExample title="Throwing errors and handling them with do-catch and try?">

```swift
enum PrinterError: Error {
    case outOfPaper
    case noToner
    case paperJam(page: Int)
}

func printDocument(pages: Int) throws -> String {
    if pages <= 0 {
        throw PrinterError.outOfPaper
    }
    return "Printed \(pages) pages successfully."
}

// 1. Handling with do-catch
do {
    let status = try printDocument(pages: 0)
    print(status)
} catch PrinterError.outOfPaper {
    print("Handled: Printer is out of paper.")
} catch {
    // Swift provides an implicit 'error' constant
    print("Unexpected error: \(error)")
}

// 2. Converting to an Optional with try?
let successfulPrint = try? printDocument(pages: 5)
let failedPrint = try? printDocument(pages: 0)

print("Success: \(successfulPrint ?? "nil")")
print("Failed print is nil: \(failedPrint == nil)")
```

```output
Handled: Printer is out of paper.
Success: Printed 5 pages successfully.
Failed print is nil: true
```

</CodeExample>

This example shows the primary error handling workflows:
- **`throws` keyword**: Indicates that `printDocument(pages:)` can throw an error.
- **`try` keyword**: Required whenever calling a function marked with `throws`.
- **`do-catch` statement**: Catches specific errors by pattern matching on enum cases.
- **Implicit `error`**: A general `catch` clause automatically provides a constant named `error`.
- **`try?`**: Evaluates to `nil` when an error is thrown, avoiding a full `do-catch` block.

<CodeExample title="Using defer for cleanup and managing Result types">

```swift
enum FileError: Error {
    case readFailure
}

func processFile() -> String {
    print("1. Opening file resource.")
    
    defer {
        print("4. Executing first defer (runs second).")
    }
    defer {
        print("3. Executing second defer (runs first).")
    }
    
    print("2. Reading file contents.")
    return "File processed."
}

_ = processFile()

// Using the Result type
let result: Result<Int, FileError> = .success(100)
switch result {
case .success(let count):
    print("Result succeeded with \(count) items.")
case .failure(let err):
    print("Result failed with error: \(err)")
}
```

```output
1. Opening file resource.
2. Reading file contents.
3. Executing second defer (runs first).
4. Executing first defer (runs second).
Result succeeded with 100 items.
```

</CodeExample>

This example highlights two important patterns:
- **`defer` reverse order**: Multiple `defer` statements run in reverse order (bottom-up), guaranteeing proper teardown of nested resources.
- **`Result` enum**: Holds either `.success` with a value or `.failure` with an error, which is useful when storing results for later inspection.

## Interview traps

<Trap title="Assuming Swift unwinds the call stack like Java or C++ exceptions">
In languages like Java or C++, exception handling unwinds the call stack, which is computationally expensive. In Swift, error handling does not unwind the stack. Errors are returned as values using dedicated registers, matching the speed of a standard return statement.
</Trap>

<Trap title="Using try! in production app code">
`try!` disables error propagation and asserts that no error will occur. If the function throws an error, the application crashes immediately. Reserve `try!` for unit tests or situations where an error is mathematically impossible.
</Trap>

<Trap title="Forgetting that multiple defer statements execute in reverse order">
When closing nested resources, candidates often assume `defer` statements run from top to bottom. They actually execute in reverse order. The last `defer` written runs first.
</Trap>

Functions that throw mark their signature with throws, and callers use try inside do-catch blocks. You can also use try? to convert errors into Optionals, or use defer to guarantee cleanup code runs when leaving scope.
</InterviewAnswer>

<InterviewAnswer level="junior">

Callers handle errors with pattern-matching do-catch blocks, optional conversion via try?, or runtime assertions via try!. For asynchronous workflows or completion storage, Swift provides the Result enum with success and failure cases. Cleanup is handled with defer blocks, which execute in reverse order upon scope exit.
</InterviewAnswer>

## Recap

<Recap>
- Errors conform to the `Error` protocol, typically modeled with enums.
- Throwing functions use the `throws` keyword before their return arrow.
- Callers must precede throwing calls with `try`, `try?`, or `try!`.
- `do-catch` blocks catch specific errors; general catch blocks provide an implicit `error` constant.
- `try?` converts errors into `nil`; `try!` crashes if an error is thrown.
- `defer` executes cleanup code upon scope exit, running in reverse order.
- The `Result` type stores either `.success(Value)` or `.failure(Error)`.
</Recap>
