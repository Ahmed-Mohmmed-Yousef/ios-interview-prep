## The simple idea

<Analogy>
Think of ordering food at a counter. If an item is sold out, the worker tells you right away and gives a clear reason. You can pick another item or cancel your order. Swift error handling works the same way by returning clear failure information instead of crashing your app.
</Analogy>

In Swift, **error handling** lets your code notice when an action fails and recover cleanly.

An error can be any type that conforms to the **`Error`** protocol. Enumerations are a popular choice because each case can name a failure and hold extra details as associated values.

Swift gives you four main ways to handle errors:
1. **Pass errors on**: Mark a function with **`throws`** to send errors back to the caller. Most functions use plain `throws`, which can throw any `Error` type. In Swift 6, you can also use **typed throws** like `throws(FileError)` to name one exact error type.
2. **Catch errors with `do-catch`**: Put throwing calls inside a `do` block and match errors in `catch` clauses.
3. **Turn errors into `nil` with `try?`**: If the call throws an error, the result becomes `nil` as an optional.
4. **Disable error propagation with `try!`**: Tells Swift you are sure the call will not throw. If it throws anyway, the app crashes at runtime.

Swift also offers two helpful tools:
- **`defer`**: Runs cleanup code right before leaving the current scope, even if an error is thrown.
- **`Result`**: A standard enum with `.success` and `.failure` cases. It stores an outcome for later or passes it to a completion handler, and **`get()`** turns it back into a throwing call.

## In code

<CodeExample title="Throwing errors and catching them with do-catch and try?">

```swift
enum PrinterError: Error {
    case outOfPaper
    case noToner
    case paperJam(page: Int)
}

func printDocument(pages: Int) throws -> String {
    if pages <= 0 {
        throw PrinterError.outOfPaper
    }
    if pages > 100 {
        throw PrinterError.paperJam(page: 101)
    }
    return "Printed \(pages) pages."
}

// 1. Handling with do-catch
do {
    let status = try printDocument(pages: 120)
    print(status)
} catch PrinterError.outOfPaper {
    print("Handled: Out of paper.")
} catch PrinterError.paperJam(let page) {
    print("Handled: Paper jam on page \(page).")
} catch {
    // Swift provides an implicit 'error' constant
    print("Unexpected error: \(error)")
}

// 2. Converting to an optional with try?
let goodPrint = try? printDocument(pages: 5)
let badPrint = try? printDocument(pages: 0)

print("Success: \(goodPrint ?? "nil")")
print("Failed print is nil: \(badPrint == nil)")
```

```output
Handled: Paper jam on page 101.
Success: Printed 5 pages.
Failed print is nil: true
```

</CodeExample>

This example shows the main error-handling steps:
- **`throws`**: Shows that `printDocument(pages:)` can throw an error.
- **`try`**: Required before any call to a throwing function.
- **`do-catch`**: Matches specific error cases and can bind associated values like `let page`.
- **Implicit `error`**: A plain `catch` clause gives you a constant named `error`.
- **`try?`**: Turns a thrown error into `nil` so you do not need a `do-catch` block.

<CodeExample title="Typed throws in Swift 6">

```swift
enum FileError: Error {
    case notFound
    case unreadable
}

func openFile(_ name: String) throws(FileError) -> String {
    if name.isEmpty {
        throw .notFound
    }
    return "Data"
}

do {
    let data = try openFile("")
    print(data)
} catch .notFound {
    print("File not found")
} catch .unreadable {
    print("File unreadable")
}
```

```output
File not found
```

</CodeExample>

With **typed throws**, the compiler knows every error comes from `FileError`, so `do-catch` can cover every case without a fallback `catch`. The Swift book notes that most code should still use plain `throws`, because it lets functions change or wrap errors later without breaking callers.

<CodeExample title="Using defer for cleanup and Result with get()">

```swift
enum LoadError: Error {
    case readFailure
}

func processFile() -> String {
    print("1. Opening file.")

    defer {
        print("4. First defer (runs second).")
    }
    defer {
        print("3. Second defer (runs first).")
    }

    print("2. Reading file.")
    return "Done"
}

_ = processFile()

let result: Result<Int, LoadError> = .success(100)
switch result {
case .success(let count):
    print("Result succeeded with \(count) items.")
case .failure(let err):
    print("Result failed: \(err)")
}

if let count = try? result.get() {
    print("Value via get(): \(count)")
}
```

```output
1. Opening file.
2. Reading file.
3. Second defer (runs first).
4. First defer (runs second).
Result succeeded with 100 items.
Value via get(): 100
```

</CodeExample>

This example highlights two patterns:
- **`defer` reverse order**: Multiple `defer` blocks run in reverse order when leaving the scope, even if an error is thrown.
- **`Result` and `get()`**: `Result` holds `.success` or `.failure` as a value. Calling `try result.get()` returns the success value or throws the failure error.

## Interview traps

<Trap title="Assuming Swift unwinds the call stack like Java or C++">
In Java or C++, throwing an exception unwinds the call stack, which is slow. Swift does not unwind the stack. Throwing an error has a cost close to returning a normal value, and `try` marks every throwing call clearly in your code.
</Trap>

<Trap title="Using try! without being sure it cannot fail">
`try!` disables error propagation and crashes your app at runtime if an error is thrown. Use `try!` only when you know the call will not fail, such as loading a file shipped inside your app bundle. Also remember that `defer` blocks do not run if `try!` crashes.
</Trap>

<Trap title="Forgetting that multiple defer blocks run in reverse order">
When closing resources, developers often assume `defer` blocks run from top to bottom. They run in reverse order instead. The last `defer` written runs first.
</Trap>

## How to answer in the interview

<InterviewAnswer level="fresh">
In Swift, errors conform to the `Error` protocol and are often enums with associated values. Functions that throw use `throws`, and callers mark calls with `try` inside a `do-catch` block. You can also use `try?` to turn errors into `nil`, or `defer` to run cleanup code when leaving a scope.
</InterviewAnswer>

<InterviewAnswer level="junior">
Swift checks throwing calls at compile time instead of unwinding the call stack, so throwing costs about the same as returning a value. Callers handle errors with `do-catch` pattern matching, `try?` for optional values, or `try!` when failure is impossible. Modern async APIs use `async throws`, while `Result` is useful for storing outcomes or passing them to completion handlers and bridging back with `get()`. In Swift 6, typed throws like `throws(FileError)` exist too, though plain `throws` fits most code. Cleanup code goes in `defer` blocks, which run in reverse order before the scope exits.
</InterviewAnswer>

## Recap

<Recap>
- Errors conform to `Error` (often enums with associated values), and functions mark failures with `throws` or typed `throws(MyError)`.
- Callers mark throwing calls with `try` (inside `do-catch`), `try?` (returns `nil` on error), or `try!` (crashes on error).
- `do-catch` matches specific cases, binds associated values, and provides an implicit `error` constant in a plain `catch`.
- `defer` runs cleanup when leaving a scope in reverse order, even on throw, though not on a `try!` crash.
- `Result` stores `.success` or `.failure` as a value and provides `get()` to return the value or throw the error.
</Recap>
