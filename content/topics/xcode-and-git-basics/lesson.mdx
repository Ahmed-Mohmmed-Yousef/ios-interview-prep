## The simple idea

Building an iOS app takes more than writing Swift code. You need tools to organize files, set build rules, and track changes over time.

Xcode gives you four core building blocks:
1. **The Project (`.xcodeproj`) and Workspace (`.xcworkspace`)**:
   - An Xcode project holds your code files, assets, and settings. Inside it, `project.pbxproj` tracks file references, build phases, and target settings.
   - An Xcode workspace (`.xcworkspace`) groups multiple projects and Swift packages together so they can share dependencies cleanly.
2. **The Target and Bundle Identifier**:
   - A target defines one product to build, such as an iOS app, a Widget Extension, or a Unit Test bundle.
   - It lists which Swift files compile into that product.
   - Each target has a **Bundle Identifier**, a unique reverse-DNS string like `com.company.appname`. iOS and App Store Connect use it for app identity, sandboxing, and capabilities.
3. **The Scheme and Build Configurations (`Debug` vs `Release`)**:
   - A scheme defines how actions like Build, Run, Test, and Archive work, and links each action to a build configuration.
   - **Debug** compiles with `-Onone` (no optimization) for fast builds, keeps LLDB debug symbols, and turns on `#if DEBUG`.
   - **Release** (the default for Archive) compiles with `-O` for speed, strips unused symbols, and disables `assert` checks.

<Analogy>
Think of building a car.

The project is the car factory.

A target is one product line, such as the family sedan or the racing edition.

A scheme is the daily build plan, telling the team whether to build for a test drive (`Debug`) or showroom delivery (`Release`).
</Analogy>

Version control with **Git** tracks every change you make:
- `git status`: Shows the current branch, staged files, and working edits.
- `git add`: Stages new or changed files for the next commit.
- `git commit`: Saves a snapshot with a clear message.
- `git switch -c <branch>` (or `git checkout -b <branch>`): Creates and switches to a new branch (`git branch <branch>` creates a branch without switching).
- `git merge <feature-branch>`: Combines commits from a feature branch into your active branch (such as `main`).
- `.gitignore`: Lists untracked files and folders (like `DerivedData` and `xcuserdata`) that Git should skip.

## In code

You can model app target properties and build configurations directly in Swift code.

<CodeExample title="Inspecting build configuration and target settings">

```swift
import Foundation

struct AppTarget {
    let name: String
    let bundleIdentifier: String
    let isTestBundle: Bool
}

let target = AppTarget(
    name: "WeatherApp",
    bundleIdentifier: "com.example.weather",
    isTestBundle: false
)

#if DEBUG
let buildMode = "Debug"
#else
let buildMode = "Release"
#endif

print("Target: \(target.name), Mode: \(buildMode)")
```

```output
Target: WeatherApp, Mode: Release
```

</CodeExample>

In Git, each commit records a focused unit of work with a hash and a message.

<CodeExample title="Modeling a Git commit history snapshot">

```swift
import Foundation

struct GitCommit {
    let hash: String
    let message: String
    let branch: String
}

let commit = GitCommit(
    hash: "7f8b9c2",
    message: "feat: add user profile screen",
    branch: "main"
)

print("Commit [\(commit.hash)] on \(commit.branch): \(commit.message)")
```

```output
Commit [7f8b9c2] on main: feat: add user profile screen
```

</CodeExample>

## Interview traps

<Trap title="Confusing Targets with Schemes">
A target defines *what* gets built (the app, extension, or test bundle). A scheme defines *how* to build and run that target (such as running tests in `Debug` or archiving in `Release`).
</Trap>

<Trap title="Forgetting Target Membership">
Xcode only compiles Swift files included in the target's **Compile Sources** build phase. If a file is missing Target Membership, the compiler cannot read it and throws "Cannot find type in scope" errors. Select the file and check **Target Membership** in the **File Inspector** panel.
</Trap>

<Trap title="Committing DerivedData or xcuserdata to Git">
`DerivedData` stores temporary build files, module caches, and code indexes. `xcuserdata` stores personal Xcode state like open tabs, window layouts, and breakpoints. Checking them into Git causes constant merge conflicts and clutters team history, so always list them in `.gitignore`.
</Trap>

<Trap title="Ignoring project.pbxproj merge conflicts">
The `project.pbxproj` file uses internal UUIDs to track files and build phases. When two branches add new files at the same time, fix merge conflicts carefully so you do not break the project file.
</Trap>

</InterviewAnswer>

<InterviewAnswer level="senior">

</InterviewAnswer>

## Recap

<Recap>
- An Xcode `.xcodeproj` holds code, assets, and settings (`project.pbxproj`); an `.xcworkspace` groups projects and packages.
- A target defines one build product and has its own reverse-DNS Bundle Identifier.
- A scheme defines how Build, Run, Test, and Archive run, using `Debug` (`-Onone`) or `Release` (`-O`).
- Git tracks work with `status`, `add`, `commit`, `switch -c`, and `merge`.
- Always exclude `DerivedData` and `xcuserdata` in `.gitignore`.
</Recap>
