## The simple idea

<Analogy>
Imagine a busy restaurant kitchen with one front counter cashier.

The cashier takes customer orders and hands them food.

If the cashier leaves the counter to chop vegetables in the back room for ten minutes, the line stops.

Customers cannot order, and the restaurant freezes.

A helper in the back should chop the vegetables, so the cashier never leaves the front counter.
</Analogy>

In iOS, the **main thread** is the front counter of your app.

It is created when your application launches and runs the main run loop.

1. **What runs on the main thread**:
   - Screen drawing, layout passes, and animations.
   - User touch events, button taps, and gestures.
   - UIKit view modifications and SwiftUI state updates.
2. **Why UI work must run on the main thread**:
   - UI frameworks like UIKit are not thread-safe.
   - Adding locks to every button and label would slow down rendering and waste battery.
   - The screen refreshes 60 or 120 times every second. All layout must synchronize on that clock.
3. **Keep the main thread free**:
   - Heavy work like file storage, network requests, and image filters belongs on background threads.
   - Dispatch the final result back to the main thread before updating any label or screen view.

## In code

<CodeExample title="Enforcing main thread execution using @MainActor in Swift">

```swift
import Foundation

@MainActor
class ProfileViewModel {
    var username: String = "Guest"
    
    func updateUsername(to newName: String) {
        username = newName
        print("Updated on main thread: \(Thread.isMainThread)")
    }
}

let vm = ProfileViewModel()
vm.updateUsername(to: "Taylor")
print("Current user: \(vm.username)")
```

```output
Updated on main thread: true
Current user: Taylor
```

</CodeExample>

In this example, `@MainActor` guarantees that `ProfileViewModel` runs exclusively on the main thread.

Swift verifies this at compile time, eliminating data races on user interface state.

`Thread.isMainThread` confirms that the property update happened on the main thread.

<CodeExample title="Asserting main thread safety before updating UI state">

```swift
import Foundation

struct UserDisplayState {
    var title: String
    var isLoading: Bool
}

@MainActor
class ScreenPresenter {
    var state = UserDisplayState(title: "Welcome", isLoading: false)
    
    func apply(title: String) {
        assert(Thread.isMainThread, "UI mutations must run on the main thread!")
        state.title = title
        state.isLoading = false
        print("UI State: title = \(state.title), main = \(Thread.isMainThread)")
    }
}

let presenter = ScreenPresenter()
presenter.apply(title: "Dashboard")
```

```output
UI State: title = Dashboard, main = true
```

</CodeExample>

In this second example, `apply(title:)` guards UI state updates.

The assertion verifies that the function runs on the main thread.

Using `@MainActor` ensures that all state mutations happen safely before the next screen redraw.

## Interview traps

<Trap title="Calling DispatchQueue.main.sync from the main thread">
Calling `DispatchQueue.main.sync` from the main thread creates an instant deadlock.

The main thread waits for the block to complete before continuing.

However, the block cannot start because the main thread is blocked waiting for it. The app freezes permanently.
</Trap>

<Trap title="Updating UI from background network callbacks">
URLSession data tasks return their results on background threads.

Assigning those results directly to labels, image views, or published properties causes background UI mutation warnings.

Always dispatch back to the main thread using `@MainActor` or `DispatchQueue.main.async`.
</Trap>

<Trap title="Assuming the watchdog only runs during app launch">
The iOS watchdog monitors your app during its entire lifecycle, not just at launch.

If the main thread is blocked for more than roughly 10 seconds during normal use, the operating system kills your process.

The crash report will display the exception code `0x8badf00d`.
</Trap>

<Trap title="Parsing large JSON files on the main thread">
Decoding large JSON payloads or database queries can take tens or hundreds of milliseconds.

Doing this work on the main thread drops frames and creates visible user interface hitches.

Decode your models on background tasks and pass only the finished state to the main thread.
</Trap>

## How to answer in the interview

<InterviewAnswer level="fresh">
"The main thread handles all user interaction and screen rendering in iOS. If we do heavy work on the main thread, the app freezes. UI frameworks like UIKit are not thread-safe, so all UI updates must happen on the main thread. We run long tasks in the background and send results to the main thread."
</InterviewAnswer>

<InterviewAnswer level="junior">
"UIKit is not thread-safe to avoid the performance cost of internal locks. Screen rendering must synchronize with display refreshes at 60 or 120 hertz. If we block the main thread for too long, the iOS watchdog kills the app with exception 0x8badf00d. In modern Swift, I use @MainActor to guarantee main thread isolation for view models and UI code."
</InterviewAnswer>

<InterviewAnswer level="senior">
"On iOS, every display frame has a strict render budget: 16.6 milliseconds at 60Hz or 8.3 milliseconds on ProMotion displays. During that window, the main thread must handle events, run layout passes, and commit Core Animation transactions to the render server. Blocking the main thread causes dropped frames known as hitches. In Xcode, I catch background UI violations using the Main Thread Checker and diagnose hitches using the Instruments Animation Hitches template."
</InterviewAnswer>

## Recap

<Recap>
- The main thread processes touch events, animations, and view drawing.
- UI frameworks are not thread-safe; all UI updates must run on the main thread.
- Heavy work like networking, image filtering, and file I/O must run on background threads.
- Calling `DispatchQueue.main.sync` from the main thread causes an immediate deadlock.
- The iOS watchdog terminates apps that block the main thread for too long with code `0x8badf00d`.
- In modern Swift, annotate UI classes and methods with `@MainActor` for compile-time safety.
</Recap>
