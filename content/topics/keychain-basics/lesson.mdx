## The simple idea

<Analogy>
Imagine a bank lobby with a guest sign-in book and a vault with safe deposit boxes.

The sign-in book sits in open view on the front counter.

Anyone walking past can read names, visit times, or visitor notes.

You would never write your bank vault pin or private safe combination in the open sign-in book.

Instead, the bank keeps high-value treasures inside a locked steel vault behind a thick metal door.

Only a customer with the right key and authorized identification can open a deposit box.
</Analogy>

In iOS apps, `UserDefaults` is your open sign-in book.

It stores lightweight user preferences in an unencrypted property list file on disk.

Anyone who inspects an unencrypted device backup can read data in `UserDefaults`.

The **Keychain** is the locked metal vault.

The Keychain is a specialized encrypted database managed by the iOS system daemon named `securityd`.

It protects sensitive secrets like passwords, OAuth access tokens, and private keys.

Hardware encryption keys derived from the Secure Enclave and user passcode protect every item.

Keychain items also follow different lifecycle rules than regular files:

- Regular sandbox files disappear when a user deletes the app.
- Keychain items persist on the physical device even after the user deletes the app.
- If the user reinstalls the app later, previously stored Keychain items remain accessible.
- Related apps from the same development team can share Keychain items using Access Groups.

## In code

Use dictionary queries with keys from the `Security` framework to save and search Keychain items.

Specify `kSecClassGenericPassword` for application tokens and passwords.

<CodeExample title="Constructing Keychain query dictionaries">

```swift
import Foundation
import Security

struct KeychainQueryBuilder {
    static func makeSaveQuery(service: String, account: String, secret: String) -> [String: Any] {
        let secretData = Data(secret.utf8)
        return [
            kSecClass as String: kSecClassGenericPassword,
            kSecAttrService as String: service,
            kSecAttrAccount as String: account,
            kSecValueData as String: secretData,
            kSecAttrAccessible as String: kSecAttrAccessibleWhenUnlocked
        ]
    }

    static func makeReadQuery(service: String, account: String) -> [String: Any] {
        return [
            kSecClass as String: kSecClassGenericPassword,
            kSecAttrService as String: service,
            kSecAttrAccount as String: account,
            kSecReturnData as String: true,
            kSecMatchLimit as String: kSecMatchLimitOne
        ]
    }
}

let saveQuery = KeychainQueryBuilder.makeSaveQuery(
    service: "com.prepstops.auth",
    account: "authToken",
    secret: "top_secret_jwt_token"
)

let readQuery = KeychainQueryBuilder.makeReadQuery(
    service: "com.prepstops.auth",
    account: "authToken"
)

print("Save class: \(saveQuery[kSecClass as String] != nil)")
print("Save service: \(saveQuery[kSecAttrService as String] ?? "")")
print("Read limit one: \(readQuery[kSecMatchLimit as String] != nil)")
```

```output
Save class: true
Save service: com.prepstops.auth
Read limit one: true
```

</CodeExample>

Security framework functions return an `OSStatus` code.

Always inspect the return status to handle duplicates and missing entries.

<CodeExample title="Interpreting Keychain status codes">

```swift
import Foundation
import Security

func statusDescription(_ status: OSStatus) -> String {
    switch status {
    case errSecSuccess:
        return "Success"
    case errSecDuplicateItem:
        return "Duplicate item error"
    case errSecItemNotFound:
        return "Item not found error"
    default:
        return "Other status: \(status)"
    }
}

print(statusDescription(errSecSuccess))
print(statusDescription(errSecDuplicateItem))
print(statusDescription(errSecItemNotFound))
```

```output
Success
Duplicate item error
Item not found error
```

</CodeExample>

## Interview traps

<Trap title="Storing tokens in UserDefaults">
UserDefaults stores unencrypted property lists on disk. Anyone with physical access to an unencrypted device backup can read tokens. Always use Keychain for secrets.
</Trap>

<Trap title="Assuming Keychain items delete with the app">
Sandbox files disappear on app deletion, but Keychain items persist on the device. Check a first-launch flag in UserDefaults to clear stale tokens after a reinstall.
</Trap>

<Trap title="Crashing on duplicate items">
Calling `SecItemAdd` on an existing item returns `errSecDuplicateItem`. Use `SecItemUpdate` or delete the existing item before adding a new secret.
</Trap>

<Trap title="Storing large files in Keychain">
Keychain is designed for small secrets under a few kilobytes like tokens and passwords. For large files, use filesystem storage with `FileProtectionType.complete`.
</Trap>

## How to answer in the interview

<InterviewAnswer level="fresh">
"The Keychain is an encrypted storage system managed by iOS. We use it to store sensitive data like passwords and authentication tokens. Unlike `UserDefaults`, which is plaintext, Keychain is hardware-encrypted. Another big difference is that Keychain data stays on the device even if the user deletes and reinstalls the app."
</InterviewAnswer>

<InterviewAnswer level="junior">
"Keychain Services in the `Security` framework provides hardware-backed storage for credentials using `kSecClassGenericPassword`. We query and save items using `SecItemAdd`, `SecItemCopyMatching`, and `SecItemDelete`. We control when data can be decrypted using accessibility attributes like `kSecAttrAccessibleWhenUnlocked` or `kSecAttrAccessibleAfterFirstUnlock` for background tasks. We also use Keychain Access Groups to share tokens between an app and its widget extension."
</InterviewAnswer>

<InterviewAnswer level="senior">
"Architecturally, we wrap procedural C Security APIs behind a clean Swift actor or service protocol. We enforce strict accessibility policies using `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` to prevent silent iCloud Keychain syncing of sensitive enterprise tokens. Where biometric protection is mandated, we configure `SecAccessControl` with `.biometryAny` or `.userPresence` to require Face ID before key derivation. For large assets, we generate symmetric keys stored in Keychain to encrypt local SQLite or Realm databases."
</InterviewAnswer>

## Recap

<Recap>
- Use `UserDefaults` for light user preferences and `Keychain` for sensitive credentials.
- The `securityd` system daemon manages the Keychain with hardware-level encryption.
- Keychain items persist across app uninstalls on the same physical hardware.
- Use `kSecAttrAccessibleAfterFirstUnlock` when background tasks need access to secrets.
- Check return codes like `errSecSuccess`, `errSecDuplicateItem`, and `errSecItemNotFound`.
- Share credentials between main apps and app extensions through Keychain Access Groups.
</Recap>
