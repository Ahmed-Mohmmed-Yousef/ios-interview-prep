## The simple idea

<Analogy>
Imagine a watchmaker assembling an expensive mechanical wristwatch.

The watch contains tiny gears, springs, and levers.
If the watchmaker builds the entire watch and closes the steel casing, finding a broken gear is frustrating.
The watchmaker would have to take the entire watch apart to locate the flaw.

Instead, the watchmaker tests each individual brass gear on a testing rig before assembly.
The watchmaker checks teeth dimensions and spins each gear independently.
If a gear wobbles, the watchmaker fixes it immediately.
Testing individual parts before assembling the full machine is the exact purpose of **unit testing**.
</Analogy>

In iOS development, **unit tests** check small, isolated units of code, like functions, models, and view models.
Good unit tests follow the **AAA pattern**:

1. **Arrange**: Set up test data, input parameters, and mock objects.
2. **Act**: Call the function or method you want to test.
3. **Assert**: Verify that the actual result matches your expected output.

Apple provides two testing frameworks:

- **XCTest**: The traditional framework. Tests inherit from `XCTestCase`, methods begin with `test`, and use assertions like `XCTAssertEqual`.
- **Swift Testing**: The modern pure-Swift framework. Uses the `@Test` and `@Suite` macros, runs tests in parallel, and checks values with `#expect`.

## In code

Here is the **Arrange-Act-Assert** pattern in action.
We test a shopping cart discount calculation without any UIKit dependencies.

<CodeExample title="The Arrange-Act-Assert pattern for business logic">

```swift
import Foundation

struct ShoppingCart {
    private(set) var items: [Int] = []

    mutating func add(price: Int) {
        items.append(price)
    }

    func total(discountPercent: Int) -> Int {
        let sum = items.reduce(0, +)
        let discount = (sum * discountPercent) / 100
        return sum - discount
    }
}

final class CartTestRunner {
    func testCartTotalCalculation() {
        // Arrange
        var cart = ShoppingCart()
        cart.add(price: 100)
        cart.add(price: 50)

        // Act
        let total = cart.total(discountPercent: 10)

        // Assert
        assert(total == 135, "Expected 135 after 10% discount")
        print("Test passed: cart total is $\(total)")
    }
}

let runner = CartTestRunner()
runner.testCartTotalCalculation()
```

```output
Test passed: cart total is $135
```

</CodeExample>

Now look at isolating code using a test double.
By injecting a `MockAuthAPI`, we test the `LoginCoordinator` without hitting a real backend.

<CodeExample title="Using a mock spy to verify method calls and parameters">

```swift
import Foundation

protocol AuthAPI {
    func signIn(token: String) -> Bool
}

final class MockAuthAPI: AuthAPI {
    var wasCalled = false
    var lastToken: String?

    func signIn(token: String) -> Bool {
        wasCalled = true
        lastToken = token
        return true
    }
}

final class LoginCoordinator {
    private let api: AuthAPI

    init(api: AuthAPI) {
        self.api = api
    }

    func authenticate(token: String) -> Bool {
        return api.signIn(token: token)
    }
}

// Arrange
let mock = MockAuthAPI()
let coordinator = LoginCoordinator(api: mock)

// Act
let success = coordinator.authenticate(token: "secret_token_123")

// Assert
assert(success == true)
assert(mock.wasCalled == true)
assert(mock.lastToken == "secret_token_123")
print("Mock verified: authentication succeeded with token")
```

```output
Mock verified: authentication succeeded with token
```

</CodeExample>

## Interview traps

<Trap title="Using #expect when unwrapping optionals">
In Swift Testing, `#expect` records a failure but continues executing.
If you check an optional with `#expect(user != nil)` and then force-unwrap `user!`, the test crashes at runtime.
Always use `let user = try #require(optionalUser)` to halt safely when unwrapping fails.
</Trap>

<Trap title="Sharing mutable global state between tests">
Swift Testing runs test functions concurrently in parallel by default.
If multiple tests read and write to a shared singleton, race conditions occur.
Tests will fail intermittently.
Always use local state or inject fresh instances for each test.
</Trap>

<Trap title="Testing implementation details instead of behavior">
Asserting on private variable states makes tests brittle.
When you refactor internal code, tests break even though user behavior remains correct.
Test public inputs and outputs rather than private implementation details.
</Trap>

<Trap title="Writing slow integration tests as unit tests">
Calling real disk files, live network endpoints, or hardware sensors belongs in integration tests.
Unit tests should execute in memory in milliseconds.
Decouple dependencies with protocols and inject mocks.
</Trap>

## Recap

<Recap>
- **Unit tests** verify isolated units of code like functions, models, and view models.
- Follow the **Arrange-Act-Assert** (AAA) pattern for clear, readable tests.
- **XCTest** uses class inheritance, `test` function prefixes, and `XCTAssert` methods.
- **Swift Testing** uses modern `@Test` and `@Suite` macros with pure Swift syntax.
- Use **#expect** for continuing checks and **try #require** to halt on fatal unwrap failures.
- Decouple networking and storage using protocols to inject fast in-memory mocks.
</Recap>
