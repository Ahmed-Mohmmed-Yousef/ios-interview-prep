## The simple idea

<Analogy>
Imagine a sign in a shop window and a remote control held by a helper.

The shop owner keeps the sign inside the shop. That sign is the **source of truth** (`@State`).

The owner hands a remote control to a helper outside. When the helper presses a button, the sign in the window changes right away.

The remote control is a **binding** (`@Binding`). It stores no letters of its own. It only reads and updates the original sign.
</Analogy>

In SwiftUI, views are structs that get recreated often.

To store and share changing data without losing it on each redraw, SwiftUI gives you two property wrappers:
1. **`@State` (the source of truth)**:
   - `@State` creates local data owned by one view.
   - SwiftUI stores the real value outside the struct in persistent memory.
   - When SwiftUI recreates the view struct, it reconnects `@State` to that saved memory.
   - When an `@State` value changes, SwiftUI updates the views that read it on the main thread.
   - Always mark `@State` properties `private` so outside views cannot change them directly.
2. **`@Binding` (the two-way connection)**:
   - `@Binding` is a value-type struct wrapper that connects to data owned by another view.
   - A binding stores no data of its own.
   - Reading a binding reads the parent value. Writing to a binding updates the parent value.
   - Unlike Swift `inout` parameters, which last only for one function call, `@Binding` works across many UI redraws.
3. **The projected value (`$`)**:
   - Writing `$` before an `@State` variable (like `$isOn`) reads its projected value.
   - That gives you a `Binding` to pass to child views or controls like `Toggle` and `TextField`.

**SwiftUI uses unidirectional (one-way) data flow.** State flows down from parent to child as plain values or bindings. User actions flow back up through bindings or closures to update the source of truth.

## In code

<CodeExample title="Managing a local counter with @State">

```swift
import SwiftUI

struct CounterView: View {
    @State private var count: Int = 0

    var body: some View {
        VStack(spacing: 8) {
            Text("Count: \(count)")
            Button("Increment") {
                count += 1
            }
        }
    }
}

let counter = CounterView()
print("CounterView created: \(type(of: counter))")
```

```output
CounterView created: CounterView
```

</CodeExample>

In this example, tapping "Increment" changes `count`. SwiftUI sees the change and calls `var body` again to show the new number.

<CodeExample title="Sharing state with a child view using @Binding">

```swift
import SwiftUI

struct ToggleSwitch: View {
    @Binding var isEnabled: Bool

    var body: some View {
        Button(isEnabled ? "Disable" : "Enable") {
            isEnabled.toggle()
        }
    }
}

struct SettingsScreen: View {
    @State private var notificationsActive: Bool = false

    var body: some View {
        VStack {
            Text("Notifications: \(notificationsActive ? "On" : "Off")")
            ToggleSwitch(isEnabled: $notificationsActive)
        }
    }
}

let screen = SettingsScreen()
print("SettingsScreen created: \(type(of: screen))")
```

```output
SettingsScreen created: SettingsScreen
```

</CodeExample>

Here, `SettingsScreen` owns `notificationsActive` with `@State`. It passes `$notificationsActive` into `ToggleSwitch` (or into built-in controls like `TextField("Enter name", text: $name)`), so the child updates the parent's state directly.

When you write previews or custom adapters, SwiftUI also gives you two helpful ways to create a `Binding`:
- **`Binding.constant(_:)`**: Creates a fixed binding (like `.constant(true)`) for `#Preview` blocks when there is no parent `@State`.
- **`Binding(get:set:)`**: Creates a custom binding from getter and setter closures, and you can read or write its value directly with `.wrappedValue`.

## Interview traps

<Trap title="Initializing @State inside init from a parameter">
Writing `_count = State(initialValue: incomingValue)` inside a view's `init` is a common mistake.

SwiftUI sets up `@State` memory only once when the view first enters the screen.

If the parent redraws and passes a new value to `init`, SwiftUI keeps the old `@State` value and ignores the new input.

If a child must update when the parent passes a new value, use a plain `let` property or a `@Binding`.
</Trap>

<Trap title="Changing @State directly inside var body">
Never write `count += 1` directly inside `var body`.

Changing `@State` while SwiftUI is running `var body` forces another immediate redraw.

This causes runtime warnings and repeated redraw loops that can freeze your app.
</Trap>

<Trap title="Thinking @Binding stores its own copy of data">
A `@Binding` stores no value of its own. It only connects to a source of truth owned somewhere else.

Changing a binding changes the original data right away.

Never use `@Binding` when a child needs its own separate copy of a value.
</Trap>

<Trap title="Using @State for app-wide shared data">
`@State` is built for view-local UI state like toggles, text input, and counters (and can also own a view-local `@Observable` class instance).

Putting shared network or database models in `@State` across many screens makes data hard to track.

For shared app data, pass `@Observable` models down or store them in the environment.
</Trap>

## How to answer in the interview

<InterviewAnswer level="fresh">
"`@State` creates a local source of truth owned by one view. Because SwiftUI recreates view structs often, SwiftUI stores `@State` values in separate persistent memory. `@Binding` is a two-way connection to data owned by another view without copying storage. We pass bindings with the `$` prefix so child views can read and update parent state."
</InterviewAnswer>

<InterviewAnswer level="junior">
"SwiftUI uses unidirectional data flow: state flows down as values or bindings, and user actions flow back up. When an `@State` value changes, SwiftUI updates the affected views on the main thread. Using `@Binding` lets reusable child views edit parent data while keeping one source of truth. We mark `@State` private and avoid setting it from parameters in `init`."
</InterviewAnswer>

<InterviewAnswer level="senior">
"SwiftUI ties `@State` storage to a view's identity in its persistent attribute graph, separate from the short-lived view struct. When state changes, SwiftUI marks dependent views dirty and computes minimal diffs on the next update pass. For previews and tests, `Binding.constant(_:)` supplies fixed values, while `Binding(get:set:)` adapts custom getters and setters. In larger apps, `@State` handles local UI state while `@Observable` models manage shared domain state."
</InterviewAnswer>

## Recap

<Recap>
- **`@State`** creates a view-local source of truth saved outside the temporary view struct.
- Always mark `@State` properties as **`private`**.
- **`@Binding`** is a value-type two-way connection to data owned elsewhere, with no storage of its own.
- The **`$`** prefix reads the projected value of `@State` and returns a `Binding`.
- Use `Binding.constant(_:)` for previews and `Binding(get:set:)` for custom read/write logic.
- Never change `@State` inside `var body`, and avoid initializing `@State` from `init` parameters.
</Recap>
