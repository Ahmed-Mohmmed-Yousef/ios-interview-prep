## The simple idea

<Analogy>
Think of a physical concert ticket with a barcode. You can let a friend look at the ticket (`borrowing`), and you still hold it. If you hand the ticket to the door guard (`consuming`), you no longer have it and cannot hand it over a second time.
</Analogy>

In Swift, every `struct` and `enum` conforms to **`Copyable`** by default, which means Swift can copy values freely. When you write **`: ~Copyable`** (read as "noncopyable"), you turn off that default `Copyable` conformance. Assigning `let b = a` moves ownership from `a` to `b` instead of copying. **A noncopyable value has exactly one owner at a time, enforced at compile time.**

Because there is only one owner, a noncopyable `struct` can define a **`deinit`**. This cleanup block runs when the owner leaves scope. Regular copyable structs cannot have a `deinit` because copies would run cleanup multiple times. Noncopyable enums do not support `deinit` yet.

Swift gives you clear ownership modifiers to control how functions and methods access values:

- **`borrowing`**: gives temporary read-only access without taking ownership or making a copy. The caller can still use the value afterward.
- **`consuming`**: transfers ownership into the function or method. For a noncopyable value, the caller cannot use that variable again.
- **`inout`** (or `mutating` on a method): gives temporary write access and returns ownership when the call finishes.

Three more keywords complete the picture:
- **`consume`**: moves a local variable (copyable or noncopyable) to another binding or call and ends use of the old variable.
- **`discard self`**: inside a `consuming` method, destroys `self` immediately and skips `deinit`. Use this after manual cleanup so `deinit` does not run twice.
- **`copy`**: creates an explicit copy of a `Copyable` value, such as inside a `borrowing` or `consuming` parameter.

By default, generic types `<T>` and protocols still require `Copyable`. Write **`<T: ~Copyable>`** or **`protocol Resource: ~Copyable`** to accept noncopyable types too. If a generic function uses such a protocol, write `<T: ~Copyable & Resource>`. Standard types like `Optional` already support `~Copyable` values.

## In code

In the example below, `Ticket` is a noncopyable struct with a `deinit`. Notice that `inspect()` uses `borrowing`, while `redeem()` uses `consuming` and `discard self`.

<CodeExample title="Borrowing, consuming, and discard self on a ~Copyable struct">

```swift
protocol Pass: ~Copyable {
    borrowing func inspect()
}

struct Ticket: ~Copyable, Pass {
    let code: Int

    borrowing func inspect() {
        print("Inspect \(code)")
    }

    consuming func redeem() {
        print("Redeemed \(code)")
        discard self
    }

    deinit {
        print("Expired \(code)")
    }
}

func checkGeneric<T: ~Copyable>(_ item: borrowing T) {
    print("Checked generic")
}

func run() {
    let first = Ticket(code: 42)
    first.inspect()
    checkGeneric(first)
    first.redeem()

    let second = Ticket(code: 99)
    second.inspect()
}

run()
```

```output
Inspect 42
Checked generic
Redeemed 42
Inspect 99
Expired 99
```

</CodeExample>

Look at the output carefully:
- `first.redeem()` printed `"Redeemed 42"` and called `discard self`, so `deinit` did **not** print `"Expired 42"`.
- `second` was never redeemed, so its `deinit` ran automatically at the end of `run()` and printed `"Expired 99"`.
- `checkGeneric` accepted `first` because its type parameter used `<T: ~Copyable>`.

You can also store a `~Copyable` type in an `Optional` or switch over a `~Copyable` enum while borrowing its associated values.

<CodeExample title="Borrowing pattern matching and Optional with ~Copyable">

```swift
enum VaultState: ~Copyable {
    case locked(keyID: Int)
    case open
}

func inspectVault(_ vault: borrowing VaultState) {
    switch vault {
    case .locked(let keyID):
        print("Locked with key \(keyID)")
    case .open:
        print("Open")
    }
}

func testVault() {
    let maybeVault: VaultState? = .locked(keyID: 7)
    if let vault = consume maybeVault {
        inspectVault(vault)
        inspectVault(vault)
    }
}

testVault()
```

```output
Locked with key 7
Locked with key 7
```

</CodeExample>

Here `consume maybeVault` moved the value into `vault`, and `inspectVault` borrowed `vault` twice without copying or consuming it.

### Ownership modifiers at a glance

| Keyword | Meaning | Can caller use value after? |
|---|---|---|
| `borrowing` | Temporary read-only access, no copy | Yes |
| `consuming` | Moves ownership into callee | No |
| `inout` / `mutating` | Temporary exclusive write access | Yes |
| `discard self` | Ends `self` inside `consuming` method without `deinit` | No |
| `copy` | Explicitly copies a `Copyable` value | Yes |

## Interview traps

<Trap title="Thinking ~Copyable turns a struct into a class">
Noncopyable structs and enums stay value types with zero ARC reference-counting overhead. They enforce unique ownership at compile time rather than sharing a heap object.
</Trap>

<Trap title="Forgetting that generic <T> still requires Copyable">
If you write `func log<T>(_ value: borrowing T)`, Swift rejects a `~Copyable` argument because `T` defaults to `Copyable`. You must write `<T: ~Copyable>` on generic types, functions, and protocols that accept noncopyable values.
</Trap>

<Trap title="Thinking borrowing and consuming only help ~Copyable types">
You can also mark parameters `borrowing` or `consuming` on normal `Copyable` types, such as `String` or `Array`. This avoids extra retains or copies in hot loops. Note that inside a `borrowing` or `consuming` parameter, implicit copies are disabled. You must write `copy value` if you really want a copy.
</Trap>

## How to answer in the interview

<InterviewAnswer level="senior">
A `~Copyable` type suppresses Swift's default `Copyable` conformance so a struct or enum has exactly one owner at compile time. This enables value-type `deinit` for resources like file handles or locks without heap allocation or ARC overhead. `borrowing` gives temporary read access, `consuming` moves ownership and ends caller access, and `discard self` prevents `deinit` from running after manual cleanup.
</InterviewAnswer>

<InterviewAnswer level="staff">
Noncopyable types and ownership modifiers let teams model strict resource lifetimes and zero-copy hot paths directly in Swift's type system. You can design unique tokens, database transactions, or state machines where use-after-close becomes a compile error instead of a runtime crash. Generic parameters and protocols still default to `Copyable`. Library boundaries must opt in with `~Copyable` and explicit `borrowing`, `consuming`, or `inout` parameters.
</InterviewAnswer>

## Recap

<Recap>
- Adding `: ~Copyable` to a `struct` or `enum` enforces single ownership at compile time. Noncopyable structs can also define a `deinit`.
- `borrowing` lends temporary read access without copying; `consuming` transfers ownership and ends caller use.
- `discard self` inside a `consuming` method destroys `self` without running `deinit`.
- Generic parameters and protocols default to `Copyable`; write `<T: ~Copyable>` to accept noncopyable types.
</Recap>
