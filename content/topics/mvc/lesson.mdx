## The simple idea

<Analogy>
Imagine a busy restaurant with three distinct roles.

The **kitchen chef** prepares the food and manages ingredients.
The chef does not care which table the customer sits at.
This chef represents the **Model**.

The **dining table** holds clean plates, napkins, and decorative flowers.
The table displays food to the customer, but cannot cook meals.
This table represents the **View**.

The **waiter** takes orders from the customer and gives tickets to the chef.
When food is ready, the waiter carries plates to the table.
This waiter represents the **Controller**.

Now imagine what happens if the restaurant fires the dishwasher, the host, and the accountant.
The waiter must now cook soup, wash plates, seat guests, and balance the cash register.
The waiter becomes exhausted and makes errors.
In iOS development, this problem is called the **Massive View Controller**.
</Analogy>

In Apple Cocoa MVC, the three layers have strict jobs:

1. **Model**: Stores data, database records, and core business rules. It knows nothing about the user interface.
2. **View**: Shows visual elements on the screen. It displays information and forwards user gestures to the controller.
3. **Controller**: Mediates between Model and View. It responds to user input, updates data models, and refreshes views.

In UIKit, `UIViewController` is closely tied to its root `UIView`.
Because of this tight connection, developers often put table data sources, network requests, and navigation inside the view controller.
The file grows too large, becomes hard to read, and is difficult to unit test.

## In code

To keep view controllers slim, move tasks into dedicated helper types.
Here, a network service handles data loading, and a custom view handles presentation.

<CodeExample title="Separating Model, View, and Service from the Controller">

```swift
import Foundation

struct User {
    let name: String
    let email: String
}

final class UserService {
    func fetchUser() -> User {
        return User(name: "Taylor", email: "taylor@example.com")
    }
}

final class UserView {
    func display(name: String, email: String) {
        print("Name: \(name)")
        print("Email: \(email)")
    }
}

final class UserController {
    private let service: UserService
    private let view: UserView

    init(service: UserService, view: UserView) {
        self.service = service
        self.view = view
    }

    func loadData() {
        let user = service.fetchUser()
        view.display(name: user.name, email: user.email)
    }
}

let controller = UserController(service: UserService(), view: UserView())
controller.loadData()
```

```output
Name: Taylor
Email: taylor@example.com
```

</CodeExample>

Another way to slim down controllers is extracting formatting logic.
Instead of formatting currency inside a view controller, use a dedicated formatter struct.

<CodeExample title="Extracting formatting logic into a dedicated helper">

```swift
import Foundation

struct Product {
    let title: String
    let priceInCents: Int
}

struct PriceFormatter {
    static func format(cents: Int) -> String {
        let dollars = Double(cents) / 100.0
        return String(format: "$%.2f", dollars)
    }
}

final class ProductDisplayCoordinator {
    func prepareText(for product: Product) -> String {
        let price = PriceFormatter.format(cents: product.priceInCents)
        return "\(product.title) costs \(price)"
    }
}

let item = Product(title: "Keyboard", priceInCents: 9999)
let coordinator = ProductDisplayCoordinator()
print(coordinator.prepareText(for: item))
```

```output
Keyboard costs $99.99
```

</CodeExample>

## Interview traps

<Trap title="Letting the View know the Model">
Developers often pass a domain model directly into a custom view class.
This couples the view to that specific model and prevents view reuse.
Pass primitive values or view data structures to views instead of raw database models.
</Trap>

<Trap title="Writing network calls in viewDidLoad">
Calling `URLSession` directly inside `viewDidLoad` couples the view controller to networking details.
This makes mock data impossible to inject during unit tests.
Always wrap network requests inside a dedicated service protocol or class.
</Trap>

<Trap title="Confusing Apple MVC with Smalltalk MVC">
In original Smalltalk MVC from 1979, the View observed the Model directly.
In Apple Cocoa MVC, the View and Model never talk directly.
The Controller mediates every exchange.
</Trap>

<Trap title="Assuming MVC is always bad">
Some developers believe MVC must never be used and that every screen requires complex architecture.
For simple screens, standard MVC is lightweight and easy to understand.
The goal is disciplined separation of responsibilities, not architecture overhead.
</Trap>

## How to answer in the interview

<InterviewAnswer level="fresh">
MVC stands for Model, View, and Controller.
The Model holds data, the View shows the user interface, and the Controller connects them.
In iOS, view controllers often get too big because developers put network calls, layout, and business logic into one file.
We can fix this by moving networking into services and formatting into helper structs.
</InterviewAnswer>

<InterviewAnswer level="junior">
In Cocoa MVC, the controller acts as an explicit mediator between dumb views and domain models.
The Massive View Controller problem occurs because `UIViewController` connects directly to the view lifecycle.
Developers often put table data sources, network requests, and navigation into one class.
I solve this by extracting services for networking and persistence.
I also use Diffable Data Sources and break complex screens into child view controllers.
</InterviewAnswer>

<InterviewAnswer level="senior">
The core design tension in UIKit MVC is that `UIViewController` combines view management with controller mediation.
This violates the Single Responsibility Principle and creates testing friction, because business rules require loading view hierarchies to test.
While modern architectures like MVVM and Coordinator decouple presentation and navigation, disciplined MVC can remain clean.
We achieve this through container child view controllers, dedicated service boundaries, and pure presentation formatters.
</InterviewAnswer>

## Recap

<Recap>
- **Model** holds data and business logic; it knows nothing about the user interface.
- **View** presents visual elements and forwards user interactions to the controller.
- **Controller** coordinates data flow between the Model and the View.
- **Massive View Controller** happens when networking, data sources, and formatting pile into one file.
- Fix bloated controllers by extracting dedicated services, formatters, and child view controllers.
- Keeping business logic in pure Swift types makes unit testing fast and reliable.
</Recap>
