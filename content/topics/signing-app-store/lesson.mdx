## The simple idea

<Analogy>
Imagine sending an important legal contract through the mail.

First, you sign the contract with your verified wax seal. The seal proves you wrote the document.

Second, you place the contract inside a tamper-proof envelope.

If anyone opens or alters the envelope along the way, the wax seal breaks.

The receiver knows the contract was changed and rejects it immediately.

Code signing works the same way. It proves who built the app and guarantees nobody altered the code.
</Analogy>

iOS requires every app running on a physical device to be signed.

Three key pieces make up the code signing process:

1. **Certificates**:
   - Digital documents issued by Apple that prove your identity.
   - A **Development Certificate** lets engineers install and debug builds on team test devices.
   - A **Distribution Certificate** signs release builds for TestFlight and the App Store.
   - The private key stays secret on your Mac. The public certificate is shared with Apple.
2. **App ID (Bundle Identifier)**:
   - A unique identifier for your app, like `com.example.phototracker`.
   - It defines which capabilities your app can use, like Push Notifications or iCloud.
3. **Provisioning Profile (`.mobileprovision`)**:
   - The file that binds everything together.
   - It links your App ID, your certificate, and your entitlements.
   - Development profiles also contain a list of allowed test device UDIDs.
   - App Store distribution profiles do not list devices because Apple signs the final release for everyone.

Once signed, you archive your app in Xcode and upload the build to App Store Connect.

You can invite teammates to test internal builds through TestFlight immediately.

After automated and human App Review, your app is approved and ready for release.

## In code

Every app submission requires distinct version and build numbers.

In your project configuration, `CFBundleShortVersionString` is the marketing version.

`CFBundleVersion` is the internal build number. Each upload requires an increased build number.

<CodeExample title="Managing version and build numbers">

```swift
struct AppVersionInfo {
    let marketingVersion: String
    let buildNumber: Int

    func isNewerBuild(than previousBuild: Int) -> Bool {
        buildNumber > previousBuild
    }
}

let currentRelease = AppVersionInfo(marketingVersion: "2.1.0", buildNumber: 42)
let isReadyForUpload = currentRelease.isNewerBuild(than: 41)

print("Marketing version: \(currentRelease.marketingVersion)")
print("Upload allowed: \(isReadyForUpload)")
```

```output
Marketing version: 2.1.0
Upload allowed: true
```

</CodeExample>

Different distribution methods require different provisioning profile rules.

Development profiles require device UDIDs, while App Store profiles omit them.

<CodeExample title="Inspecting provisioning profile requirements">

```swift
enum ProvisioningKind {
    case development
    case appStore
}

func requiresDeviceList(for kind: ProvisioningKind) -> Bool {
    switch kind {
    case .development:
        return true
    case .appStore:
        return false
    }
}

let profileType = ProvisioningKind.appStore
print("Type: \(profileType)")
print("Needs device UDIDs: \(requiresDeviceList(for: profileType))")
```

```output
Type: appStore
Needs device UDIDs: false
```

</CodeExample>

## Interview traps

<Trap title="Assuming App Store profiles list devices">
Many developers assume all provisioning profiles list allowed test devices.

Development and Ad-Hoc profiles include device UDIDs.

App Store profiles never contain device UDIDs.

Apple re-encrypts and signs production binaries so all customers can install them.
</Trap>

<Trap title="Confusing marketing version with build number">
Uploading a new binary requires incrementing the build number (`CFBundleVersion`).

If you upload two builds with the same build number, App Store Connect rejects the second upload.

The marketing version (`CFBundleShortVersionString`) can remain the same while fixing beta bugs.
</Trap>

<Trap title="Forgetting to backup distribution private keys">
When moving to a new Mac, developers often copy only the project code.

If you do not export your private key as a `.p12` file, you cannot sign releases.

Always back up certificates and private keys securely or use automatic team signing.
</Trap>

<Trap title="Releasing to 100% of users immediately">
Releasing a major update to all users on day one is risky.

If an unexpected crash occurs, all active users experience the bug.

Use Phased Release to roll out updates gradually over seven days.
</Trap>

## Recap

<Recap>
- Code signing verifies author identity and guarantees binary integrity.
- The three signing pillars are Certificates, App IDs, and Provisioning Profiles.
- Development certificates are for debugging on personal test hardware.
- Distribution certificates sign builds for TestFlight and the App Store.
- Development profiles include device UDIDs; App Store profiles do not.
- Each upload to App Store Connect requires an increased build number (`CFBundleVersion`).
- Internal TestFlight builds are available immediately without Apple review.
- Phased Release rolls out updates gradually over seven days.
</Recap>
