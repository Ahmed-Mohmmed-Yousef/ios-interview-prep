## The simple idea

<Analogy>
Imagine a rolling billboard with a small viewing window.

Instead of pasting ten thousand posters along miles of highway, the billboard keeps only three posters ready near the window. As the paper rolls upward, posters leaving the top are removed, and new posters entering the bottom are inserted.

This lazy recycling is how a **`List`** works. It creates only the rows visible on screen.
</Analogy>

In iOS development, displaying collections of data is one of the most common tasks.

SwiftUI provides two core tools for building scrolling lists:
1. **`List` (Lazy Recycling)**:
   - `List` is built for performance.
   - It only allocates memory and renders views for rows that are currently visible on screen.
   - As you scroll, offscreen rows are recycled.
   - It includes standard iOS styling like row separators and swipe actions.
2. **`ForEach` (Collection Iteration)**:
   - `ForEach` loops over a collection to generate views dynamically.
   - It requires each element to have a unique and stable identity.
3. **`Identifiable` (Row Identity)**:
   - When a data struct conforms to `Identifiable`, it provides an `id` property.
   - SwiftUI uses this `id` to track which rows are added, removed, or animated.
   - If your model does not conform to `Identifiable`, you must pass an explicit key path like `id: \.self`.

## In code

<CodeExample title="Displaying identifiable data with List">

```swift
import SwiftUI

struct TodoItem: Identifiable {
    let id = UUID()
    let title: String
}

struct TodoListView: View {
    let items = [
        TodoItem(title: "Prepare interview questions"),
        TodoItem(title: "Review Swift 6 features"),
        TodoItem(title: "Practice SwiftUI layouts")
    ]
    
    var body: some View {
        List(items) { item in
            Text(item.title)
        }
    }
}

let list = TodoListView()
print("TodoListView initialized: \(type(of: list))")
```

```output
TodoListView initialized: TodoListView
```

</CodeExample>

Because `TodoItem` conforms to `Identifiable`, you pass `items` directly to `List`. You do not need to provide an explicit `id` key path parameter.

<CodeExample title="Deleting items from a list with ForEach">

```swift
import SwiftUI

struct FruitListView: View {
    @State private var fruits = ["Apple", "Banana", "Cherry"]
    
    var body: some View {
        List {
            ForEach(fruits, id: \.self) { fruit in
                Text(fruit)
            }
            .onDelete { indices in
                fruits.remove(atOffsets: indices)
            }
        }
    }
}

let fruitList = FruitListView()
print("FruitListView initialized: \(type(of: fruitList))")
```

```output
FruitListView initialized: FruitListView
```

</CodeExample>

In this example, the string elements use `id: \.self` for identity.

The `.onDelete` modifier attaches to the `ForEach`, enabling standard iOS swipe-to-delete behavior.

## Interview traps

<Trap title="Attaching .onDelete directly to List">
A very frequent interview mistake is writing `List { ... }.onDelete { ... }`.

This will fail to compile.

The `.onDelete` modifier belongs to `DynamicViewContent`. In SwiftUI, `ForEach` conforms to this protocol, while `List` does not.

Always attach `.onDelete` and `.onMove` to your `ForEach` block.
</Trap>

<Trap title="Using id: \.self with duplicate items">
If an array contains duplicate strings like `["Apple", "Banana", "Apple"]`, using `id: \.self` creates identical IDs.

SwiftUI relies on unique IDs to diff rows. Duplicate IDs cause row animations to glitch, selections to break, or wrong items to delete.

Always make sure elements have unique identifiers or conform to `Identifiable` using a `UUID`.
</Trap>

<Trap title="Generating dynamic UUIDs inside computed id getters">
Declaring `var id: UUID { UUID() }` as a computed property is dangerous.

Every time SwiftUI inspects the view struct, it generates a brand new UUID.

This causes SwiftUI to treat existing rows as newly inserted items on every redraw, breaking scroll position and animations.

Always store the identifier in a constant stored property: `let id = UUID()`.
</Trap>

<Trap title="Using ScrollView and VStack for massive lists">
A `ScrollView` wrapping a standard `VStack` creates every single row immediately upon loading.

If your dataset contains hundreds of items, this eager loading causes memory spikes and stuttering frames.

Use `List` (or `LazyVStack`) when scrolling through large collections.
</Trap>

## How to answer in the interview

<InterviewAnswer level="fresh">
"`List` is a scrolling container that creates and recycles rows lazily as they appear on screen. In contrast, `ScrollView` with a `VStack` loads all row views eagerly in memory. To loop over collections, we use `ForEach`, which requires elements to have unique identities using `Identifiable` or an explicit `id` key path. We add swipe-to-delete by attaching the `.onDelete` modifier to the `ForEach`."
</InterviewAnswer>

<InterviewAnswer level="junior">
"SwiftUI uses element identity to track row insertions, removals, and reordering animations. When models conform to `Identifiable`, SwiftUI tracks row lifecycles cleanly. It is critical that `id` values remain stable; generating `UUID()` inside a computed property breaks diffing and resets scroll states. For collection mutations, we attach `.onDelete` and `.onMove` to `ForEach` because it conforms to `DynamicViewContent`."
</InterviewAnswer>

<InterviewAnswer level="senior">
"Behind the scenes on iOS, `List` is backed by `UICollectionView`, providing native cell reuse queues and high-performance virtualization. When rendering heterogeneous lists, `List` provides built-in swipe actions, headers, and separator insets. For custom scrolling layouts that require continuous coordinate tracking without list cell semantics, we choose `LazyVStack` inside a `ScrollView`. To maintain 120fps scrolling on ProMotion displays, row view bodies should remain pure and avoid synchronous image decodes."
</InterviewAnswer>

## Recap

<Recap>
- **`List`** loads and recycles rows lazily, making it efficient for large collections.
- `ScrollView` with `VStack` loads all views eagerly, which can cause memory problems.
- **`ForEach`** generates views from a collection and requires unique element identities.
- Models conforming to **`Identifiable`** provide a stable `id` for diffing and animations.
- Always store identifiers with **`let id = UUID()`**; never use a computed getter.
- Attach **`.onDelete`** to `ForEach`, not to `List`, to enable swipe-to-delete.
</Recap>
