## The simple idea

<Analogy>
Imagine a rolling billboard with a small viewing window.

Instead of pasting ten thousand posters along miles of highway, the billboard keeps only three posters ready near the window. As the paper rolls upward, posters leaving the top are removed, and new posters entering the bottom are placed in.

This lazy reuse is how a **`List`** works. It creates only the rows visible on screen.
</Analogy>

In iOS apps, showing lists of data is one of the most common tasks.

SwiftUI gives you three core tools for building scrolling lists:
1. **`List` (Lazy Row Reuse)**:
   - `List` is built for speed and low memory use.
   - It creates views only for rows that are visible on screen, loading lazily as you scroll.
   - As you scroll, offscreen rows are reused instead of keeping thousands of views in memory.
   - It includes built-in iOS row styles, separator lines, selection, and swipe actions.
2. **`ForEach` (Looping Over Data)**:
   - `ForEach` loops over a collection to build views inside a `List` or stack.
   - It needs each item to have a unique, stable ID.
3. **`Identifiable` (Row Identity)**:
   - When a data struct conforms to `Identifiable`, it has an `id` property of any `Hashable` type (such as `UUID` or `Int`).
   - SwiftUI uses this `id` to track which rows are added, removed, moved, or animated.
   - If your model does not conform to `Identifiable`, pass an explicit key path like `id: \.self`.

## In code

<CodeExample title="Displaying identifiable data with List">

```swift
import SwiftUI

struct TodoItem: Identifiable {
    let id = UUID()
    let title: String
}

struct TodoListView: View {
    let items = [
        TodoItem(title: "Prepare interview questions"),
        TodoItem(title: "Review Swift 6 features"),
        TodoItem(title: "Practice SwiftUI layouts")
    ]
    
    var body: some View {
        List(items) { item in
            Text(item.title)
        }
    }
}

let list = TodoListView()
print("TodoListView initialized: \(type(of: list))")
```

```output
TodoListView initialized: TodoListView
```

</CodeExample>

Because `TodoItem` conforms to `Identifiable`, you pass `items` directly to `List`. You do not need an `id` key path parameter.

<CodeExample title="Deleting items from a list with ForEach">

```swift
import SwiftUI

struct FruitListView: View {
    @State private var fruits = ["Apple", "Banana", "Cherry"]
    
    var body: some View {
        List {
            ForEach(fruits, id: \.self) { fruit in
                Text(fruit)
            }
            .onDelete { indices in
                fruits.remove(atOffsets: indices)
            }
        }
    }
}

let fruitList = FruitListView()
print("FruitListView initialized: \(type(of: fruitList))")
```

```output
FruitListView initialized: FruitListView
```

</CodeExample>

In this example, the string items use `id: \.self` for identity.

Common modifiers and options for `List` and `ForEach`:
- **Swipe to delete and reorder**: Attach `.onDelete(perform:)` or `.onMove(perform:)` to `ForEach`. In `.onMove`, the closure receives a source `IndexSet` and a destination `Int` so you can call `items.move(fromOffsets: source, toOffset: destination)`.
- **Custom swipe buttons**: Add `.swipeActions(edge:)` (leading or trailing) to a row view inside the list.
- **List styles and separators**: Apply `.listStyle(_:)` (such as `.plain` or `.insetGrouped`) to `List` to change its visual style. Add `.listRowSeparator(.hidden)` to row views to hide default separator lines.
- **Multi-row selection**: Pass a binding to a `Set` of item IDs using `List(selection: $selectedIDs)`.

## Interview traps

<Trap title="Attaching .onDelete directly to List">
A common interview mistake is writing `List { ... }.onDelete { ... }`.

This will fail to compile.

The `.onDelete` modifier belongs to `DynamicViewContent`. In SwiftUI, `ForEach` conforms to this protocol, while `List` does not.

Always attach `.onDelete` and `.onMove` to your `ForEach` block.
</Trap>

<Trap title="Using id: \.self with duplicate items">
If an array has duplicate strings like `["Apple", "Banana", "Apple"]`, using `id: \.self` gives two rows the same ID.

SwiftUI uses unique IDs to compare rows. Duplicate IDs break row animations, break row selection, or delete the wrong item.

Always make sure items have unique IDs, or wrap your data in an `Identifiable` model.
</Trap>

<Trap title="Generating new UUIDs inside computed id getters">
Declaring `var id: UUID { UUID() }` as a computed property causes bugs.

Every time SwiftUI reads the view struct, it generates a new UUID.

SwiftUI then treats existing rows as brand-new items on every redraw, breaking scroll position and animations.

Always store the ID in a stored constant property: `let id = UUID()`.
</Trap>

<Trap title="Using ScrollView and VStack for large lists">
A `ScrollView` wrapping a standard `VStack` creates every row at once as soon as it loads (eager loading).

If your list has hundreds of items, loading them all at once causes memory spikes and slow frames.

Use `List` when you want built-in list styling and cell reuse. Use `LazyVStack` inside `ScrollView` when you want lazy loading without list separators or default row styles.
</Trap>

## How to answer in the interview

<InterviewAnswer level="fresh">
"`List` is a scrolling container that creates and reuses rows lazily as they appear on screen. In contrast, `ScrollView` with a `VStack` loads all row views eagerly in memory. To loop over collections, we use `ForEach`, which needs unique IDs using `Identifiable` or an explicit `id` key path. We add swipe-to-delete by attaching `.onDelete` to the `ForEach`."
</InterviewAnswer>

<InterviewAnswer level="junior">

ID values must stay stable because generating `UUID()` in a computed property breaks diffing and resets scroll position. For collection edits, we attach `.onDelete` and `.onMove` to `ForEach` because it conforms to `DynamicViewContent`."
</InterviewAnswer>

<InterviewAnswer level="senior">

When you need custom scroll layouts without list row styling, `LazyVStack` inside a `ScrollView` loads lazily with full layout control. To keep scrolling smooth, keep row `body` work light and avoid heavy image decoding on the main thread."
</InterviewAnswer>

## Recap

<Recap>
- **`List`** loads and reuses rows lazily, making it fast for large collections.
- `ScrollView` with `VStack` loads all views at once (eagerly), which can cause memory problems.
- **`ForEach`** builds views from a collection and needs unique item IDs.
- Models conforming to **`Identifiable`** give a stable `id` for diffing and animations.
- Always store IDs with **`let id = UUID()`**; never use a computed getter.
- Attach **`.onDelete`** and **`.onMove`** to `ForEach`, not to `List`.
</Recap>
