## The simple idea

Asynchronous code performs work that takes time, such as downloading data or querying a database.
In older Swift, testing asynchronous code required expectations and completion handlers.
You had to create an expectation, wait for a callback, and fulfill the expectation before a timeout.

With modern Swift Concurrency, testing asynchronous code is much simpler.
Test functions can be marked with `async throws`.
You can call asynchronous methods directly using `await` and write assertions on the returned results.

<Analogy>
  Think of ordering food at a drive-through window.
  In the old callback approach, you drove away with a buzzer in your pocket.
  You had to stand in the parking lot waiting for the buzzer to vibrate before returning to claim your order.
  With modern async/await, you pull up to the window and wait directly until the attendant hands you the meal.
  You take the bag, check that the food is correct, and drive home immediately.
</Analogy>

### Key tools for async tests

1. **Direct `await`**: Test functions can pause and resume naturally without blocking threads.
2. **Cancellation testing**: You can trigger `task.cancel()` and assert that a `CancellationError` is thrown.
3. **Actor isolation**: You can test actors safely because calling an actor method from a test requires `await`.
4. **Swift Testing `confirmation`**: When testing legacy callbacks or event streams, confirmations verify that events fire expected numbers of times.

## In code

Let us look at testing actor-isolated asynchronous methods and testing cooperative task cancellation in Swift.

<CodeExample title="Testing an asynchronous method directly with await">
```swift
import Foundation

actor UserClient {
    func fetchUser(id: Int) async throws -> String {
        try Task.checkCancellation()
        return "Maria"
    }
}

// In a test method, we await the call directly
let client = UserClient()
let name = try await client.fetchUser(id: 101)
print("Fetched user: \(name)")
```
```output
Fetched user: Maria
```
</CodeExample>

<CodeExample title="Verifying cooperative task cancellation in a test">
```swift
import Foundation

actor SearchService {
    func search(query: String) async throws -> [String] {
        try Task.checkCancellation()
        return ["Result 1", "Result 2"]
    }
}

let service = SearchService()
let task = Task {
    try await service.search(query: "Swift")
}
task.cancel()

do {
    _ = try await task.value
    print("Completed")
} catch is CancellationError {
    print("Caught CancellationError as expected")
} catch {
    print("Other error: \(error)")
}
```
```output
Caught CancellationError as expected
```
</CodeExample>

## Interview traps

<Trap title="Unawaited Detached Tasks in Tests">
  Launching a detached `Task { ... }` inside a test without awaiting its completion is dangerous.
  The test method finishes and reports success before the background task completes or crashes.
  Always await the task value or use structured concurrency inside test methods.
</Trap>

<Trap title="Using Large Timeouts in CI">
  Setting a 60-second timeout on asynchronous expectations causes test suites to hang when something breaks.
  Keep test timeouts short, such as 1 to 2 seconds.
  Fast timeouts give immediate feedback and keep continuous integration pipelines quick.
</Trap>

## How to answer in the interview

<InterviewAnswer level="junior">
  In modern Swift, we write asynchronous unit tests by marking test functions with `async throws`.
  We call async methods directly using `await` and verify the results with standard assertions.
  We avoid using sleeps because sleeps make tests slow and unreliable.
</InterviewAnswer>

<InterviewAnswer level="mid">
  Modern Swift testing leverages native concurrency.
  Both Swift Testing and XCTest allow test functions to be `async throws`, eliminating the need for expectation boilerplate when testing async/await code.
  For legacy callback APIs or streaming events, we use Swift Testing confirmations or `XCTestExpectation`.
  We also write tests for edge cases like cooperative task cancellation by checking that `CancellationError` is thrown properly.
</InterviewAnswer>

<InterviewAnswer level="senior">
  Testing concurrent architectures requires strict determinism.
  I avoid non-deterministic `Task.sleep` delays by injecting custom time clocks or mock schedulers into asynchronous services.
  When testing actors, calls naturally require `await`, enforcing actor isolation at compile time under Swift 6 rules.
  For cancellation testing, we verify that tasks respond promptly to cancellation without leaking resources.
  In large CI pipelines, keeping expectation timeouts tight prevents broken tests from blocking integration queues.
</InterviewAnswer>
