## The simple idea

<Analogy>
Imagine an actor performing on a theater stage.

When the actor stands under the spotlight speaking lines, the actor is **active**.

If a phone rings in the audience and pauses the show, the actor stands frozen on stage.

The actor is still visible, but the show is **inactive**.

When the scene ends, the actor walks backstage. The actor is now in the **background**.

After a few minutes backstage, the actor sits quietly in the dressing room.

The actor uses zero energy while resting. That resting state is **suspended**.

If the theater closes for the night, the actor leaves the building without another curtain call.
</Analogy>

In modern iOS, Apple splits lifecycle management into two separate layers:

1. **The App Process Layer (`UIApplicationDelegate`)**:
   - Manages the single operating system process.
   - Handles app launch options, push notifications, and background task registration.
2. **The Scene Layer (`UISceneDelegate` and SwiftUI `ScenePhase`)**:
   - Manages individual on-screen windows.
   - On iPadOS and macOS, one app process can display multiple scenes side by side.
   - Each scene moves through its own lifecycle independently.

A scene moves through four primary states:

- **Not Running**: The scene is not in memory or has disconnected.
- **Inactive**: The scene is visible on screen but cannot receive touch input (for example, during a phone call banner).
- **Active**: The scene is visible and actively receiving user taps and typing.
- **Background**: The scene is hidden from view.
- **Suspended**: The app stays in memory with zero processor execution until resumed or purged.

## In code

In SwiftUI, you monitor scene changes using the `@Environment(\.scenePhase)` property wrapper.

You inspect whether the scene is `.active`, `.inactive`, or `.background`.

<CodeExample title="Observing ScenePhase in SwiftUI">

```swift
import SwiftUI

let currentPhase = ScenePhase.active
var statusDescription = ""

switch currentPhase {
case .active:
    statusDescription = "Scene is interactive in foreground"
case .inactive:
    statusDescription = "Scene is paused by an interruption"
case .background:
    statusDescription = "Scene is hidden and saving data"
@unknown default:
    statusDescription = "Unknown phase"
}

print("Active phase check: \(currentPhase == .active)")
print("Status: \(statusDescription)")
```

```output
Active phase check: true
Status: Scene is interactive in foreground
```

</CodeExample>

In your SwiftUI view, use `.onChange(of: scenePhase)` to save pending user input whenever the phase becomes `.background`.

Next, see how UIKit represents scene activation states.

The `UIScene.ActivationState` enum indicates whether a window is active, inactive, or in the background.

<CodeExample title="Checking activation states in UIKit">

```swift
import UIKit

let sceneState = UIScene.ActivationState.foregroundActive
let isInteractive = sceneState == .foregroundActive
let isHidden = sceneState == .background

print("Is interactive: \(isInteractive)")
print("Is hidden in background: \(isHidden)")
```

```output
Is interactive: true
Is hidden in background: false
```

</CodeExample>

In UIKit, `UISceneDelegate` methods like `sceneDidEnterBackground(_:)` provide the exact point to flush unsaved changes to disk.

## Interview traps

<Trap title="Relying on applicationWillTerminate">
Many developers assume `applicationWillTerminate(_:)` is always called before an app exits.

In reality, when an app sits suspended in the background, iOS frees memory by killing the process silently.

`applicationWillTerminate(_:)` never executes in that common scenario.

Always save essential user state when the scene enters the background.
</Trap>

<Trap title="Heavy work during app launch">
Running slow network calls or synchronous database migrations in `didFinishLaunchingWithOptions` blocks the main thread.

iOS uses a watchdog timer that terminates any app that fails to finish launching within about twenty seconds.

Keep app launch fast and dispatch long tasks to background queues.
</Trap>

<Trap title="Confusing Inactive with Background">
An app does not move to the background when an incoming phone call or Face ID alert appears.

It transitions to the Inactive state.

The view is still visible, but touch interaction is temporarily paused.

Do not discard temporary screen state or cancel active connections during brief interruptions.
</Trap>

<Trap title="Storing window state in AppDelegate">
Since iOS 13, iPadOS supports multiple windows for the same application.

If you store window-specific view controllers or navigation paths in `AppDelegate`, windows overwrite each other.

Keep window-specific state inside each individual `SceneDelegate` or SwiftUI `Scene`.
</Trap>

## How to answer in the interview

<InterviewAnswer level="fresh">
"The app lifecycle manages how an app moves between active, inactive, background, and suspended states. Active means the user is tapping and typing. Inactive means it is visible but paused by an alert. Background means it is hidden. I save user data when moving to the background because suspended apps can be killed without warning."
</InterviewAnswer>

<InterviewAnswer level="junior">
"Apple separates process lifecycle in `AppDelegate` from UI scene lifecycle in `SceneDelegate`. This allows iPadOS to support multiple windows for a single process. Scenes transition from unattached to inactive, active, and background. In SwiftUI, we observe these transitions with `@Environment(\.scenePhase)` and persist state when entering `.background`."
</InterviewAnswer>

<InterviewAnswer level="senior">
"We isolate process-level services like push notifications in `UIApplicationDelegate`, while managing multi-window UI state through `UISceneDelegate`. We treat background transitions as our boundary for persisting state and releasing volatile caches. We also keep launch routines asynchronous to avoid watchdog timer crashes. In SwiftUI, observing `ScenePhase` at the App level allows coordinated multi-scene persistence."
</InterviewAnswer>

## Recap

<Recap>
- `UIApplicationDelegate` manages the process; `UISceneDelegate` manages individual windows.
- Inactive means the scene is visible on screen but paused from user touch input.
- Active means the scene is in the foreground and responding to interactions.
- Background means the scene is hidden; iOS gives a brief window to save data.
- Suspended apps sit in RAM with zero CPU usage and can be killed silently without notice.
- Never rely on `applicationWillTerminate` to save critical user data.
- In SwiftUI, observe `@Environment(\.scenePhase)` to handle state changes cleanly.
</Recap>
