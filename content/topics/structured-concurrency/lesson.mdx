## The simple idea

In earlier iOS code, starting asynchronous work was like sending a letter. You launched a closure on a background queue, but your function returned immediately. The background work floated on its own.

Structured concurrency changes this model. Work runs in a clear tree of parent and child tasks.

<Analogy>
  Think of a company project. The project lead assigns three tasks to team members. The project cannot finish until all team members finish their work. If the client cancels the project, the lead cancels all team tasks at once.
</Analogy>

In structured concurrency, every child task has a parent. A parent task cannot complete until all its child tasks have finished.

Structured concurrency gives you two critical features:

1. **Automatic lifetime control**: When a scope exits, Swift makes sure all child tasks finish or cancel. No background task is left running by mistake.
2. **Automatic cancellation propagation**: When a parent task cancels, cancellation signals flow down to every child task in the tree.

Swift provides two ways to build structured concurrency:

- `async let`: Spawns a fixed number of child tasks concurrently in the current scope.
- `withTaskGroup`: Spawns a dynamic number of child tasks using a loop.

## In code

Use `async let` when you know the exact number of concurrent operations at compile time.

```swift
func fetchUser() async -> String {
    return "Alex"
}

func fetchScore() async -> Int {
    return 95
}

func loadDashboard() async {
    async let user = fetchUser()
    async let score = fetchScore()
    let result = await "\(user) scored \(score)"
    print(result)
}

await loadDashboard()
```
```output
Alex scored 95
```

Both `fetchUser()` and `fetchScore()` run at the same time. The parent task awaits their results before continuing.

When you need to run an unknown number of concurrent tasks, use `withTaskGroup`.

```swift
func loadNumbers() async -> [Int] {
    await withTaskGroup(of: Int.self) { group in
        for i in 1...3 {
            group.addTask {
                return i * 10
            }
        }
        var numbers: [Int] = []
        for await value in group {
            numbers.append(value)
        }
        return numbers.sorted()
    }
}

let values = await loadNumbers()
print("Numbers: \(values)")
```
```output
Numbers: [10, 20, 30]
```

`withTaskGroup` suspends until all child tasks finish. The closure returns the combined result cleanly.

## Interview traps

<Trap label="Task { } is not structured concurrency">
  Writing `Task { }` creates an unstructured task. Its lifetime is not bound to the surrounding function. If the function returns, the task continues running in the background. To keep work structured, use `async let` or `withTaskGroup`.
</Trap>

<Trap label="Cancellation is cooperative">
  Cancelling a task group does not stop child tasks by force. Child tasks must check `Task.isCancelled` or call `Task.checkCancellation()` to stop their own loops. Without these checks, child tasks keep consuming CPU cycles.
</Trap>

## How to answer in the interview

<InterviewAnswer level="mid">
  Structured concurrency organizes asynchronous work into parent and child relationships. A parent cannot finish until all its child tasks complete. Swift provides `async let` for a fixed number of concurrent calls and `withTaskGroup` for dynamic loops. If a parent cancels or throws, cancellation propagates down to all child tasks automatically.
</InterviewAnswer>

<InterviewAnswer level="senior">
  I design concurrent systems using structured task hierarchies to avoid orphaned work and resource leaks. Child tasks inherit priority and actor isolation from their parent, which prevents priority inversions. In task groups, I prefer `group.addTaskUnlessCancelled` to avoid scheduling work into cancelled scopes. When building producer-consumer streams, I use discarding task groups to prevent memory accumulation from completed child tasks.
</InterviewAnswer>

## Recap

<Recap>
  Structured concurrency links child tasks to their parent scope. Parents wait for child tasks before returning. Use `async let` for fixed parallel calls and `withTaskGroup` for dynamic collections. Remember that `Task { }` is unstructured, and cancellation requires cooperative checks inside child task code.
</Recap>
