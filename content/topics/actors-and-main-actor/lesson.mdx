## The simple idea

When multiple threads read and write the same memory simultaneously, you get a data race. Data races cause memory corruption and random crashes.

An `actor` solves this problem. Like a class, an actor is a reference type. But unlike a class, an actor protects its mutable state.

<Analogy>
  Think of a single bank teller window. Only one customer can stand at the counter and speak to the teller at a time. Other customers wait patiently in line. When your turn arrives, you step up and complete your transaction.
</Analogy>

Only one task can access an actor's mutable properties at any given moment.

When calling an actor method from outside, you must write `await`. This is known as actor-hopping. Your task pauses if another task is currently using the actor.

If a property is an immutable `let` constant, you can mark it `nonisolated`. Callers can then read that constant synchronously without writing `await`.

For user interfaces, Apple provides `@MainActor`. `@MainActor` is a global actor that runs all its code on the main thread.

## In code

Here is an example of an actor protecting a bank balance. It also exposes a `nonisolated` property.

```swift
actor BankAccount {
    let accountNumber: String
    private(set) var balance: Int

    init(accountNumber: String, balance: Int) {
        self.accountNumber = accountNumber
        self.balance = balance
    }

    func deposit(amount: Int) {
        balance += amount
    }

    nonisolated var accountID: String {
        "ACC-\(accountNumber)"
    }
}

func testAccount() async {
    let account = BankAccount(accountNumber: "123", balance: 100)
    print("ID: \(account.accountID)")
    await account.deposit(amount: 50)
    print("Balance: \(await account.balance)")
}

await testAccount()
```
```output
ID: ACC-123
Balance: 150
```

Notice that reading `accountID` does not require `await` because it is `nonisolated`. Mutating `balance` requires `await` to hop onto the actor.

Next, here is how you use `@MainActor` to isolate a view model to the main thread.

```swift
@MainActor
final class ProfileViewModel {
    var username = "Guest"

    func update(name: String) {
        username = name
        print("Updated to \(username) on main thread")
    }
}

func run() async {
    let model = ProfileViewModel()
    await model.update(name: "Taylor")
}

await run()
```
```output
Updated to Taylor on main thread
```

Calling `update(name:)` from an outside task automatically hops to the main thread.

## Interview traps

<Trap label="Beware of actor reentrancy bugs">
  When an actor method suspends at an `await` call, other tasks can run on that actor. If your method assumes state remains unchanged across an `await`, bugs occur. Always re-check state assumptions after returning from an `await`.
</Trap>

<Trap label="Do not mark background workers with @MainActor">
  Applying `@MainActor` to heavy image processors or database decoders forces that work onto the main thread. This causes UI stutters and dropped frames. Only use `@MainActor` for UI updates, view models, and views.
</Trap>

## How to answer in the interview

<InterviewAnswer level="mid">
  An actor is a reference type that protects its mutable state by ensuring only one task executes on it at a time. Callers from the outside must write `await` to hop onto the actor. For immutable constants, I use `nonisolated` so callers can read them synchronously. For UI code, I apply `@MainActor` to ensure view models and state mutations run safely on the main thread.
</InterviewAnswer>

<InterviewAnswer level="senior">
  I design actors to eliminate data races without manual lock management. I design around actor reentrancy by validating state invariants before and after every `await` suspension point. In Swift 6, data passed across actor boundaries must conform to `Sendable` to guarantee thread safety at compile time. When writing view models, I annotate classes with `@MainActor` to prevent race conditions during UI state updates.
</InterviewAnswer>

## Recap

<Recap>
  Actors are reference types that protect mutable state through mutual exclusion. External callers use await to hop onto the actor. Use nonisolated for immutable reads and synchronous protocol conformances. Use @MainActor to tie UI code and view models to the main thread. Watch out for actor reentrancy across suspension points.
</Recap>
