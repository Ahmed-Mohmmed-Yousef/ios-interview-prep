## The simple idea

<Analogy>
Imagine a multi-tool pocket knife with interchangeable attachments.

Each attachment has one clear purpose: a screwdriver turns screws, and a bottle opener removes caps.
The knife does not try to be an entire kitchen sink.
This represents the **Single Responsibility Principle**.

When you want to add a mini flashlight attachment, you snap it into the slot.
You do not need to cut the knife handle in half to add a tool.
This represents the **Open/Closed Principle**.

Every screwdriver bit fits the standardized magnetic socket securely without wobbling or breaking.
Any valid bit can substitute for another bit safely.
This represents the **Liskov Substitution Principle**.

You buy only the tool bits you actually need for your camping trip.
You are not forced to carry heavy wrench attachments you will never touch.
This represents the **Interface Segregation Principle**.

Finally, the knife handle connects to standardized tool sockets, not one specific steel blade brand.
Both handle and attachments depend on the common socket specification.
This represents the **Dependency Inversion Principle**.
</Analogy>

The five SOLID principles help developers write clean, maintainable iOS apps:

1. **S — Single Responsibility Principle**: A class or struct should have only one reason to change.
2. **O — Open/Closed Principle**: Open for extension, but closed for modification. Add new features with new types instead of editing old code.
3. **L — Liskov Substitution Principle**: Subclasses or conforming types must work properly anywhere the parent type is expected.
4. **I — Interface Segregation Principle**: Prefer many small, focused protocols over one massive protocol with unused methods.
5. **D — Dependency Inversion Principle**: Depend on abstractions like protocols rather than concrete classes. This makes unit testing fast and easy.

## In code

Here is the **Open/Closed Principle** in action.
Instead of modifying a `switch` statement every time a payment method is added, define a `PaymentMethod` protocol.
Adding Apple Pay requires writing a new struct, not editing existing code.

<CodeExample title="Open/Closed Principle using protocols">

```swift
import Foundation

protocol PaymentMethod {
    func pay(amount: Int) -> String
}

struct CreditCardPayment: PaymentMethod {
    func pay(amount: Int) -> String {
        return "Paid $\(amount) with Card"
    }
}

struct ApplePayPayment: PaymentMethod {
    func pay(amount: Int) -> String {
        return "Paid $\(amount) with Apple Pay"
    }
}

final class CheckoutService {
    func checkout(amount: Int, method: PaymentMethod) -> String {
        return method.pay(amount: amount)
    }
}

let checkout = CheckoutService()
let card = CreditCardPayment()
let applePay = ApplePayPayment()

print(checkout.checkout(amount: 50, method: card))
print(checkout.checkout(amount: 90, method: applePay))
```

```output
Paid $50 with Card
Paid $90 with Apple Pay
```

</CodeExample>

Now look at the **Dependency Inversion Principle**.
The `ProfileViewModel` depends on a `UserLoader` protocol.
During testing, pass a `MockUserLoader` to verify output in milliseconds.

<CodeExample title="Dependency Inversion Principle with protocol injection">

```swift
import Foundation

protocol UserLoader {
    func loadUserName() -> String
}

final class MockUserLoader: UserLoader {
    func loadUserName() -> String {
        return "Jordan"
    }
}

final class ProfileViewModel {
    private let loader: UserLoader

    init(loader: UserLoader) {
        self.loader = loader
    }

    func welcomeMessage() -> String {
        return "Welcome, \(loader.loadUserName())!"
    }
}

let viewModel = ProfileViewModel(loader: MockUserLoader())
print(viewModel.welcomeMessage())
```

```output
Welcome, Jordan!
```

</CodeExample>

## Interview traps

<Trap title="Confusing Dependency Inversion with Dependency Injection">
Dependency Inversion is the architectural principle: depend on abstractions, not concrete types.
Dependency Injection is the technique: passing dependencies into initializers or properties.
Dependency Injection is one tool used to achieve Dependency Inversion.
</Trap>

<Trap title="Creating single-method classes everywhere">
The Single Responsibility Principle means a class has one reason to change, not one single method.
A class can contain multiple related methods as long as they serve the same cohesive purpose.
Over-splitting creates confusing code with too many tiny files.
</Trap>

<Trap title="Protocol explosion with Interface Segregation">
Interface Segregation advises small, focused protocols.
However, creating a separate protocol for every single function creates unnecessary boilerplate.
Group related methods that clients naturally use together.
</Trap>

<Trap title="Subclassing with fatalError">
Creating a `ReadOnlyDocument` that subclasses `Document` and throws `fatalError` inside `save()` breaks Liskov Substitution.
Callers expecting a `Document` will crash.
Use composition and protocols instead of invalid inheritance.
</Trap>

## How to answer in the interview

<InterviewAnswer level="fresh">
SOLID represents five rules for writing clean software.
Single Responsibility means each class has one job.
Open/Closed means adding new features with new code instead of modifying old code.
Liskov Substitution means subclasses must not break when replacing parent classes.
Interface Segregation means writing small protocols.
Dependency Inversion means depending on protocols so we can easily inject mocks in unit tests.
</InterviewAnswer>

Open/Closed uses protocols so we can add new payment types without editing big switch statements.
Liskov Substitution avoids brittle subclassing where overrides crash or break parent contracts.
Interface Segregation creates small, composable Swift protocols.
Dependency Inversion uses protocol abstractions and initializer injection, letting us swap live services with test mocks.
</InterviewAnswer>

<InterviewAnswer level="senior">

Single Responsibility establishes clean domain boundaries between views, state, and services.
Open/Closed and Interface Segregation align naturally with Swift protocol composition and extension defaults.
Liskov Substitution reminds us that inheritance is often fragile; we prefer value types and composition over inheritance.
Dependency Inversion decouples high-level business logic from framework details like URLSession or SwiftData.

</InterviewAnswer>

## Recap

<Recap>
- **S (Single Responsibility)**: Give each class one clear reason to change.
- **O (Open/Closed)**: Add new capabilities by creating new types conforming to protocols.
- **L (Liskov Substitution)**: Subclasses must fulfill parent contracts without unexpected errors.
- **I (Interface Segregation)**: Keep protocols small and focused; compose them when needed.
- **D (Dependency Inversion)**: Depend on protocol abstractions and inject dependencies for testing.
</Recap>
