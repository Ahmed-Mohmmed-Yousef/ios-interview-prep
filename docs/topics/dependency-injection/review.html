The simple idea

In software design, an object often relies on helper objects to do its job. For example, a view model might need a network client to download user data. If the view model creates the network client internally, the two classes become tightly coupled.

Dependency Injection (DI) means passing needed helper objects in from the outside instead of creating them internally. The object receives what it needs to work.

Think of it like this

Think of an electric car. The car needs a charging cable to receive electricity. If the manufacturer solders a specific wall plug directly into the car engine, you can never change charging stations. Instead, the car provides an external charging socket. You can plug in a home wall charger, a public fast charger, or a portable test battery. The car does not care who supplies the power as long as the cable fits the socket.

Why inject dependencies?

  1. Testability: You can inject mock objects or stubs during unit tests without making real network requests.
  2. Loose coupling: Your class depends on an abstract protocol instead of a concrete type.
  3. Flexibility: You can swap implementations for previews, tests, or different app environments.

Interview traps

Trap Hardcoding Singletons

Calling URLSession.shared or UserDefaults.standard directly inside business logic makes classes impossible to test in isolation. Instead of referencing global singletons directly, wrap them in protocols or inject URLSession instances through initializers.

Trap The Service Locator Anti-Pattern

Using a global dictionary or service locator conceals class dependencies from the compiler. Callers cannot see what an object requires until runtime crashes occur. Always prefer explicit initializer injection so dependencies are visible at compile time.

How to answer in the interview

Junior answer

Dependency injection means passing helper objects into a class instead of creating them inside that class. In Swift, we usually pass dependencies through initializers. This makes our code flexible because unit tests can pass mock objects instead of real network services.

Mid answer

Dependency injection implements Inversion of Control by supplying collaborators from the outside. We prefer initializer injection because it allows dependencies to be stored as immutable let constants and avoids invalid state. By programming to protocols rather than concrete classes, we can swap production network clients with fast stubs in automated tests. In SwiftUI, we also use the environment system to pass shared dependencies down the view hierarchy.

Senior answer

In production iOS architecture, dependency injection is essential for modularity, parallel builds, and test isolation. I advocate for pure initializer injection backed by protocol abstractions over complex third-party runtime containers. Pure DI keeps dependency graphs explicit and verified at compile time. When building modular frameworks, we define domain protocols in feature interfaces and inject concrete implementations at the app composition root.

Recap

  • Dependency Injection supplies collaborator objects from outside a class instead of creating them inside.
  • Initializer injection is the preferred approach in Swift because it supports constant properties and compile-time safety.
  • Programming to protocols allows unit tests to inject mock objects without triggering real network or disk operations.
  • Avoid hardcoded singletons and service locators that hide class dependencies.
  • SwiftUI provides @Environment for injecting dependencies down the view hierarchy.
