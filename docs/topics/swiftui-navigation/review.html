The simple idea

Mobile apps often organize screens in layers. You start at a home screen, tap an item to push a detail screen, and tap back to return.

In SwiftUI, NavigationStack holds your root view:

  1. The Navigation Stack:
    • NavigationStack manages a stack of screens.
    • When a user taps a navigation link, SwiftUI pushes a new screen on top.
    • When the user taps Back or swipes from the left edge, SwiftUI pops the top screen off.
  2. Data-Driven Navigation:
    • Modern SwiftUI uses data values to drive navigation.
    • NavigationLink(value:) sends a Hashable data value to the stack.
    • .navigationDestination(for:destination:) defines which view to show for that data type.
    • Inside NavigationStack, attach .navigationTitle(_:) and .navigationBarTitleDisplayMode(_:) (.inline or .large) to the child view, not the stack itself.
  3. Lazy Creation:
    • Destination views are created only when the user taps a row.
    • This avoids loading dozens of detail screens into memory before the user visits them.

Think of it like this

Think of a stack of cafeteria trays.

The bottom tray is your home screen. When you tap an item, you place a new tray on top, and you only see the top tray.

When you finish, you lift off the top tray to reveal the screen below.

In code

Here is a NavigationStack using NavigationLink(value:) and .navigationDestination(for:).

You can control navigation in code by binding a NavigationPath (or a typed array) to NavigationStack(path: $path):

  • Push a screen: Call path.append(value) to push a matching destination onto the stack.
  • Pop one screen: Call path.removeLast() to remove the top screen from path.
  • Pop to root: Call path.removeLast(path.count) or assign path = NavigationPath() to clear all pushed screens.
  • Check depth: Use path.count (starts at 0) and path.isEmpty (true when at the root screen).
  • NavigationPath vs a typed array like [Route]: A typed array like [Route] holds one single (homogeneous) type. NavigationPath is type-erased, so it can store mixed (heterogeneous) Hashable types such as String, Int, and custom structs in the same stack. If every item in NavigationPath also conforms to Codable, path.codable lets you save and restore the path.

Quick check (not scored)

How do you pop all screens back to the root view in code?

Resetting the bound NavigationPath to an empty path removes all stacked screens and reveals the root.

Interview traps

Trap Using deprecated NavigationView

NavigationView was deprecated in iOS 16 because it had navigation bugs and eager view creation.

In modern SwiftUI interviews, use NavigationStack for single-column flows or NavigationSplitView for multi-column layouts (sidebar, content, and detail columns) on iPad and Mac.

Trap Loading views early with NavigationLink(destination:)

Passing a view directly into NavigationLink(destination: DetailView()) creates DetailView structs immediately for every row in your list.

Always use NavigationLink(value:) with .navigationDestination(for:) so destination screens are created lazily only when tapped.

Trap Placing .navigationTitle on NavigationStack

Attaching .navigationTitle("Home") directly to NavigationStack does not show a title.

Always attach .navigationTitle() and .navigationBarTitleDisplayMode() to the child view inside the stack.

Trap Missing Hashable conformance on values

NavigationLink(value:) requires data values to conform to Hashable.

If your custom struct or enum does not conform to Hashable, the Swift compiler reports an error.

Trap Nesting NavigationStack inside another NavigationStack

Never put a NavigationStack inside another NavigationStack.

Nested stacks create duplicate navigation bars and broken back gestures. Keep one NavigationStack at the root of each navigation flow.

How to answer in the interview

Fresh answer

"In SwiftUI, we use NavigationStack to move between screens in layers. We wrap the root view in NavigationStack, use NavigationLink(value:) to send a Hashable item, and resolve the destination screen lazily with .navigationDestination(for:). We attach .navigationTitle to the child view inside the stack."

Junior answer

"Apple introduced NavigationStack in iOS 16 to replace NavigationView. It separates data values from destination views so screens load lazily when tapped. By binding a NavigationPath with NavigationStack(path: $path), we can push with append, pop with removeLast, support deep links, and pop to root cleanly."

Senior answer

"NavigationStack gives us data-driven navigation instead of tying views directly to links. Separating routes from destination views avoids eager view creation in large lists. For single-type stacks, a typed [Route] array works cleanly, while NavigationPath handles mixed Hashable types and supports saving state via path.codable when elements are Codable."

Recap

  • Use NavigationStack to manage a stack of screens, and NavigationSplitView for multi-column iPad layouts.
  • Pair NavigationLink(value:) with .navigationDestination(for:) for lazy screen creation.
  • Bind a NavigationPath (or typed [Route] array) to push, pop with removeLast(), or reset to root.
  • Always attach .navigationTitle() and .navigationBarTitleDisplayMode() to the child view inside the stack.
  • Values passed to NavigationLink(value:) must conform to Hashable, and never nest a NavigationStack inside another.
