Retain Cycles

Interview question

Why does storing a closure that accesses self often cause a memory leak in Swift?

Your guess first (not scored). We come back to it in the recap.

The simple idea

Think of it like this

Imagine two rock climbers holding onto each other with safety ropes.

Climber A holds the rope of Climber B. Climber B holds the rope of Climber A.

Both climbers want to leave the cliff, but each climber refuses to let go first.

Neither climber can ever go home.

To free them, at least one climber must use a loose slip knot that releases when pulled.

A retain cycle happens when two or more objects hold strong references to each other.

Because each object keeps the other alive, the strong reference count for both never reaches zero.

ARC can never free their memory. This causes a memory leak.

  1. Common cause: Stored closures:
    • A class property holds a closure strongly.
    • The closure references self inside its body.
    • The closure captures self strongly by default.
    • Both hold each other forever.
  2. Common cause: Delegates:
    • A parent view controller owns a helper service strongly.
    • The helper service holds the view controller strongly through its delegate.
    • Neither object can deallocate when the user leaves the screen.
  3. The fix: Break the cycle:
    • Use [weak self] in closures.
    • Declare delegate properties as weak var delegate: CustomDelegate?.
    • Weak references do not keep objects alive, allowing the count to reach zero.

Do standard non-escaping closures like Array.forEach cause retain cycles?

Non-escaping closures do not outlive the function call, so they do not hold references after returning.

Interview traps

Trap Assuming non-escaping closures need weak self

Candidates often write [weak self] inside map, filter, or forEach.

Non-escaping closures execute synchronously on the current stack frame.

They do not outlive the method call and do not store self. Writing [weak self] there adds unnecessary clutter.

Trap Accessing self.property without a capture list

Some developers believe writing self.name instead of self avoids capturing self.

In Swift, accessing any member property inside a closure still captures the entire instance of self strongly.

You must still use [weak self] in the capture list to prevent the cycle.

Trap Using unowned self for network callbacks

Using [unowned self] in asynchronous network handlers is dangerous.

If the user dismisses the screen while the network request is in flight, self is deallocated.

When the callback returns and tries to access self, your app crashes. Prefer [weak self].

Trap Forgetting AnyObject on delegate protocols

If a delegate protocol does not inherit from AnyObject, you cannot mark the delegate property weak.

The Swift compiler reports an error because only class types can be weak references.

Always write protocol CustomDelegate: AnyObject.

How to answer in the interview

Fresh answer

"A retain cycle happens when two objects hold strong references to each other. Because neither reference count can drop to zero, both objects leak in memory. Common examples are delegates and closures that capture self. We fix retain cycles by making one reference weak."

Junior answer

"Retain cycles occur when a class owns a closure or child object that holds a strong reference back to the owner. In closures, I break cycles by adding [weak self] to the capture list and unwrapping with guard let self. For delegates, I constrain the protocol to AnyObject and mark the delegate property weak."

Senior answer

"I diagnose retain cycles in production apps using the Xcode Memory Graph Debugger and Instruments Leaks profiling. I also add unit tests asserting that weak references to dismissed view controllers become nil. When designing asynchronous APIs, I choose weak self over unowned self because network or background timing cannot guarantee that the UI hierarchy remains alive."

Recap

  • A retain cycle prevents reference counts from reaching zero, leaking memory.
  • Stored closures capturing self strongly create retain cycles.
  • Break closure cycles by adding [weak self] in the capture list.
  • Break delegate cycles by declaring weak var delegate: CustomDelegate?.
  • Non-escaping closures like map or forEach do not cause retain cycles.
  • Accessing any property of self captures the entire instance strongly.
