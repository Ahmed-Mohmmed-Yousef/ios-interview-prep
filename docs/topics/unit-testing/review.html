The simple idea

Think of it like this

Imagine a watchmaker assembling an expensive mechanical wristwatch.

The watch contains tiny gears, springs, and levers. If the watchmaker builds the entire watch and closes the steel casing, finding a broken gear is frustrating. The watchmaker would have to take the entire watch apart to locate the flaw.

Instead, the watchmaker tests each individual brass gear on a testing rig before assembly. The watchmaker checks teeth dimensions and spins each gear independently. If a gear wobbles, the watchmaker fixes it immediately. Testing individual parts before assembling the full machine is the exact purpose of unit testing.

In iOS development, unit tests check small, isolated units of code, like functions, models, and view models. Good unit tests follow the AAA pattern:

  1. Arrange: Set up test data, input parameters, and mock objects.
  2. Act: Call the function or method you want to test.
  3. Assert: Verify that the actual result matches your expected output.

Apple provides two testing frameworks:

  • XCTest: The traditional framework. Tests inherit from XCTestCase, methods begin with test, and use assertions like XCTAssertEqual.
  • Swift Testing: The modern pure-Swift framework. Uses the @Test and @Suite macros, runs tests in parallel, and checks values with #expect.

Quick check (not scored)

When should you use try #require instead of #expect in Swift Testing?

try #require halts the test immediately if the value is nil or false, preventing crashes on subsequent lines.

Interview traps

Trap Using #expect when unwrapping optionals

In Swift Testing, #expect records a failure but continues executing. If you check an optional with #expect(user != nil) and then force-unwrap user!, the test crashes at runtime. Always use let user = try #require(optionalUser) to halt safely when unwrapping fails.

Trap Sharing mutable global state between tests

Swift Testing runs test functions concurrently in parallel by default. If multiple tests read and write to a shared singleton, race conditions occur. Tests will fail intermittently. Always use local state or inject fresh instances for each test.

Trap Testing implementation details instead of behavior

Asserting on private variable states makes tests brittle. When you refactor internal code, tests break even though user behavior remains correct. Test public inputs and outputs rather than private implementation details.

Trap Writing slow integration tests as unit tests

Calling real disk files, live network endpoints, or hardware sensors belongs in integration tests. Unit tests should execute in memory in milliseconds. Decouple dependencies with protocols and inject mocks.

How to answer in the interview

Fresh answer

Unit tests verify that functions and models work correctly in isolation. We follow the Arrange-Act-Assert pattern: set up data, run the method, and assert results. Apple provides XCTest and the new Swift Testing framework. XCTest uses classes with test method prefixes. Swift Testing uses @Test and @Suite macros with #expect. Tests must run fast in memory and never touch live network endpoints.

Junior answer

I write unit tests using the Arrange-Act-Assert pattern to verify business logic. In legacy code, I use XCTest with XCTestCase and XCTAssertEqual. In modern Swift code, I use Swift Testing with @Test and @Suite. Swift Testing lets us use structs instead of classes and runs tests in parallel. I use #expect for regular assertions and try #require when unwrapping optionals that must halt on failure. I decouple external systems with protocols so I can inject fast in-memory mocks.

Senior answer

Unit testability is an architectural requirement. I apply the Dependency Inversion Principle to isolate view models and business engines from UIKit, Core Data, and URLSession. With Swift Testing in Swift 6, tests execute concurrently across actors by default, enforcing thread safety and exposing singleton leaks. I use parameterized testing with @Test(arguments:) to test edge cases declaratively. We maintain test suites that run in seconds, enabling continuous integration pipelines to catch regressions on every pull request.

Recap

  • Unit tests verify isolated units of code like functions, models, and view models.
  • Follow the Arrange-Act-Assert (AAA) pattern for clear, readable tests.
  • XCTest uses class inheritance, test function prefixes, and XCTAssert methods.
  • Swift Testing uses modern @Test and @Suite macros with pure Swift syntax.
  • Use #expect for continuing checks and try #require to halt on fatal unwrap failures.
  • Decouple networking and storage using protocols to inject fast in-memory mocks.
