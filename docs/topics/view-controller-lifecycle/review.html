Why should you avoid refreshing user data inside viewDidLoad when returning to an existing screen?

The simple idea

Think of it like this

Imagine an actor preparing for a theater performance.

Building the stage set happens once during morning rehearsal. That is viewDidLoad.

Right before the curtains rise, the actor checks their costume. That is viewWillAppear.

When the curtains open and the audience watches, the actor speaks. That is viewDidAppear.

When the scene ends and curtains close, the actor exits. That is viewWillDisappear and viewDidDisappear.

In UIKit, every screen is driven by a UIViewController.

The system calls specific lifecycle methods as a screen loads, appears, disappears, and leaves memory.

Knowing when each method runs helps you place code in the right location:

  1. viewDidLoad:
    • Runs once when the view hierarchy is loaded into memory.
    • Ideal for adding subviews, setting constraints, and configuring delegates.
  2. viewWillAppear & viewDidAppear:
    • Run every time the screen is about to become visible, and after it appears.
    • Ideal for refreshing data, starting animations, and tracking analytics.
  3. viewWillLayoutSubviews & viewDidLayoutSubviews:
    • Run whenever subview frames are calculated or bounds change.
    • Subview dimensions and safe area insets are final here.
  4. viewWillDisappear & viewDidDisappear:
    • Run when the screen is dismissed or covered.
    • Ideal for dismissing keyboards, pausing timers, and saving drafts.

Interview traps

Trap Refreshing data only in viewDidLoad

If you load profile data only in viewDidLoad, navigating away and returning leaves old data.

viewDidLoad does not run again when popping back from a child screen.

Move data refresh tasks to viewWillAppear so the screen updates on every visit.

Trap Adding subviews repeatedly in viewWillAppear

Calling view.addSubview inside viewWillAppear creates duplicate views on every screen visit.

This wastes memory and degrades rendering performance.

Add subviews once inside viewDidLoad.

Trap Setting corner radii before layout runs

Do not use button.bounds.height / 2 inside viewDidLoad.

At that moment, view frames are zero or placeholder values.

Update geometry-dependent corner radii or gradient layer frames in viewDidLayoutSubviews.

Trap Forgetting to call super in lifecycle methods

Failing to call super.viewWillAppear(animated) breaks UIKit internal state management.

Accessibility announcements and navigation animations may fail.

Always call super inside lifecycle overrides, except when overriding loadView.

How to answer in the interview

Fresh answer

"The lifecycle starts with viewDidLoad, which runs once when views load into memory. viewWillAppear runs every time the screen is about to appear, and viewDidAppear runs when visible. When leaving, viewWillDisappear and viewDidDisappear run. Always call super in these methods."

Junior answer

"We place one-time setup like adding subviews and Auto Layout constraints in viewDidLoad. We place repeatable tasks like data reloading and keyboard observers in viewWillAppear. For tasks requiring final view geometry, such as gradients or round corner radii, we use viewDidLayoutSubviews. We tear down timers and hide keyboards in viewWillDisappear."

Senior answer

"We manage screen transitions cleanly by respecting the runloop and presentation context. We separate configuration from layout passes, letting Auto Layout solve constraints before touching layer geometries in viewDidLayoutSubviews. We also consider presentation styles, since modal sheets do not trigger disappearance on presenting controllers in iOS 13 and later."

Recap

  • viewDidLoad runs once per view hierarchy lifetime for one-time setup.
  • viewWillAppear runs every time the view is about to appear on screen.
  • viewDidAppear runs after transition animations finish; start analytics and timers here.
  • viewDidLayoutSubviews runs when bounds update; subview frames are final here.
  • viewWillDisappear runs when leaving; dismiss keyboards and pause video playback here.
  • Always call super in lifecycle overrides to maintain UIKit system transitions.
