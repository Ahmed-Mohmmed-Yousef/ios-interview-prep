Interview question

How does the @Observable macro improve SwiftUI view rendering compared to ObservableObject?

Your guess first (not scored). We come back to it in the recap.

The simple idea

Think of it like this

Imagine a restaurant kitchen order board.

Two chefs work together. One chef makes soup and the other chef makes salad.

If the soup chef receives an alert every time a salad order changes, the soup chef wastes time.

With ObservableObject, changing any property caused every observing view to redraw.

With @Observable, each chef only gets alerts for their own orders.

In iOS 17, Apple introduced the Observation framework.

You mark a model class with the @Observable macro.

SwiftUI tracks which properties each view reads inside its body.

  1. Property-level tracking:
    • A view only redraws when a property that it actually accessed changes.
    • Other properties in the same class can change without causing redraws.
  2. No @Published needed:
    • Stored properties are observable by default.
    • Use @ObservationIgnored on stored properties that should not trigger updates.
  3. Simple view bindings:
    • Store models in a parent view using @State.
    • Pass them to child views as regular properties.
    • Use @Bindable in a child view if you need two-way bindings.

Interview traps

Trap Using @StateObject with @Observable

Do not use @StateObject or @ObservedObject with an @Observable class.

The @Observable macro does not conform to ObservableObject.

Use @State to own the object, or a plain property to pass it down.

Trap Applying @Observable to value types

Do not attach @Observable to a struct.

The @Observable macro only supports classes.

For value types, use standard SwiftUI @Binding or @State values.

Trap Expecting two-way bindings without @Bindable

If a child view receives an @Observable class as a plain parameter, you cannot write $model.name.

Controls like TextField need a binding.

Mark the property with @Bindable in the child view to enable the dollar-sign syntax.

Trap Assuming all views redraw when any property changes

Under ObservableObject, changing any property caused every observing view to redraw.

With @Observable, SwiftUI tracks exact property access.

A view only invalidates when a property that it actually read inside its body changes.

How to answer in the interview

Fresh answer

"The @Observable macro was added in iOS 17. It turns a class into an observable model for SwiftUI views. We store it with @State in the parent view. When any property we display changes, SwiftUI updates the view automatically."

Junior answer

"The @Observable macro tracks properties individually instead of invalidating the whole object like ObservableObject. In views, we own models using @State rather than @StateObject. We use @Bindable when we need two-way bindings in child views, and we read shared data using @Environment(Model.self)."

Senior answer

"The Observation framework replaces Combine-based tracking with compiler-generated observation registrars. It uses runtime tracking to record exactly which properties are read during a view body. This avoids unnecessary body evaluations and reduces view graph diffing. It eliminates the need for @Published and streamlines environment injection without custom keys."

Recap

  • Use the @Observable macro on classes in iOS 17 and later.
  • SwiftUI tracks changes at the property level, so views only redraw when properties they read change.
  • Store model ownership in views using @State private var model = Model().
  • Use @Bindable to create two-way bindings to properties of an @Observable instance.
  • Inject models using .environment(model) and read them using @Environment(Model.self).
  • Mark stored properties that should not trigger updates with @ObservationIgnored.
