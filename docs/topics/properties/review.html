Interview question

Why must a lazy property in Swift always be declared with var instead of let?

Your guess first (not scored). We come back to it in the recap.

The simple idea

Think of it like this

Think of your smartphone. The battery size is a stored value built into the phone. The battery percentage on screen is a computed value calculated when you look at it. A heavy app download is lazy because it only loads the first time you open it. A low battery alert is an observer that runs when the charge level is set.

In Swift, properties attach values to a structure, class, or enumeration.

Swift has three main kinds of instance properties:

  1. Stored properties: Save constants (let) or variables (var) in memory inside an instance. Classes and structs support stored properties, while enums do not.
  2. Computed properties: Do not store a value in memory. Instead, they use a getter (get) and an optional setter (set) to calculate values each time you access them. Classes, structs, and enums all support computed properties.
  3. Lazy stored properties: Wait to calculate their initial value until the first time your code reads them. This saves work when a value is slow to build or might never be needed.

Keep two important rules in mind for stored and lazy properties:

  • let on structs vs classes: On a let struct instance, you cannot change any stored properties, even var ones. On a let class instance, let only locks the reference, so you can still change var stored properties.
  • Lazy properties are not thread-safe: If several threads read an uninitialized lazy var at the same time, Swift does not guarantee it runs only once.

Swift also has type properties (static let or static var) that belong to the type itself, not to any single instance.

Finally, Swift provides property observers on stored properties:

  • willSet: Runs right before a value is stored. It gives you the incoming value as newValue.
  • didSet: Runs right after a value is stored. It gives you the previous value as oldValue.

Quick check (not scored)

Which kind of property calculates its value on demand without allocating memory in the instance?

Computed properties do not allocate storage. They run their getter code every time you read them.

In code

This example shows four core property patterns:

  • Read-only computed property: area calculates width * height on demand and skips get braces. Computed properties must always use var.
  • Getter and setter: fahrenheit defines get and set. When you write temp.fahrenheit = 212.0, Swift gives set an implicit newValue constant.
  • Type property (static let): Document.maxPages belongs to the Document type, not an instance. Stored type properties are initialized lazily on first access and are guaranteed to be thread-safe.
  • Lazy property: content does not run when Document() is created. It runs only when doc.content is read for the first time.

This example shows how property observers work:

  • willSet: Runs right before the new value is stored and gives you newValue.
  • didSet: Runs right after the value is stored and gives you oldValue. Observers run every time the property is set, even if the new value equals the old one.
  • Assigning inside didSet: Setting totalSteps = 500 inside didSet updates the value directly and does not trigger didSet again.
  • Initializers: Property observers do not run when an instance is first created in init.

Quick check (not scored)

Do willSet and didSet observers run when a property is set inside an initializer?

Property observers only run when a property is set on an existing instance, not during init.

Interview traps

Trap Declaring a lazy property with let

A lazy property cannot use let. The compiler stops with an error ('lazy' cannot be used on a let). Because its value is assigned after initialization finishes, a lazy property must always use var.

Trap Declaring a read-only computed property with let

Developers often think a read-only computed property is a constant, so they write let area: Double { ... }. This causes a compile error. Computed properties must always use var because their value is calculated each time and can change.

Trap Expecting observers to fire during initializers

Property observers (willSet and didSet) do not run when a property gets its initial value inside an init method. Swift skips observers during initialization so they never read half-built state.

Trap Adding willSet or didSet to a computed property

You cannot attach willSet or didSet to a computed property you define on a type. A computed property already controls reads and writes through its get and set blocks, so handle changes inside set instead.

How to answer in the interview

Fresh answer

In Swift, stored properties save values in memory for classes and structs, while computed properties calculate values on demand with getters and setters. Lazy properties wait until first access to run their initializer and must always use var. Property observers like willSet and didSet react when a stored property is set, but they do not run during init.

Junior answer

Swift properties separate storage from calculation. Stored properties allocate instance memory, while computed properties run code on demand and can be read-only or read-write with newValue in the setter. Lazy properties delay expensive setup until first access, though they are not thread-safe. By contrast, static stored type properties are lazily initialized once in a thread-safe way. Property observers provide willSet (newValue) and didSet (oldValue) hooks without running during init or looping when you reassign inside didSet.

Recap

  • Stored properties save values in memory on classes and structs; computed properties calculate values on demand on classes, structs, and enums.
  • Read-only computed properties omit get and must still use var; read-write computed properties use get and set (with newValue).
  • lazy var properties compute their value on first access, must use var, and are not thread-safe.
  • static stored type properties belong to the type and initialize lazily once in a thread-safe way.
  • Property observers (willSet and didSet) run when a stored property is set, but not during init and not recursively inside didSet.
