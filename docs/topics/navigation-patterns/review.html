Interview question

What is the main architectural problem with having one view controller instantiate and present the next view controller directly?

Your guess first (not scored). We come back to it in the recap.

The simple idea

In simple mobile apps, a view controller often creates the next screen and pushes it onto the navigation stack. While this works for tiny projects, it tightly couples screens together. The first screen must know the exact type, initializer, and dependencies of the second screen. You cannot easily reuse that first screen in another flow.

Navigation patterns solve this by moving transition logic into dedicated objects.

  1. The Coordinator Pattern: In UIKit or hybrid apps, a Coordinator owns screen navigation. Views report user actions to the Coordinator, which instantiates and presents the next screen.
  2. The Router Pattern: In modern SwiftUI, an observable Router manages a collection of routes bound to a NavigationStack.

Think of it like this

Think of an airport control tower. Pilots flying individual airplanes do not negotiate runway landings directly with each other in the sky. Instead, pilots report their location and intent to the air traffic controller. The controller directs which airplane takes off, which airplane holds, and which runway is cleared. In mobile architecture, views are airplanes, and the Coordinator is the control tower.

Why decouple navigation?

  • Reusability: You can display a profile view from onboarding, settings, or search without modifying the profile view itself.
  • Deep Linking: A central router can parse a push notification URL and build a multi-screen navigation stack programmatically.
  • Testability: You can test whether a user action triggers the correct navigation event without loading UIKit view hierarchies.

Quick check (not scored)

Why must a parent coordinator remove a child coordinator from its child array when the child finishes?

Parents retain child coordinators. If you do not remove finished children, they stay in memory indefinitely, causing a memory leak.

Interview traps

Trap Leaking Child Coordinators

A common bug in Coordinator implementations is failing to clean up child coordinators. When a user taps the standard back button in a navigation bar, the coordinator may not know. Use UINavigationControllerDelegate to intercept pop gestures and remove finished child coordinators.

Trap Hardcoding Concrete Destinations in SwiftUI

Using NavigationLink(destination: DetailView()) eagerly instantiates destination views and couples view layouts. Instead, use NavigationLink(value: route) paired with .navigationDestination(for: Route.self). This enables lazy destination resolution and decoupled routing.

How to answer in the interview

Junior answer

Instead of letting view controllers push each other directly, we use navigation patterns like Coordinators or Routers. A Coordinator handles screen creation and transitions. This keeps our view controllers decoupled and makes screens reusable in different parts of the app.

Mid answer

In UIKit, the Coordinator pattern isolates screen flow from view controllers. View controllers or view models communicate user intent through delegates or closures, and the Coordinator handles presentation. The parent coordinator manages child coordinators in an array to maintain their lifecycles. In modern SwiftUI, we use data-driven navigation with NavigationStack and NavigationPath. An observable router manages a collection of routes, making deep links and programmatic navigation straightforward.

Senior answer

Navigation is a first-class architectural concern. Coupling views directly to navigation destinations impedes modularization and dynamic server-driven flows. In large apps, we define feature boundaries where feature modules expose entry coordinators or route contracts. In modern SwiftUI, state-driven navigation paths allow serialization, state restoration, and universal link routing. We must handle coordinator cleanup carefully, intercepting navigation controller delegate callbacks to avoid memory leaks.

Recap

  • Navigation patterns remove screen transition logic from visual views.
  • The Coordinator pattern uses dedicated flow controllers to instantiate and present view controllers.
  • Parent coordinators must store and clean up child coordinators to prevent memory leaks.
  • Modern SwiftUI uses data-driven NavigationStack with typed routes or NavigationPath.
  • Decoupled navigation enables seamless deep linking, state restoration, and view reusability.
