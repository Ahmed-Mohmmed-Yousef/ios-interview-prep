The simple idea

Think of it like this

Think of a stamp maker at a post office. You give the stamp maker an envelope with a name on it. The stamp maker checks the format and stamps extra lines onto a card. They cannot erase your writing or call outside the office.

A Swift macro generates Swift code for you at compile time so you write less repeated code. Unlike old C macros that paste raw text, Swift macros work on a syntax tree (a structured tree of your code, also called an AST). The compiler checks types before and after macro expansion, so generated code stays type-safe.

Every custom macro lives in a separate compiler plugin target built with SwiftSyntax (the Swift library for reading and building syntax trees). Your macro declaration connects to that plugin with #externalMacro(module:type:). The plugin runs inside a sandbox, so it has no network access and cannot read files on disk. This keeps builds safe and repeatable (deterministic).

Macros are also additive. A macro can add new code or generate a function body, but it cannot delete declarations you already wrote.

Swift splits macros into two groups based on how you write them:

  1. Freestanding macros (#) stand alone and do not attach to a declaration.
    • Expression role (@freestanding(expression)): produces a value, like #Predicate, #fileID, #line, or #function.
    • Declaration role (@freestanding(declaration)): generates new declarations in place, like #Preview.
  2. Attached macros (@) sit right in front of a declaration and expand it.
    • Member role (@attached(member)): adds new properties or methods inside a type or extension.
    • Member attribute role (@attached(memberAttribute)): adds attributes to members already inside a type.
    • Peer role (@attached(peer)): adds new declarations next to the target in the same scope, like an async version of a function.
    • Accessor role (@attached(accessor)): adds get, set, willSet, didSet, or init accessors to a property.
    • Extension role (@attached(extension, conformances: ...)): adds an extension and protocol conformances to a type. This replaced the older conformance role.
    • Body role (@attached(body)): generates or wraps the body of a function or accessor. At most one body macro can sit on a function.

Macro declarations also list name specifiers using names:. Options include named(...), overloaded, prefixed(...), suffixed(...), and arbitrary. These tell the compiler which symbol names the macro can create before running the plugin.

    Quick check (not scored)

    Which macro role adds new declarations next to a function in the same scope, rather than inside a type?

    @attached(peer) creates sibling declarations beside the target declaration in the same scope, such as an async overload next to a completion-handler method.

    In code

    Let us look at built-in macros in Apple frameworks first. @Observable from the Observation framework combines multiple attached roles (member, memberAttribute, and extension) to track property changes without a _property wrapper struct. You can mark a property with @ObservationIgnored to skip tracking. @Observable works only on classes, not on structs.

    Here, #function, #line, and #fileID are freestanding expression macros in the Swift standard library. @Observable expands on Cart to add tracking storage, @ObservationTracked attributes on stored properties, and Observable conformance.

    Next, #Predicate in Foundation is a freestanding expression macro that turns a closure into a type-checked query object.

    New in Xcode 27

    New Xcode app targets isolate code to @MainActor by default. Because #Predicate builds Sendable key paths, mark structs passed to #Predicate with nonisolated (or turn off default main-actor isolation for the target).

    When you declare your own macro, you state its category, role, name specifiers, and #externalMacro(module:type:) implementation. You can inspect what any macro generates in Xcode using Expand Macro in the editor menu.

    Quick check (not scored)

    What happens if you try to put @Observable on a Swift struct instead of a class?

    @Observable requires reference semantics and emits a compile-time error when applied to a struct.

    Interview traps

    Trap Thinking macros can read build config files or call the web

    Macro compiler plugins run in a strict sandbox. They only receive the syntax tree of the macro call and cannot read files on disk, inspect environment variables, or make network calls.

    Trap Using a macro when a protocol extension or generic function is enough

    Every macro target pulls SwiftSyntax into your build graph, which increases clean build times. Reach for generics, protocol extensions, or property wrappers first. Choose macros only when Swift's type system cannot remove the repeated code cleanly.

    Trap Confusing @attached(member) with @attached(memberAttribute)

    @attached(member) adds brand-new declarations inside a type, such as an init. @attached(memberAttribute) attaches attributes like @ObservationTracked to existing declarations inside that type.

    How to answer in the interview

    Senior answer

    Swift macros generate type-checked Swift code at compile time. They transform syntax trees with SwiftSyntax inside a sandboxed compiler plugin. Freestanding macros use # for standalone expressions or declarations. Attached macros use @ with roles like member, memberAttribute, peer, accessor, extension, and body. Unlike property wrappers, macros work across whole types and functions without per-property wrapper storage. You can inspect generated code in Xcode using Expand Macro.

    Staff answer

    At scale, macros remove repeated code like @Observable tracking or mock generation. Sandboxing keeps builds repeatable, and the compiler checks types before and after expansion. However, macros add a SwiftSyntax dependency, lengthen clean compile times, and can hide control flow if teams overuse them. I reserve custom macros for cases where generics or protocol extensions fall short. I also unit-test macro expansions and require clear compiler error messages for bad inputs.

    Recap

    • Swift macros run at compile time in a sandboxed SwiftSyntax plugin and produce additive, type-checked Swift code.
    • Freestanding macros (#) have expression and declaration roles; attached macros (@) use member, memberAttribute, peer, accessor, extension, and body roles.
    • Macro declarations declare symbol names with names: and point to their plugin via #externalMacro(module:type:).
    • Prefer generics, protocol extensions, or property wrappers when they fit, because macros add SwiftSyntax build-time cost.
