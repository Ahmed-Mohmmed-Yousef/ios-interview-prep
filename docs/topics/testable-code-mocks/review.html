The simple idea

Unit tests must be fast, reliable, and isolated. If your code talks to real web servers or disk databases, tests run slowly and fail whenever Wi-Fi drops. To make code testable, we replace real external services with test doubles.

A test double is any helper object you use in place of a real production collaborator during a test.

Think of it like this

Think of a movie stunt double. When an action movie scene requires jumping off a moving train, the director does not risk the lead actor. Instead, the director uses a stunt double who dresses like the actor. The stunt double performs the specific stunt safely. In software testing, test doubles stand in for real network and database systems so your tests run safely and quickly.

The 5 types of test doubles

Martin Fowler categorized test doubles into five distinct types:

  1. Dummy: An object passed to fill a required parameter, but never used in the test.
  2. Stub: An object that provides canned, pre-programmed answers to calls during the test.
  3. Spy: A stub that also records how it was called (such as call counts and arguments).
  4. Mock: An object pre-programmed with expected calls that verifies communication behavior.
  5. Fake: A working implementation that uses a shortcut not suitable for production, such as an in-memory dictionary.

State verification versus behavior verification

  • State verification: You check the final outcome or property value of your class after calling a method.
  • Behavior verification: You check that your class called specific collaborator methods with exact arguments.

Prefer state verification whenever possible. Checking final state makes your tests resilient when internal implementation details change.

Interview traps

Trap The Over-Mocking Anti-Pattern

Mocking every private collaborator couples your tests to exact implementation details. If you rename an internal helper method, your tests break even though the feature works. Only mock external boundaries like network, disk, or device hardware.

Trap Hardcoding Real System Clocks and UUIDs

Calling Date() or UUID() directly inside business logic makes tests non-deterministic. Inject a date provider closure like dateProvider: () -> Date = { Date() }. In tests, pass a fixed date so assertions never fail due to timezone or timing differences.

How to answer in the interview

Junior answer

To write testable code, we use dependency injection and protocols instead of hardcoding services. In unit tests, we pass test doubles like stubs and mocks. A stub returns canned data, while a mock verifies that certain methods were called.

Mid answer

Testable code relies on loose coupling, single responsibility, and protocol abstractions. I use the classic test double taxonomy: Dummies fill parameters, Stubs provide canned data, Spies record method calls, and Fakes provide in-memory implementations. I favor state verification over behavior verification because asserting on final state keeps tests resilient during internal refactoring.

Senior answer

In production iOS architecture, testability directly reflects system design. Over-mocking is a common pitfall that makes test suites brittle. I reserve test doubles for true external boundaries like network clients, persistence stores, and system clocks. For domain logic, I prefer testing pure functions and state transitions. By injecting protocols with sensible defaults, production code stays clean while unit tests run deterministically in milliseconds.

Recap

  • Testable code decouples external dependencies through protocols and initializer injection.
  • Test doubles include Dummies, Stubs, Spies, Mocks, and Fakes.
  • Stubs provide canned responses; Spies record call counts and parameters; Fakes provide working in-memory shortcuts.
  • Prefer state verification over behavior verification to avoid brittle tests.
  • Avoid over-mocking internal collaborators and inject date providers to keep tests deterministic.
