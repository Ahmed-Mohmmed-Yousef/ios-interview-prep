Interview question

Why does calling .padding().background(.blue) look completely different from calling .background(.blue).padding()?

Your guess first (not scored). We come back to it in the recap.

The simple idea

Think of it like this

Imagine wrapping a gift box.

First, you wrap the box in colorful blue paper. Then, you place bubble wrap around the outside of the blue package. The bubble wrap stays clear.

If you reverse the order, you place bubble wrap around the box first. Then you put blue paper over everything. Now the entire outer layer is blue.

In SwiftUI, a view is not a permanent drawing object on the screen.

Instead, a view is a lightweight struct that describes what the screen should look like:

  1. Views are Structs:
    • Every SwiftUI view conforms to the View protocol.
    • The protocol requires a single computed property: var body: some View.
    • Because views are value types on the stack, SwiftUI can create and destroy thousands of them without slowing down the device.
  2. Modifiers Wrap Views:
    • Modifiers do not mutate an existing view.
    • Calling .padding() takes your view and wraps it inside a new padding view.
    • Calling .background(.blue) wraps that view inside a colored background view.
  3. Order Matters:
    • Because each modifier wraps the previous layer, the order of modifiers changes the visual result.
    • Padding before background makes a large colored rectangle.
    • Background before padding makes a small colored rectangle with transparent space around it.
  4. Opaque Return Types (some View):
    • Chaining modifiers creates deeply nested generic types like ModifiedContent<Text, _PaddingLayout>.
    • The keyword some View hides these messy types behind a simple name.

Why are SwiftUI views built as structs instead of classes?

SwiftUI recreates view descriptions constantly. Structs live on the stack and avoid heap allocation overhead.

Interview traps

Trap Believing modifiers mutate views in place

Many developers coming from UIKit assume calling .padding() changes a property on the existing view.

In SwiftUI, views are immutable structs. Modifiers never mutate the original instance.

Each modifier returns a brand new view wrapping the previous one.

Trap Doing heavy work inside var body

SwiftUI evaluates var body repeatedly whenever inputs or state variables change.

Never start network requests, open database connections, or perform heavy algorithms inside var body.

Heavy work inside var body blocks the main thread and causes UI frame drops.

Trap Using classes for SwiftUI views

SwiftUI is designed around value types.

Conforming a class to View breaks SwiftUI state tracking, identity diffing, and performance optimizations.

Always declare SwiftUI views as structs.

Trap Forgetting the #Preview macro syntax

In older SwiftUI code, previews required declaring a PreviewProvider struct with a static previews property.

Modern SwiftUI uses the clean #Preview macro introduced in Swift 5.9.

Interviewers often check if candidates know current modern SwiftUI syntax.

How to answer in the interview

Fresh answer

"A SwiftUI view is a lightweight struct conforming to the View protocol with a body property. Views are descriptions of UI, not persistent objects like UIKit views. Modifiers do not mutate views in place. Instead, each modifier wraps the view in a new container. Because wrapping is hierarchical, modifier order matters. For example, applying padding before background colors the padded area, while applying background first colors only the text."

Junior answer

"SwiftUI uses value types to make view recreation fast and memory efficient. When state changes, SwiftUI rebuilds the view struct hierarchy and computes a diff against the previous view description. Modifiers return ModifiedContent wrappers, which is why modifier order changes layout and rendering. We use some View as an opaque return type so the compiler knows the concrete type without forcing us to write complex generic wrappers."

Senior answer

"Behind the scenes, SwiftUI separates the transient view description from the persistent render graph. Views are pure functions of state. Because views are lightweight stack-allocated structs, recreation is cheap. SwiftUI uses structural identity based on @ViewBuilder generic type trees to identify which subtrees need updates. When building reusable components, custom ViewModifier structs encapsulate layout logic and support view composition without subclassing."

Recap

  • SwiftUI views are lightweight structs conforming to View, not heavy reference classes.
  • The body property returns some View, an opaque type hiding nested generic wrappers.
  • Modifiers do not mutate views; they wrap views into new ModifiedContent structs.
  • Modifier order matters because each modifier wraps the previous view hierarchy.
  • Custom modifiers conform to ViewModifier and can be chained using View extensions.
  • Modern Xcode previews use the #Preview macro instead of PreviewProvider.
