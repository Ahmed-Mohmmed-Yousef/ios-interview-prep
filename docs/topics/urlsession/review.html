The simple idea

Think of it like this

Imagine a delivery courier picking up packages for you.

You hand the courier an address slip. The courier drives to the warehouse, collects your parcel, and returns.

If the road is washed out by a storm, the courier cannot reach the warehouse. That is a transport error.

If the courier reaches the warehouse and the clerk says the item is missing, the trip succeeded.

The courier hands you a formal notice stating "Item 404 Not Found".

You received a valid response from the clerk, even though you did not get your item.

In iOS, URLSession is the core engine for all network communication.

It handles connection pooling, TLS security, caching, and background transfers.

You configure sessions using one of three primary configurations:

  1. Default (.default): Uses persistent disk caching, shared cookies, and Keychain credentials.
  2. Ephemeral (.ephemeral): Stores caches and credentials in RAM only. Data disappears when the session closes.
  3. Background (.background): Delegates transfers to a system daemon. Downloads continue even if iOS suspends your app.

For simple requests, you can use the pre-configured URLSession.shared singleton.

When fetching data with modern Swift, call try await URLSession.shared.data(from: url).

This call returns two items: raw Data bytes and a URLResponse.

You cast the response to HTTPURLResponse to verify the three-digit status code.

Because network requests run on background threads, always dispatch user interface updates to the main thread.

Quick check (not scored)

Why must you call task.resume() when creating a classic dataTask?

Classic URLSession tasks are created in the suspended state. Calling resume starts the network connection.

In code

Check the HTTP status code before decoding JSON data.

Inspect whether the status falls in the successful 200...299 range.

Pick the session configuration that matches your privacy and caching needs.

Use ephemeral sessions when handling sensitive user records in memory only.

Interview traps

Trap Assuming 404 or 500 throws an error

URLSession.shared.data(from: url) does not throw an error for 404 or 500 HTTP responses.

It only throws for transport failures like loss of internet or DNS errors.

Always cast the returned response to HTTPURLResponse and check statusCode.

Trap Forgetting task.resume() in classic code

In completion handler code, session.dataTask(...) returns a suspended task.

If you forget to call task.resume(), the network call never starts.

The application sits waiting forever with no error or output.

Trap Updating UI from background completion queues

URLSession executes callbacks and tasks on background threads.

Modifying UIKit controls or SwiftUI state from background queues causes UI glitches or crashes.

Always dispatch UI mutations to the main actor or main thread.

Trap Using URLSession.shared for background file downloads

URLSession.shared cannot perform out-of-process background downloads.

If the user locks the phone or switches apps, transfers pause or fail.

Use URLSessionConfiguration.background(withIdentifier:) for background file downloads.

How to answer in the interview

Fresh answer

"URLSession is the Foundation class we use to fetch data from web APIs. With modern Swift, we use try await URLSession.shared.data(from: url). We check that the response status code is in the 200 range, and decode the JSON into our Codable model. Because network calls run in the background, we update our UI on the main thread."

Junior answer

"URLSession supports three configurations: default, ephemeral for private in-memory storage, and background for transfers managed by the system daemon. In modern code, we use async/await data(for:), which supports structured cancellation. We differentiate transport errors from HTTP status errors by checking HTTPURLResponse.statusCode. In older code, we remember that tasks start suspended and need task.resume()."

Senior answer

"We wrap URLSession behind an injectable service protocol to help mock unit testing. We tune URLSessionConfiguration for request timeouts and custom cache limits. We manage cancellation using Swift structured concurrency Task trees. We also map HTTP status codes and URLError transport domains into strongly-typed domain errors before dispatching state updates to @MainActor view models."

Recap

  • URLSession coordinates data transfers over HTTP/HTTPS in iOS.
  • Three main configurations: .default (disk cache), .ephemeral (RAM only), and .background (system daemon).
  • URLSession.shared is a convenient singleton with the default configuration.
  • Modern Swift uses try await URLSession.shared.data(from: url) for clean concurrency.
  • 4xx and 5xx responses do not throw errors; you must check HTTPURLResponse.statusCode.
  • Classic dataTask instances start suspended and require task.resume().
  • Network tasks run on background threads; always update user interfaces on the main thread.
