The simple idea

Think of it like this

Imagine exploring a deep filing cabinet.

You open a folder to read a document. When you want more detail, you place another folder on top.

You can keep adding folders to go deeper. To go back, you lift the top folder off.

That folder stack is a navigation controller.

If someone hands you a clipboard to sign right now, you set the folders aside. You sign the paper and return it.

That temporary interrupt is a modal presentation.

In UIKit, screen transitions fall into two main categories:

  1. Hierarchical Navigation (UINavigationController):
    • Manages a stack of screens in a Last-In, First-Out order.
    • Pushing adds a new screen to the top of the stack.
    • Popping removes the top screen to reveal the screen below.
    • Provides a navigation bar with a back button automatically.
  2. Modal Presentation (present):
    • Slides or fades a new screen over current content.
    • Interrupts the user to complete a focused task.
    • Supports different presentation styles like .pageSheet and .fullScreen.

Interview traps

Trap Pushing without a navigation controller

Calling navigationController?.pushViewController(...) does nothing if no navigation controller exists.

If your view controller is not embedded in a UINavigationController, the optional evaluates to nil.

Initialize UINavigationController(rootViewController: vc) when starting the app window.

Trap Assuming viewWillAppear runs after pageSheet dismiss

On iOS 13 and later, modal presentations use .pageSheet by default.

Because the presenting view never leaves the screen hierarchy, viewWillAppear does not run upon dismissal.

Use delegate callbacks or .fullScreen presentation if you need appearance refresh events.

Trap Creating retain cycles with strong delegates

If a child view controller retains its parent delegate strongly, neither controller can deallocate.

The popped controller stays leaked in memory forever.

Always declare delegate properties as weak var delegate: DelegateType?.

Trap Presenting before the view enters window hierarchy

Calling present() inside viewDidLoad triggers a UIKit runtime warning.

The view is not attached to the window yet, and the presentation fails.

Call present() inside viewDidAppear or in response to a user action button tap.

How to answer in the interview

Fresh answer

"In UIKit, we push and pop screens using UINavigationController for drill-down flows. For focused tasks, we present screens modally using present. We pass data forward by setting properties on the next view controller before pushing."

Junior answer

"We choose navigation patterns based on user intent. We use UINavigationController for hierarchical stacks and present for modal tasks. We use weak delegate protocols to pass data back without retain cycles. In iOS 13+, default .pageSheet modals do not trigger viewWillAppear on presenting views, so we use delegates or completion blocks for updates."

Senior answer

"We decouple view controllers from navigation by implementing Coordinator patterns. This keeps view controllers reusable and testable. For complex workflows, we manipulate the navigation stack using setViewControllers and handle custom transition animations with UIViewControllerAnimatedTransitioning."

Recap

  • UINavigationController manages a LIFO stack of screens with automatic back buttons.
  • Call pushViewController to add a screen, and popViewController to go back.
  • Call present to display modal screens for focused tasks.
  • .pageSheet modals keep the presenting view in the hierarchy on modern iOS.
  • Always use weak delegates to prevent retain cycles when passing data backwards.
  • Call present only after the view is attached to the window hierarchy.
