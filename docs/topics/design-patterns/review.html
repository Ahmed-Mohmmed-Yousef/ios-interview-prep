The simple idea

Software design patterns are proven solutions to common programming problems. They give developers a shared language to build clear, maintainable systems.

In iOS development, patterns fall into three main groups:

  1. Creational Patterns (like Singleton and Factory): Deal with how objects are instantiated.
  2. Structural Patterns (like Adapter and Facade): Organize relationships between classes and protocols.
  3. Behavioral Patterns (like Observer and Delegation): Manage communication between components.

Think of it like this

Think of electrical adapters when traveling internationally. Your laptop charger expects a standard two-pin plug. The hotel wall in another country provides a three-prong triangular outlet. You do not tear open the hotel wall or rewire your laptop charger. Instead, you plug an adapter in between them. The adapter translates the foreign outlet into the interface your charger understands. This is exactly how the Adapter pattern works in software.

The Singleton: Use with care

A singleton is a class that allows only one instance throughout the entire application lifecycle. Apple uses singletons for genuine system-wide resources like UIApplication.shared and FileManager.default.

In Swift, creating a singleton is straightforward: You declare a static let shared constant and make the initializer private. Swift initializes static constants lazily and guarantees thread safety during creation.

However, overusing singletons creates serious problems:

  • Global mutable state: Any part of the app can change values at any time, leading to subtle bugs.
  • Hidden dependencies: Classes use the singleton directly without declaring it in their initializers.
  • Testing friction: Tests run in unpredictable order. If one test changes shared state, subsequent tests can fail randomly.

Interview traps

Trap Overusing Singletons as Global Bags

Treating singletons as convenient global storage bags tightly couples your entire codebase. If an object needs a service, inject it through the initializer. You can supply AppAnalytics.shared as a default parameter while still allowing unit tests to pass a mock.

Trap Conflating Adapter and Facade

Developers often confuse Adapter with Facade. An Adapter converts one specific interface to match an existing protocol. A Facade provides a simplified high-level interface over an entire complex subsystem.

How to answer in the interview

Junior answer

Design patterns are standard templates for solving common architecture problems. Common examples in iOS include Singletons for shared services, Delegation for one-to-one communication, and Observers for state updates. We must be careful with singletons because they introduce global state and make unit testing tricky.

Mid answer

In modern iOS, we balance classic object-oriented design patterns with Swift protocol-oriented programming. For creational needs, Factories decouple instantiation logic from consumer views. For structural needs, Adapters let us isolate third-party libraries behind clean app protocols. While singletons offer thread-safe lazy loading via static let, we avoid calling them directly inside business logic. Instead, we back singletons with protocols and inject them via initializers to preserve testability.

Senior answer

Design patterns are communication tools, not dogmatic rules. When evaluating singletons, I treat them as an implementation detail rather than an architecture. Singletons introduce implicit dependencies, order-dependent test pollution, and concurrency hazards when storing mutable state. In large-scale codebases, we prefer composition roots with explicit dependency injection. We use Structural patterns like Facades and Adapters to enforce architectural boundaries between feature modules and external SDKs.

Recap

  • Design patterns provide standard architectural solutions across Creational, Structural, and Behavioral categories.
  • Swift singletons use static let shared and a private init() for thread-safe lazy creation.
  • Singletons risk global mutable state, hidden dependencies, and test pollution.
  • The Factory pattern centralizes object creation and returns protocol abstractions.
  • The Adapter pattern bridges incompatible interfaces without altering existing source code.
