App Launch Time

The simple idea

Think of it like this

Think of opening a coffee shop in the morning.

You do not bake every pastry for the whole day before unlocking the front door.

You unlock the door, turn on the espresso machine, and greet the first customer fast.

Other prep work happens after the shop is open.

An iOS app works the same way. Show the first frame fast, and delay extra work until after the screen appears.

Every time a user taps your app icon, iOS starts the app in one of three ways.

  1. Cold launch: The app is not in memory or cached by the system. iOS must create a new process and load everything from disk.
  2. Warm launch: The process is not running, but parts of the app binary remain cached in memory. Warm launches are faster than cold launches.
  3. Resume: The app is already suspended in memory. iOS brings it back to the foreground without launching a new process.

Sometimes iOS also uses prewarming. The system starts your app process early, loads linked libraries, and pauses the process before user code runs.

A cold launch has two main parts: pre-main and post-main.

Pre-main work

Before your Swift main entry point runs, the dynamic linker (dyld) prepares your app binary.

  • dyld loads your app executable and every dynamic library (separate code frameworks linked at launch).
  • dyld resolves symbols and fixes memory addresses across libraries.
  • The system runs static initializers, such as Objective-C +load methods and C++ static constructors.

In Swift, global variables and static let properties initialize lazily (only when your code reads them for the first time), not before main.

To speed up pre-main time, remove unused frameworks and avoid +load or C++ static constructors.

You can also use mergeable libraries in Xcode. Set MERGEABLE_LIBRARY to Yes on framework targets and MERGED_BINARY_TYPE on your app target.

In Debug builds, frameworks stay dynamic so builds stay fast. In Release builds, Xcode merges them into one binary so dyld has less work at launch.

Post-main work to the first frame

After main runs, SwiftUI or UIKit creates your app object (@main or UIApplicationMain) and connects a scene.

In UIKit, the system calls application(_:willFinishLaunchingWithOptions:), application(_:didFinishLaunchingWithOptions:), and scene(_:willConnectTo:options:).

Then the app builds its initial views, calculates layout, and draws the first frame on screen.

Keep startup light until the first frame appears. Aim for a fast first frame (around 400 milliseconds is a common target for instant feel).

If your app blocks the main thread for too long at launch, the system watchdog stops it with crash code 0x8badf00d.

Measuring launch time

Do not guess where startup time goes. Measure it with Apple tools:

  • Instruments (App Launch template): Shows pre-main dyld work, main-thread hangs, and time to the first frame.
  • OSSignposter: Marks custom startup intervals (such as loading config) so they appear in Instruments.
  • XCTApplicationLaunchMetric: Measures launch time inside automated XCTest UI tests. It replaces the deprecated XCTOSSignpostMetric.applicationLaunch.
  • Xcode Organizer and MetricKit (MetricManager / MetricResult): Reports real-world launch histograms from users in production. In iOS 27, MetricResult provides TimeToFirstDrawMetric (standard launch to first draw) and OptimizedTimeToFirstDrawMetric (launches sped up by system prewarming). It also includes ExtendedLaunchMetric for extended startup tasks. Before iOS 27, apps used the now-deprecated MXAppLaunchMetric (histogrammedTimeToFirstDraw, histogrammedOptimizedTimeToFirstDraw, and histogrammedExtendedLaunch).

    Quick check (not scored)

    Which launch type forces iOS to create a new process and load the app binary from disk with no cached pages?

    A cold launch happens when the app is not in memory or system cache, so the OS must build the process from scratch.

    In code

    Never block application(_:didFinishLaunchingWithOptions:) or your root @main initializer with analytics setup or heavy file reads.

    Load only what the first screen needs. Defer optional work until after the first frame is ready.

    This pattern keeps critical launch steps tiny. Heavy services like analytics or crash reporting start only after the user sees the screen.

    Swift also helps you avoid pre-main work through lazy static let initialization. The property initializes only when your code reads it.

    Using OSSignposter lets you see exact start and end times for custom launch tasks inside Instruments.

    Quick check (not scored)

    How do Xcode mergeable libraries speed up cold launches without slowing down daily development builds?

    Mergeable libraries act as dynamic frameworks in Debug builds and merge into the app binary in Release builds, cutting dynamic linker work.

    Go deeper: Monitoring launch regressions in XCTest and MetricKit

    You can automate cold launch tests in UI test targets using XCTApplicationLaunchMetric.

    In production on iOS 27, MetricManager delivers MetricResult entries with TimeToFirstDrawMetric, OptimizedTimeToFirstDrawMetric, and ExtendedLaunchMetric (replacing older MXAppLaunchMetric histograms).

    Interview traps

    Trap Measuring launch time in Debug mode on the Simulator

    Many developers time app launch in the Xcode Simulator using a Debug build.

    Debug builds turn off compiler optimizations and add extra runtime checks. The Simulator also uses your Mac processor and disk, which are much faster than an iPhone.

    Always measure launch time using a Release build on a real physical device.

    Trap Assuming protected user data is ready during prewarming

    After a device reboot, iOS can prewarm or start an app in the background before the user unlocks the phone.

    Files with completeUntilFirstUserAuthentication protection and many Keychain items stay locked until that first unlock.

    If early launch code reads protected storage right away, those reads can fail or return nil.

    Check UIApplication.shared.isProtectedDataAvailable and delay reading user secrets until the scene becomes active or protected data is ready.

    Trap Initializing every SDK inside didFinishLaunchingWithOptions

    Teams often paste five or ten third-party SDK setup calls into application(_:didFinishLaunchingWithOptions:).

    Those calls add dynamic framework load time and run work before the first frame.

    Initialize optional SDKs lazily when a feature opens, or schedule them after the first frame renders.

    How to answer in the interview

    Mid answer

    To improve app launch time, I first measure a Release build on a real device using the App Launch template in Instruments. I split the trace into pre-main work and post-main work up to the first frame. For pre-main, I reduce dynamic frameworks, merge libraries where possible, and remove static initializers like Objective-C +load. For post-main, I move analytics, disk I/O, and network calls out of didFinishLaunchingWithOptions so the first frame appears quickly without risking a watchdog crash.

    Senior answer

    I treat launch time across three stages: pre-main, first frame, and extended launch. First, I profile a Release build on an older supported device with Instruments and OSSignposter intervals to separate dyld time from UI setup. In Xcode, I use mergeable libraries (MERGEABLE_LIBRARY and MERGED_BINARY_TYPE) so Debug builds stay fast while Release builds avoid dynamic linking work. I defer non-critical SDKs past the first frame. I also guard against prewarming before first unlock so protected reads do not fail silently. Finally, I add XCTApplicationLaunchMetric tests in CI and monitor MetricResult launch histograms (TimeToFirstDrawMetric and OptimizedTimeToFirstDrawMetric, or MXAppLaunchMetric on older OS versions) in Xcode Organizer.

    Recap

    • Cold launches are the slowest because iOS creates a new process and loads binaries from disk.
    • Pre-main time is dominated by dyld loading dynamic libraries and running static initializers.
    • Mergeable libraries keep fast Debug builds while removing dyld launch overhead in Release builds.
    • Keep didFinishLaunchingWithOptions minimal and defer optional setup until after the first frame.
    • Always profile launch time on a real device in Release configuration with Instruments, OSSignposter, and XCTApplicationLaunchMetric.
