The simple idea

Think of it like this

Think of ordering food. When you order coffee at a counter, you wait and receive your cup immediately before leaving the register. That is a non-escaping closure. When you order a pizza delivery, you hang up the phone and receive your pizza thirty minutes later. The restaurant needs your phone number and address after the initial call ends. That is an escaping closure.

In Swift, function closure parameters are non-escaping by default.

A non-escaping closure runs inside the function body. The enclosing function does not finish until the closure finishes. Because the closure cannot outlive the function, Swift allocates it on the stack.

An escaping closure outlives the function that received it.

It is passed into a function, but it executes after that function returns. Common examples include network requests and scheduled timers. Because an escaping closure must stay alive in memory, Swift stores it on the heap. You must mark that parameter with @escaping.

Closures also capture variables from surrounding scope by reference by default.

If a class instance stores an escaping closure, and the closure holds a strong reference to that instance, a retain cycle occurs. Neither object can ever be deallocated.

A capture list like [weak self] breaks retain cycles by converting the reference into an optional weak reference.

What happens to a weak self reference when the class instance deallocates?

weak references in Swift are always optional. When the referenced object deallocates, ARC sets the weak reference to nil.

Interview traps

Trap Assuming non-escaping closures cause retain cycles

Non-escaping closures execute synchronously during the function call and are discarded immediately. They cannot create retain cycles. Adding [weak self] inside non-escaping functions like map or filter is unnecessary.

Trap Using unowned self for asynchronous network tasks

unowned assumes that the referenced object will never deallocate before the closure executes. If a user dismisses a view controller before a network call finishes, accessing unowned self crashes the app. Always prefer [weak self] for asynchronous network completions.

Trap Believing capture lists only work with self

Capture lists can capture any variable from the surrounding scope. When capturing a value type like [count], Swift creates an immutable copy at the moment of closure creation.

How to answer in the interview

Fresh answer

In Swift, closure parameters are non-escaping by default and run before the function returns. When a closure runs later, like after an asynchronous network call, we mark it @escaping. We use [weak self] to avoid retain cycles and memory leaks.

Junior answer

Swift closure parameters are non-escaping by default, enabling stack allocation optimizations. If a closure is stored or executed after the enclosing function returns, it must be annotated with @escaping and moves to the heap. When an escaping closure captures self strongly, and self owns the closure, a retain cycle occurs. We write [weak self] in the capture list to break the cycle by creating an optional weak reference.

Senior answer

Escaping closures outlive their calling scope and require heap allocation. They demand deliberate reference management to avoid retain cycles with view models or controllers. Using capture lists with [weak self] prevents strong reference cycles by creating non-retaining optional pointers that ARC zeroes on deallocation. In modern Swift, structured concurrency with async/await replaces many escaping completion handlers, eliminating callback lifecycle hazards entirely.

Recap

  • Closure parameters in Swift are non-escaping by default.
  • An escaping closure executes after the enclosing function returns and requires @escaping.
  • Closures capture surrounding variables by reference by default.
  • [weak self] creates an optional weak reference to prevent strong reference cycles.
  • [unowned self] creates an unowned reference that crashes if the instance has already deallocated.
  • Capture lists take immutable snapshot copies of value types at creation time.
