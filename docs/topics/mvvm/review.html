The simple idea

Mobile apps display data on a screen and process user actions. When you put networking, data formatting, and visual layout in one file, code becomes hard to read and test. The Model-View-ViewModel (MVVM) pattern divides your screen into three distinct parts:

  1. Model: Pure data objects and domain rules. Models hold raw values such as numbers, strings, and dates. They do not know anything about user interfaces.
  2. View: Visual elements on the screen. Views lay out controls, display text, and capture user gestures like button taps.
  3. ViewModel: The bridge between Model and View. The ViewModel stores UI state, runs presentation logic, and formats raw values into readable strings.

Think of it like this

Think of a restaurant. The kitchen chefs are the Model. They prepare the raw ingredients and cook the meals. The dining room table is the View. It presents the meal to the guest in a clean setting. The waiter is the ViewModel. The waiter takes requests from the guest, communicates with the kitchen, and serves the finished dish in a pleasant format. The guest never enters the kitchen, and the chef never waits on tables.

Why use MVVM?

In standard MVC (Model-View-Controller), view controllers frequently become bloated with networking, validation, and string formatting. This problem is often called Massive View Controller. MVVM solves this problem by moving presentation logic out of the view controller or SwiftUI view.

The ViewModel does not import UIKit or render SwiftUI views directly. Because the ViewModel contains no user interface controls, you can write fast unit tests for it without launching a simulator.

Interview traps

Trap The Massive ViewModel

Moving all logic out of a view controller into a view model can create a Massive ViewModel. Do not place networking requests, database queries, and navigation handling inside a single ViewModel class. Instead, inject specialized service objects or repository protocols into your ViewModel. Keep the ViewModel focused on managing UI state.

Trap Overusing ViewModels for simple SwiftUI views

SwiftUI views are lightweight structs that already observe state efficiently. Do not force a separate ViewModel for static views, simple forms, or pure UI animations. Creating a ViewModel for every trivial screen adds unnecessary boilerplate without providing testability benefits.

How to answer in the interview

Junior answer

MVVM stands for Model, View, and ViewModel. The Model holds our raw data. The View displays the user interface and passes user actions forward. The ViewModel contains the presentation logic and state. It converts raw data into strings that the View can display easily.

Mid answer

MVVM separates presentation logic from UI rendering, resolving the Massive View Controller issue in iOS. The View observes the ViewModel through SwiftUI Observation or Combine. When users interact with the View, it calls methods on the ViewModel. The ViewModel mutates state properties and coordinates with business services. Because the ViewModel has no UI dependencies, we can write unit tests for UI states and formatting without running the simulator.

Senior answer

In modern iOS, MVVM provides clean boundary separation when paired with Dependency Injection and unidirectional data flow. In SwiftUI, we model ViewModels as @Observable classes isolated to @MainActor, keeping the views declarative and dumb. However, we must avoid treating MVVM as a silver bullet. A ViewModel should delegate networking to repositories and navigation to coordinators or routers. For trivial screens, native SwiftUI state properties are often cleaner than an artificial ViewModel layer.

Recap

  • MVVM splits responsibilities into Model (domain data), View (visual UI), and ViewModel (presentation state).
  • The ViewModel formats raw data into displayable text and coordinates user actions.
  • ViewModels contain no UI framework dependencies, making presentation logic easy to unit test.
  • Avoid Massive ViewModels by injecting services for networking and storage.
  • Do not create unnecessary ViewModels for simple static SwiftUI views.
