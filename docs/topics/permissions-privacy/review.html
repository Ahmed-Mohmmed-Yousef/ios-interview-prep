The simple idea

Think of it like this

Imagine visiting a building that has private secure offices.

Before you enter a private office, you must knock on the door and ask for permission.

You must state your name and explain why you need to enter.

If the owner welcomes you, you step inside and begin your work.

If the owner turns you away, knocking repeatedly is rude and pointless.

You cannot open the door yourself. You must accept their choice or ask building security to update your badge.

If the door has a parental lock, even the owner cannot invite you inside.

iOS protects private hardware and personal data using system permissions.

Protected items include the camera, microphone, photo library, contacts, location, and health records.

Your app must explain why it needs access. You place these explanations inside your Info.plist file.

Apple calls these explanations purpose strings.

When an app checks permission status, the system returns one of four primary states:

  1. Not Determined: The user has never seen the permission prompt. Your app can trigger the system prompt now.
  2. Authorized: The user granted permission. Your app can use the hardware or data freely.
  3. Denied: The user tapped "Do Not Allow" or disabled the feature in Settings. The system prompt will never show again. You must guide the user to the Settings app.
  4. Restricted: Device controls like Screen Time or enterprise management block access. The user cannot turn it on.

Some frameworks offer partial access. For example, Photos supports a limited status where the user picks only specific pictures.

Modern iOS also requires a privacy manifest file named PrivacyInfo.xcprivacy.

This file declares collected data categories, tracking domains, and reasons for using sensitive system APIs.

Quick check (not scored)

What should your app do when the user denies camera permission?

Once denied, the system alert never shows again. You must guide the user to the Settings app to change the setting.

In code

Check permission status before performing an action.

Handle each state clearly in your logic.

In your app, open the Settings app by calling UIApplication.shared.open(URL(string: UIApplication.openSettingsURLString)!).

Always configure proper purpose strings in your project configuration.

Quick check (not scored)

Restricted status means parental controls or mobile device management policies prevent access. The user cannot turn it on in Settings.

Interview traps

Trap Missing Info.plist purpose strings

If you access the camera or location without the required Info.plist key, iOS terminates your app immediately.

The app crashes with a SIGABRT error in both debug and release builds.

Always verify that every hardware API has its matching description string.

Trap Calling requestAuthorization repeatedly after denial

Some developers call the request method again hoping the dialog appears a second time.

The system prompt displays only once in the entire lifecycle of your app install.

Subsequent calls return .denied without showing any interface.

Direct the user to the Settings app instead.

Trap Asking for all permissions at launch

Requesting camera, microphone, and location permissions on first launch overwhelms users.

Users often deny permissions when they do not understand the need.

Ask for permissions in context only when the user taps a feature that requires them.

Trap Treating restricted as denied

Do not show a "Go to Settings" button when the status is .restricted.

Parental controls or company device policies lock the setting.

The user cannot change the setting, so sending them to Settings causes confusion.

How to answer in the interview

Fresh answer

"iOS protects user privacy with system permissions for things like the camera and location. We must add a purpose string in Info.plist, or the app crashes. When checking status, we handle not determined, authorized, denied, and restricted. If the user denies permission, the prompt will not show again, so we guide them to the Settings app."

Junior answer

"We follow Apple guidelines by requesting permissions in context when the user activates a feature, rather than on launch. We check authorization status first. If denied, we explain why access helps and offer a deep link to Settings. If restricted, we disable the feature gracefully because parental controls block it. We also include PrivacyInfo.xcprivacy to declare API usage and data collection."

Senior answer

"Our architecture decouples user intent from permission requests by using custom priming screens. This prevents burning the one-time system dialog before users understand the value. We handle granular permissions such as limited photo access. We also automate compliance with PrivacyInfo.xcprivacy manifests, documenting Required Reason APIs and tracking domains to streamline App Store privacy reports."

Recap

  • Protected resources require purpose strings in Info.plist or the app crashes immediately.
  • Authorization states include .notDetermined, .authorized, .denied, and .restricted.
  • The system permission prompt displays only once per app installation.
  • When permission is denied, direct the user to UIApplication.openSettingsURLString.
  • When permission is restricted, parental controls or MDM profiles prevent access.
  • Request permissions in context when the user taps an action, not at app launch.
  • Modern iOS apps require a PrivacyInfo.xcprivacy manifest for App Store submission.
