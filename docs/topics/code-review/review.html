The simple idea

Code review is a collaborative peer review process. Before merging code into the main branch, another engineer inspects the proposed changes.

Google defines the main goal of code review clearly. The primary purpose is to make sure that the overall code health of the codebase improves over time.

Code review is not about achieving perfection. There is no perfect code. There is only better code.

If a pull request improves codebase health and meets project standards, you should approve it. You do not block progress waiting for flawless code.

Think of it like this

Think of code review as an editorial check before publishing a book chapter.

The editor checks for plot holes, factual errors, and clear storytelling. The editor does not rewrite the author entire personal writing voice.

In software, reviewers guard system architecture and correctness without imposing personal style preferences.

In iOS development, reviewers look for specific danger areas.

These include memory retain cycles in closures, concurrency data races, missing error handling, and unhandled edge cases.

Automated tools like SwiftLint and continuous integration should check formatting and unit tests. Human reviewers focus on design, correctness, and maintainability.

Interview traps

Trap Blocking pull requests over personal styling opinions

Do not block approvals because someone indented code differently than your preference. Use automated formatters and SwiftLint to enforce style rules. Reserve your human review for architecture, logic bugs, and maintainability.

Trap Submitting massive pull requests

Avoid submitting changes with thousands of lines of code. Large pull requests trigger review fatigue, receive superficial reviews, and hide critical bugs. Keep pull requests under 400 lines so reviewers can review thoroughly.

How to answer in the interview

Junior answer

Code reviews help us catch bugs early and learn from each other. When reviewing iOS code, I check for memory leaks like missing weak self in closures, clear naming, and adequate unit tests. I keep feedback constructive by critiquing the code rather than the person.

Mid answer

I approach code reviews following the principle that review improves overall codebase health over time. I look for architectural alignment, edge-case safety, Swift 6 concurrency correctness, and memory management. I use comment tags like nit: or blocking: to clearly separate non-blocking preferences from critical defects.

Senior answer

At a senior level, code review is an essential cultural tool for engineering excellence and mentorship. I promote small, focused pull requests and delegate style enforcement to automated CI pipelines. My reviews focus on system design, boundary safety, and maintainability. When disagreements arise, I seek consensus through shared technical principles or quick synchronous chats rather than prolonged comment threads.

Recap

  • The primary purpose of code review is to improve codebase health over time.
  • Reviewers should approve pull requests that improve the codebase, without waiting for unattainable perfection.
  • Offload style and formatting checks to automated linters and CI bots.
  • Human reviews focus on architecture, concurrency, memory leaks, and test coverage.
  • Use clear comment labels to distinguish blocking defects from optional suggestions.
  • Keep pull requests small to prevent review fatigue and catch subtle defects.
