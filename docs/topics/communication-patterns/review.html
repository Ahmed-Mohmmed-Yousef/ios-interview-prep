Interview question

When should an iOS developer use a delegate instead of a closure or notification?

Your guess first (not scored). We come back to it in the recap.

The simple idea

Think of it like this

Imagine three different ways people share information at work.

First, imagine a manager and a personal assistant. They have a clear contract with several duties. The manager can ask questions, and the assistant replies with answers. This is like a delegate.

Second, imagine calling a courier service to deliver a package. You give the driver a single instruction: call me when the delivery finishes. Once the task finishes, you receive one callback. This is like a closure.

Third, imagine a company loudspeaker on the office ceiling. The office manager announces that the building closes in ten minutes. Anyone with ears can hear the announcement. The speaker does not know who is listening. This is like a notification.

iOS apps use these three patterns to send messages between objects:

  1. Delegates: One-to-one communication with a formal protocol. The sender can ask for decisions and receive values back.
  2. Closures: One-to-one communication with a quick block of code. Great for a single callback or event.
  3. NotificationCenter: One-to-many broadcast. The sender broadcasts an event to any object that registered as an observer.

Why must a delegate reference usually be marked with the weak keyword?

A parent object often owns its child view or service. If the child also holds a strong reference to the parent delegate, neither object can deallocate.

Quick check (not scored)

On which thread does NotificationCenter execute observer blocks by default?

NotificationCenter delivers notifications synchronously on the thread where post was called. Always dispatch UI updates to the main thread.

Interview traps

Trap Retain cycles in closures

When an escaping closure refers to properties or methods on self, it captures self strongly. If self also stores that closure, a retain cycle forms. Neither object can ever free its memory. Always use [weak self] in stored closures when self owns the closure.

Trap Missing weak on delegates

Forgetting weak on a delegate variable is one of the most common mistakes in iOS interviews. If a view controller creates a child view and assigns itself as the delegate, a strong property creates a leak. Always constrain delegate protocols to AnyObject and mark the delegate variable weak.

Trap Zombie observer tokens

When you add an observer using the block-based NotificationCenter method, it returns an observer token. If you do not store and remove this token, the observer continues listening. The closure may capture dead views and waste memory. Store the token and remove it when the object deallocates.

Trap Background notification posts

NotificationCenter.default.post delivers notifications on the caller thread. If a network service posts a notification on a background thread, the observer runs on that background thread. Updating user interface elements directly inside that observer causes race conditions and crashes.

How to answer in the interview

Fresh answer

iOS provides three main ways for objects to talk to each other. A delegate is a one-to-one link that uses a protocol. We mark delegate variables with weak to avoid retain cycles. Closures are blocks of code passed as callbacks for single tasks. Notifications broadcast events from one sender to many listeners across the app.

Junior answer

I choose patterns based on the number of listeners and whether two-way communication is needed. For one-to-one communication with multiple related methods or back-and-forth questions, I use a delegate protocol with AnyObject and a weak reference. For a single completion event, I use a closure with [weak self]. For one-to-many communication where the sender does not know the listeners, like user logout, I use NotificationCenter. I remember that notifications run synchronously on the posting thread, so UI work must dispatch to the main queue.

Senior answer

I evaluate coupling, type safety, and memory management. Delegates provide strict compile-time contracts and are easy to mock in unit tests. Closures minimize boilerplate for asynchronous completion handlers and flow naturally into Swift concurrency. NotificationCenter decouples components completely, but payload dictionaries lack compile-time safety and make the data flow harder to trace. In modern Swift, I prefer typed async sequences with NotificationCenter.default.notifications(named:) instead of manual token removal.

Recap

  • Delegates provide one-to-one, two-way communication with a typed protocol contract.
  • Always constrain delegate protocols to AnyObject and declare delegate properties as weak.
  • Closures provide lightweight one-to-one callbacks, ideal for single asynchronous events.
  • Capture [weak self] in escaping closures stored on an object to prevent retain cycles.
  • NotificationCenter broadcasts one-to-many events across unrelated parts of the app.
  • Notifications run synchronously on the posting thread and block-based tokens require cleanup.
