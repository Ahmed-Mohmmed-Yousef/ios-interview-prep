Opaque and Boxed Types: some vs any

The simple idea

Think of it like this

Think of ordering a surprise gift. An opaque type (some Gift) means the shop wraps one real, specific item in opaque paper. You know it is a gift, and the shop knows exactly what it is. A boxed type (any Gift) is a magic box that can hold completely different items over time. The magic box needs extra packaging to hold different sizes.

In Swift, some declares an opaque type. An opaque type represents one specific concrete type that conforms to a protocol. The caller only knows the protocol, but the compiler knows the real underlying type. Because the compiler knows the exact type, it preserves full type identity and optimizes the code with static dispatch.

In contrast, any declares a boxed protocol type, also known as an existential type. An any type is a box that can hold any conforming type at runtime.

A boxed type lets you store different types in one collection, like an array containing circles and squares.

However, that flexibility has a price. Boxed types use dynamic dispatch through witness tables. Large values also allocate memory on the heap.

Default to some for speed and type safety; use any only when you need to store different types together.

Interview traps

Trap Returning different concrete types from a function returning some

If a function return type is some Shape, every return statement must return the exact same concrete type. You cannot return a Circle in an if branch and a Square in an else branch. If you need dynamic branches, return any Shape or wrap the branches in a custom enum.

Trap Using any everywhere by default

In older Swift code, developers wrote let item: Protocol everywhere. Swift 6 makes the existential box explicit by requiring any Protocol. Writing any introduces runtime boxes and dynamic dispatch. Always prefer some unless you truly need heterogeneous collections.

How to answer in the interview

Fresh answer

The keyword some creates an opaque type. The function chooses one concrete type, but hides the exact name from callers. The keyword any creates a boxed type that can hold different types at runtime. We use some for performance and any when we need to mix different types in an array.

Junior answer

The difference between some and any is static versus dynamic typing. With some, the compiler knows the exact concrete type, enabling static dispatch and full type identity. All return branches must return the same type. With any, Swift creates an existential container that can hold different conforming types dynamically. Swift 6 requires the any keyword to make this runtime overhead explicit.

Senior answer

Opaque types (some) provide reverse generics, hiding implementation details while retaining compile-time type identity and zero-cost abstraction. Boxed existentials (any) store values in existential containers with a 3-word value buffer, allocating heap memory for larger values. They incur witness table dynamic dispatch. Modern Swift automatically opens existentials when passed into generic arguments taking some. We default to some and reserve any for heterogeneous collections.

Recap

  • some represents an opaque type with one fixed underlying concrete type.
  • The compiler knows the concrete type behind some, enabling static dispatch and optimizations.
  • Functions returning some must return the same concrete type from all branches.
  • any creates a boxed existential type that can hold different types dynamically.
  • Collections containing mixed conforming types must use any.
  • Swift 6 requires the any keyword to make existential container costs visible.
  • Prefer some by default for performance and safety; use any when dynamic flexibility is required.
