UserDefaults and Files

Why should you never store user authentication tokens or passwords in UserDefaults?

Your guess first (not scored). We come back to it in the recap.

The simple idea

Think of it like this

Imagine a small nightstand next to your bed.

On the nightstand, you keep a notepad with quick notes, like your alarm time or favorite reading light setting.

You would never leave your house keys or gold jewelry in an open notepad on the nightstand.

Anyone walking past could read your personal secrets.

For expensive jewelry, you place items inside a locked metal safe.

For large binders of tax papers, you store boxes in the garage or attic filing cabinets.

In iOS, UserDefaults is your digital nightstand.

It is a lightweight key-value store intended for small user settings:

  • Whether the user finished the onboarding walkthrough.
  • Their preferred theme (Light, Dark, or System).
  • Sound effects toggles and audio volume levels.

UserDefaults is backed by a property list file on disk.

When your app launches, iOS loads the entire property list file into memory.

Storing large items like images or databases slows down app launch and wastes memory.

UserDefaults has no encryption. Never store passwords, tokens, or private secrets in UserDefaults.

For larger assets like documents, pictures, or databases, use FileManager to store files inside the App Sandbox.

The sandbox isolates your files from all other apps on the device:

  1. Documents/: For user-created files. This folder is backed up to iCloud.
  2. Library/Caches/: For downloaded pictures and temporary cache files. iOS can purge these files when storage is low. They are never backed up.
  3. Library/Application Support/: For app databases and internal configuration files. This folder is backed up to iCloud.
  4. tmp/: For short-lived scratch files needed during an active session.

In code

Store simple settings and boolean flags in UserDefaults.

In SwiftUI, use @AppStorage to bind view state to user defaults directly.

Pick the correct sandbox directory using FileManager.

Write files using atomic writing to prevent corrupted data if the app crashes during a write.

Quick check (not scored)

Why should you pass the .atomic option when writing data to disk with Foundation?

Atomic writing creates an auxiliary temporary file and renames it when finished, protecting existing files from partial write corruption.

Interview traps

Trap Storing secrets in UserDefaults

UserDefaults is not encrypted.

The underlying .plist file can be read directly by anyone inspecting device backups.

Store passwords, tokens, and personal credentials in the Keychain instead.

Trap Storing megabytes of data in UserDefaults

UserDefaults loads the entire file into RAM when your app starts up.

Storing high-resolution photos or large collections in UserDefaults makes your app launch sluggish.

Save large files to the filesystem using FileManager.

Trap Saving cache files in the Documents folder

Files saved in Documents are backed up to iCloud by default.

If you store megabytes of temporary images in Documents, Apple may reject your app during review.

Save re-downloadable content in Library/Caches instead.

Trap Calling synchronize() manually

Many developers still call UserDefaults.standard.synchronize() after writing values.

This method was deprecated in iOS 12.

The operating system automatically batches and persists writes to disk asynchronously.

How to answer in the interview

Fresh answer

"UserDefaults is for small settings like dark mode flags or onboarding state. We should never store passwords in UserDefaults because it is not encrypted. For larger files like documents or photos, we use FileManager in the app sandbox. User files go in Documents and back up to iCloud, while cached images go in Caches so they do not waste backup space."

Junior answer

"UserDefaults is backed by a plist file that loads entirely into memory on launch, so it is strictly for lightweight primitives. Secrets belong in Keychain, and large assets belong on disk via FileManager. The sandbox provides distinct directories: Documents for user-created content that backs up to iCloud, Application Support for internal databases, and Caches for purgeable assets. When writing files, we use .atomic to avoid corrupted writes."

Senior answer

"We tier data storage based on security, memory footprint, and backup policies. We isolate secrets in Keychain with hardware-backed access control. We store UI preferences in UserDefaults via @AppStorage, keeping launch plists under a few kilobytes. For file storage, we enforce atomic writes via Data.WritingOptions.atomic, store databases in Application Support/, and place transient assets in Library/Caches/ to respect Apple iCloud backup guidelines."

Recap

  • UserDefaults is for small user preferences and flags.
  • UserDefaults loads completely into memory on launch; avoid large data.
  • UserDefaults is unencrypted; never store passwords or auth tokens in it.
  • UserDefaults.standard.synchronize() is deprecated; writes persist automatically.
  • Documents/ holds user files and backs up to iCloud.
  • Library/Caches/ holds purgeable cache data and is not backed up.
  • Library/Application Support/ holds internal app databases and backs up to iCloud.
  • Use .atomic writes with FileManager to prevent corrupted files during crashes.
