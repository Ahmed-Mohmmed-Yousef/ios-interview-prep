The simple idea

Think of it like this

Imagine a folding dining table. When guests arrive, you unfold both table leaves to seat a large dinner party with multiple plates. When eating alone in a small kitchen, you fold the leaves down into a compact desk. Adaptive layouts work like this folding table, expanding into multiple columns on large screens and folding into a single column on compact screens.

iOS devices come in many shapes, from a pocket-sized iPhone to a large 13-inch iPad Pro. Furthermore, iPadOS allows users to run apps side-by-side using Split View, in a floating overlay using Slide Over, or in resizable windows using Stage Manager.

To handle this variety without hardcoding screen sizes, iOS uses size classes. A size class categorizes available screen space into two values:

  1. Compact: Constrained space, typical of an iPhone in portrait orientation or an iPad window sharing the screen in Split View.
  2. Regular: Expansive space, typical of a full-screen iPad or a large iPhone in landscape orientation.

Every view environment provides both a horizontal size class (horizontalSizeClass) and a vertical size class (verticalSizeClass).

Never design for a specific device model; always design for the active size class and available window bounds.

In code

Classifying layout size categories

Your app should respond to container width rather than checking physical hardware identifiers.

import Foundation

enum WindowWidthCategory {
    case compact
    case regular

    static func from(width: Double) -> WindowWidthCategory {
        width >= 768.0 ? .regular : .compact
    }
}

let fullPadWidth = 1024.0
let splitPadWidth = 375.0

print("Full: \(WindowWidthCategory.from(width: fullPadWidth))")
print("Split: \(WindowWidthCategory.from(width: splitPadWidth))")

OutputFull: regular
Split: compact

When the user resizes an iPad window, your views receive updated layout traits dynamically.

Adapting navigation columns in SwiftUI and UIKit

In SwiftUI, NavigationSplitView displays multi-column layouts on regular width and collapses automatically on compact width. You can also determine column counts programmatically based on size classes.

import Foundation

struct AdaptiveColumnPlan {
    let horizontalSizeClass: String

    var columnCount: Int {
        horizontalSizeClass == "regular" ? 2 : 1
    }
}

let padPlan = AdaptiveColumnPlan(horizontalSizeClass: "regular")
let phonePlan = AdaptiveColumnPlan(horizontalSizeClass: "compact")

print("iPad columns: \(padPlan.columnCount)")
print("iPhone columns: \(phonePlan.columnCount)")

OutputiPad columns: 2
iPhone columns: 1

In SwiftUI, use @Environment(\.horizontalSizeClass) to read the active size class. In UIKit, use registerForTraitChanges([UITraitHorizontalSizeClass.self]) to observe updates in iOS 17 and later.

Interview traps

Trap Checking UIDevice userInterfaceIdiom for layout decisions

Do not write if UIDevice.current.userInterfaceIdiom == .pad to pick layouts. An iPad running in Slide Over or Split View has a narrow width identical to an iPhone. If you force a multi-column iPad layout inside a narrow Split View window, text truncates and columns overlap. Always branch on horizontalSizeClass or container width instead.

Trap Using UIScreen.main.bounds to calculate view frames

UIScreen.main.bounds returns the physical hardware display resolution, not your app window size. On iPad with Stage Manager or Split View, your window is only a fraction of the hardware screen. UIScreen.main is deprecated in modern iOS. Always calculate frames using view bounds, container geometry, or Auto Layout constraints.

Trap Using deprecated traitCollectionDidChange

traitCollectionDidChange(_:) was deprecated in iOS 17. Apple replaced it with the modern trait registration API. Use registerForTraitChanges([UITraitHorizontalSizeClass.self]) on views or view controllers to register precise closure handlers.

How to answer in the interview

Fresh answer

Adaptive layout means designing user interfaces that adjust smoothly across iPhone and iPad screens. Apple provides size classes, dividing horizontal and vertical space into compact and regular categories. I avoid hardcoding screen sizes or checking device hardware models. Instead, I use SwiftUI NavigationSplitView and size class environment values so layouts scale from single columns on phones to multiple columns on tablets.

Senior answer

Building robust iPad experiences requires embracing variable window geometries, multitasking, and Stage Manager. I treat the app window as an arbitrary viewport, relying on Auto Layout and ViewThatFits rather than fixed screen constants. In SwiftUI, I use NavigationSplitView which provides automatic column collapse when transitioning between regular and compact widths. For UIKit view controllers, I register for specific trait changes with registerForTraitChanges introduced in iOS 17. Finally, I support multi-scene architectures with UISceneConfiguration so users can open multiple instances of the app simultaneously.

Recap

  • Size classes abstract screen space into compact and regular categories for width and height.
  • An iPad app running in Slide Over or Split View transitions dynamically to a compact horizontal size class.
  • Never check UIDevice.current.userInterfaceIdiom for layout decisions; use horizontalSizeClass.
  • UIScreen.main.bounds is deprecated because multitasking windows do not match physical screen size.
  • SwiftUI NavigationSplitView displays side-by-side columns on regular width and collapses into a stack on compact width.
  • In iOS 17+, register trait changes with registerForTraitChanges instead of traitCollectionDidChange.
